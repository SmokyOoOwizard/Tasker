# Связи и иерархия задач

Одна задача может ссылаться на другую: «зависит от», «дублирует», «клонирует», «связана с», «причина» — как связи в Jira.

- **Связь и её стороны.** Связь — «задача A —тип→ задача B». У типа два названия — по одному для каждой стороны: A видит **исходящее** («blocks»), B — **входящее** («is blocked by»). Задачи только одного проекта; нельзя связать задачу с самой собой; одна и та же связь (тип, источник, цель) не повторяется.
- **Типы.** Настраиваются в проекте (`link-types`, у каждого `name`, `outwardName`, `inwardName`, `allowCycles`, `hierarchical`; название типа уникально без учёта регистра). По умолчанию — набор Jira: **Blocks** (blocks / is blocked by), **Duplicate** (duplicates / is duplicated by), **Cloners** (clones / is cloned by), **Relates** (relates to / relates to), **Problem/Incident** (causes / is caused by) и иерархический **Parent/Child** (includes / is part of, см. «Иерархия» ниже). Это обычные типы: можно переименовать, поменять названия сторон, удалить, добавить свои — например, «depends on» / «is a dependency of». Если оба названия совпадают (**Relates**), у связи нет направления: она выглядит одинаково с обеих сторон, а обратная связь (B relates to A) считается уже имеющейся. Пока в проекте нет сохранённых типов, чтение (список, `task links`, `task get`) показывает типы по умолчанию, ничего не записывая; в файлы или БД они попадают при первой записи — создании, правке или удалении типа, добавлении связи (так проекты, созданные до связей, получают их без миграции, а просмотр задачи не создаёт файлов). У показанных, но ещё не сохранённых типов `version` — `default`: после сохранения у них настоящая версия, и изменение со старой даст `409 modified` — перечитайте. id у типов по умолчанию детерминированные из проекта и ключа, поэтому две ветки репозитория, где они сохранились независимо, не конфликтуют. Удалили все типы — чтение снова покажет типы по умолчанию (оставьте хотя бы один свой, чтобы этого не было).
- **Циклы.** Связь, замыкающая цикл любой длины (A blocks B, B blocks C, C blocks A — и просто «A blocks B» при уже существующей «B blocks A»), отклоняется, если у её типа признак **`allowCycles`** выключен: `400` в REST, `[invalid]` в MCP, `Error:` в консоли — с путём цикла: `Cycle: TSK-3 → TSK-1 → TSK-2 → TSK-3 (link type 'Blocks' does not allow cycles; …)` (у задачи без серии вместо ссылки короткий id). Проверяются только связи **одного типа** внутри проекта и только у типов с направлением: у «relates to» (названия сторон совпадают) циклов нет по определению, признак ни на что не влияет; связь задачи с самой собой отклоняется всегда. Признак у типов по умолчанию: **Blocks — `false`** (циклы запрещены), остальные четыре — `true`; у типа, созданного пользователем, по умолчанию `true` (как было до появления признака), выбрать можно при создании и правке: REST `allowCycles` в `POST`/`PATCH /link-types`, MCP `create_link_type`/`update_link_type` (параметр `allowCycles`), консоль `link-type create|update … --allow-cycles true|false`. Изменение признака не трогает уже созданные связи: запретили циклы у типа, где они уже есть, — их сообщает сверка (см. ниже), а не удаляет. **Как проверяется.** Обход графа вперёд от цели новой связи по связям того же типа (поиск пути «цель → … → источник») по уровням: на уровень один запрос `ITaskStorage.GetLinkTargets` (файлы — таблица `task_links` индекса, индекс по `(project_id, type_id, source_id)`; БД — запрос по первичному ключу связей); обход ограничен `LinkCycles.MaxVisited` (20000 достижимых задач): в графе больше проверка отказывает с понятным сообщением, а не принимает связь вслепую. **Гонка.** Проверка и запись связи выполняются в одной секции записи проекта (`IWriteScope.Exclusive`: файлы — межпроцессная блокировка `.cache/write.lock` со сверкой индекса, БД — транзакция), поэтому две встречные связи «A blocks B» и «B blocks A» из разных процессов или запросов не пройдут обе: одна запишется, вторая увидит её и получит отказ. Очередь по задаче-источнику и повтор записи (`TaskLinkService.Change`) работают внутри секции как раньше; типы с `allowCycles: true` и симметричные в секцию не входят (проверять нечего). **Существующие циклы** (две ветки git независимо добавили «A blocks B» и «B blocks A» — файлы разные, конфликта нет) читаются и показываются как обычно; `tasker sync`, `tasker cleanup` (в том числе `--check` и `--dry-run`) и демон **сообщают** о них (`LinkCycles.Find` по `ITaskStorage.GetLinkEdges`: компоненты сильной связности, по одному кратчайшему циклу на компоненту, не больше 50 на проект): `Link cycle: TSK-1 → TSK-2 → TSK-1 (link type Blocks): remove one of the links with 'tasker task unlink' …`; `cleanup --check` в этом случае завершается кодом 2; в JSON сверки и `cleanup` — `linkCycles: [{typeId, linkType|typeName, path, taskIds}]`. **`cleanup` сам связи цикла не удаляет** — какую связь снять, решает человек: `tasker task unlink TSK-2 blocks TSK-1`.
- **Иерархия: эпик и дочерние задачи.** Признак типа связи **`hierarchical`** (рядом с `allowCycles`; `link-type create/update --hierarchical true|false`, REST `hierarchical` в `POST/PATCH /link-types`, MCP `create_link_type`/`update_link_type`) делает связь «родитель включает потомка»: источник связи — родитель, цель — потомок. Стандартный тип **Parent/Child** (`includes` / `is part of`, иерархический, без циклов) есть у каждого проекта; в проекте с уже сохранёнными типами (файлы или БД) он появляется без миграции данных: пока в проекте нет иерархического типа и типа с этим названием, чтение показывает его «виртуально» (версия `default`), а запись типов или связей сохраняет (`LinkTypeService.EnsureDefaults`); удалить Parent/Child насовсем можно, оставив другой иерархический тип. У иерархического типа циклы запрещены всегда (`allowCycles: true` вместе с `hierarchical: true` — `400`), названия сторон должны различаться, а проверка цикла при добавлении связи идёт по связям **всех** иерархических типов проекта (`LinkCycles.FindPath` с набором типов). Эпик — не тип задачи, а любая задача с исходящими иерархическими связями; у задачи может быть **несколько родителей** (граф без циклов).
- **Список задач деревом** (`TaskService.ListTree`, `tasker task list`). По умолчанию дочерние задачи идут сразу под родителем с отступом (четыре пробела на уровень в первой колонке таблицы, выравнивание и обрезка по ширине учитывают отступ); `--flat` — плоский список как раньше. Правила: фильтры (тип, статус, серия, поля) действуют на каждую задачу отдельно — ребёнок, подошедший под фильтр, при неподходящем эпике идёт на верхнем уровне, при нескольких родителях — под каждым подошедшим и на верхнем уровне только если не подошёл ни один; задача с несколькими родителями показывается под каждым вместе с поддеревом, повторные строки помечены `(+)` после ссылки (`TaskTreeItem.Repeated`); глубина показа — `TaskHierarchy.MaxDepth` = 10 уровней, повторы после `TaskHierarchy.MaxRows` = 5000 строк страницы остаются строкой без потомков; задачи, замкнутые в цикл родителей (после слияния веток), берутся на верхний уровень, чтобы не пропасть. `Found N` считает **уникальные задачи**; `--offset/--limit` (и `Page` в `ListTree`) считают задачи **верхнего уровня** (без родителя в результате), поддеревья показываются целиком и не разрываются между страницами: `Found 106, shown top-level 1-20 of 57 (use --offset/--limit)` (нет вложенности — прежнее `Found 106, shown 1-20 (use --offset/--limit)`), `TaskTreeList.TopLevelCount` — число задач верхнего уровня. Порядок `--sort` применяется и к верхнему уровню, и к дочерним внутри родителя. Загрузка без чтения всех задач в память: `ITaskStorage.GetIds` (id найденных в порядке списка, один запрос), связи иерархических типов (`GetLinkEdges`, только id), затем `TaskFilter.Ids` — только задачи показанных страниц; нет иерархических связей — обычная страница `GetRange`. `board show`/`board tasks` дерева не строят (колонки по статусам).
- **Иерархия в `--json`, REST и MCP.** Список остаётся плоским (клиенты не ломаются); в каждой записи списка (`task list --json`, `GET /tasks`, MCP `list_tasks`/`find_tasks_by_reference`, задачи колонок доски) добавлены `parentIds` (id родителей по иерархическим связям) и `childCount` (число дочерних; больше 0 — эпик). REST `GET /tasks?flat=false` отдаёт строки деревом: те же записи с `depth` и `repeated`, ответ с `topLevelCount`, `offset`/`limit` по верхнему уровню, `totalCount` — уникальные задачи. Без `flat` REST плоский.
- **Короткая запись.** `tasker task create "…" --type Task --parent TSK-5` (можно несколько родителей), `tasker task update TSK-7 --add-parent TSK-5 --remove-parent TSK-3` — те же связи, что `task link TSK-5 includes TSK-7`; иерархический тип берётся единственный в проекте или из `--parent-type`.
- **Хранение.** Исходящие связи — список `links: [{typeId, taskId}]` в файле задачи-источника (как номера серий; пустого списка в файле нет), в БД — таблица `task_links`; типы — `link-types/<id>.yaml` (поля `allowCycles` и `hierarchical`, в файлах формата 8 и старше `hierarchical` нет — тип обычный; `allowCycles`; в файлах формата 6 и старше его нет — тогда у «Blocks» циклы запрещены, у остальных разрешены; формат файлов теперь 8, старый Tasker файлы формата 8 не читает) и таблица `link_types` (столбец `AllowCycles`; в уже созданной БД без этого столбца он добавляется при открытии, у «Blocks» — `false`). Обратная сторона вычисляется (в индексе файлового режима — таблица `task_links`, в БД — индекс по цели). **Миграций БД, кроме добавления этого столбца, нет: существующие БД нужно пересоздать; индекс папки пересоберётся сам.** Создание и удаление связи — изменение задачи-источника (меняются её версия и время, на неё действует блокировка на время правки); у цели ничего не меняется, поэтому блокировка цели на связь не влияет и правки двух задач не конфликтуют.
- **Версия необязательна.** Добавление и удаление связей коммутативны (две добавленные разными людьми связи нужны обе), поэтому `version` задачи можно не указывать — операция берёт актуальную задачу и при гонке повторяется. Указана и устарела — `409 modified`, как везде.
- **Удаление.** Тип, по которому есть связи, удалить нельзя (`409 in_use`, «links of N task(s)»). Удаляя задачу, Tasker убирает связи, которые на неё указывали. Связи, у которых нет типа или задачи (удалены в другой ветке), при показе пропускаются, а убирает их `tasker cleanup` (см. [«Серии задач»](Серии-задач)); о них сообщают `tasker sync` и демон.
- **Связи в самой задаче.** Одна задача (`GET /tasks/{id}`, ответы `POST`/`PATCH /tasks`, MCP `get_task`/`create_task`/`update_task`, `tasker task get --json`) отвечает полями `linkViews` — связи **с обеих сторон** в том же виде, что у `GET /tasks/{id}/links` и `get_task_links` (`direction: "outward"|"inward"`, `name` со стороны этой задачи, другая задача с `title` и `statusId`) — и `linkCount` (всего действительных связей; в `linkViews` не больше 100, остальные — через `GET /tasks/{id}/links`). Поле `links` остаётся сырым хранимым списком исходящих связей (`typeId`, `targetId`): входящих в нём нет, они вычисляются при чтении (индекс файлового хранилища / запрос к БД) и только внутри проекта; связи на удалённую задачу или тип пропускаются, симметричные показываются один раз. В списках (`list_tasks`, `GET /tasks`, доски) `linkViews` нет — входящие там не считаются, чтобы чтение списка не дорожало; только `links`. `tasker task get` печатает тот же набор блоком `links:` (не больше 100 строк, дальше «… and N more»).
- **REST** (внутри проекта): `GET /tasks/{id}/links` — все связи задачи, исходящие и входящие: `[{typeId, typeName, direction: "outward"|"inward", name, task: {id, title, statusId, seriesNumbers}}]`, `name` — название именно с её стороны; `POST /tasks/{id}/links {typeId, targetId, version?}` и `DELETE /tasks/{id}/links?typeId=&targetId=&version=` возвращают изменённую задачу; `/link-types` — `GET`, `POST`, `GET/PATCH/DELETE /link-types/{id}`, а также `…/lock`. Неверный тип или цель (нет в проекте, сама задача) или связь, замыкающая цикл (`Cycle: …`), — `400`; нет задачи — `404`. Событие SSE типа связи — `linkType`.
- **MCP:** `list_link_types`, `create_link_type`, `update_link_type`, `delete_link_type`, `get_task_links`, `link_tasks`, `unlink_tasks`. Связь задаётся фразой: `link_tasks {taskId, link: "blocks", otherTaskId}` — «задача блокирует другую»; `link: "is blocked by"` — «задача заблокирована другой» (хранится как «другая blocks задача»). Фраза — название типа или любое из названий его сторон без учёта регистра. Ответ — все связи `taskId`.
- **Консоль:** `tasker task link TSK-5 blocks TSK-7`, `tasker task link TSK-7 "is blocked by" TSK-5` (то же самое), `tasker task unlink …` (нет такой связи — не ошибка), `tasker task links TSK-5` (строки `blocks  TSK-7  Бэклог  Название`, выровненные по колонкам, `--json` — те же представления, что в REST), связи показывает и `tasker task get`. Типы: `tasker link-type list | create <имя> --outward … [--inward …] [--allow-cycles true|false] | get | update [--allow-cycles true|false] | delete`. Версию задачи указывать не нужно.
