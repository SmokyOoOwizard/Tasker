# Хранилище и формат файлов

Весь остальной код работает только с интерфейсами хранилищ из `Tasker.Core` (`IProjectStorage`, `ITaskStorage`, `ITaskTypeStorage`, `IStatusStorage`, `IStatusSetStorage`, `IBoardStorage`). Создание сущностей идёт через сервисы `Core` (`ProjectService`, `TaskService` и т.д.), которые проверяют входные данные и ссылки. Реализация хранилища выбирается настройками (см. [«Конфигурация»](Конфигурация)): БД (Postgres, файл SQLite или SQLite в памяти) или файлы в `<папка>/.tasker/projects/<projectId>/…`.

Раскладка файлов: у каждого проекта своя папка, внутри — по файлу на сущность:

```
.tasker/.gitignore        — исключает .cache
.tasker/.cache/           — локальный индекс (см. «Индекс файлового режима»)
.tasker/users/<id>.yaml
.tasker/projects/<projectId>/
  project.yaml
  tasks/<заголовок>-<id8>.yaml   task-types/<название>-<id8>.yaml   statuses/<название>-<id8>.yaml   status-sets/<название>-<id8>.yaml   boards/<название>-<id8>.yaml
  series/<название>-<id8>.yaml   link-types/<название>-<id8>.yaml   fields/<название>-<id8>.yaml   enums/<название>-<id8>.yaml
```

Файлы сущностей проекта называются по названию и короткому id (`в-работе-19d3f76d.yaml`, подробнее — [«Имя файла сущности»](Хранилище-и-формат-файлов#имя-файла-сущности)); пользователи (`users/<id>.yaml`) и проект (`projects/<projectId>/project.yaml`) — по-прежнему по Guid.

Модель (все ссылки — по Guid):

```
Задача ──typeId──▶ Тип задачи ──statusSetId──▶ Набор статусов ──statusIds[]──▶ Статусы
   └──────────────────────statusId────────────────────────────────────────────▶ Статус
```

- **Проект** изолирует данные: статусы, наборы, типы, задачи и доски принадлежат одному проекту. Ссылаться на сущности другого проекта нельзя, и по id они из чужого проекта не находятся.
- **Статус**: название, цвет (`#RRGGBB`) и необязательное описание (`description`, см. [«Описание статусов и типов задач»](Хранилище-и-формат-файлов#описание-статусов-и-типов-задач)). Статусов может быть сколько угодно.
- **Набор статусов**: название и список статусов в порядке отображения. Один статус может входить в несколько наборов, в каждом на своём месте.
- **Тип задачи**: название, необязательное описание и набор статусов, из которого задача этого типа берёт свой статус.
- **Доска**: название, наборы статусов и колонки.
  - На доске видны задачи тех типов, чей набор статусов включён в доску. Наборов может быть несколько.
  - **Колонка** содержит список статусов из любых наборов доски и, необязательно, **условия по полям** каталога (`fieldFilters` на входе, `fieldConditions` в модели). Задача попадает в колонку, если её статус есть в списке **и** выполнены все условия: так задачи попадают в колонку сами, когда меняются их поля (подробно — «Поля задач → Колонки доски»).
  - **Правила переноса** (`dropStatuses`, в YAML `onDrop`) задают для каждого набора, какой статус получит задача, перетянутая в колонку. Если правила для набора нет, задачи этого набора в колонку не переносятся.

Проверки при создании и изменении:

- **Задача**: тип из этого проекта. Статус должен входить в набор статусов её типа; если статус не указан при создании, берётся первый статус набора.
- **Тип задачи**: набор статусов из этого проекта. Сменить набор можно, только если статусы всех задач типа есть в новом наборе.
- **Набор статусов**: хотя бы один статус, без повторов, все статусы из этого проекта. Убрать статус из набора нельзя, если:
  - его используют задачи типов с этим набором;
  - на него ссылается правило переноса доски;
  - он остался бы в колонке доски, где его больше не даёт ни один набор.
- **Доска**:
  - наборы статусов из этого проекта;
  - статусы колонок входят в наборы доски; один статус — только в одной колонке, **кроме колонок, условия которых по полям заведомо исключают друг друга** (`Level=High` и `Level!=High`): иначе задача показывалась бы в двух колонках (`400`: «status … is already used by column …, and the columns' field conditions do not exclude each other»);
  - условия колонки — как у `task list --field` и проверяются по каталогу: поле есть, оператор подходит типу (`>`, `>=`, `<`, `<=` — int, float, date), значение разбирается по типу, у enum — значение перечисления; нет поля, значения или неверный оператор — `400` с номером колонки (`Columns[1].FieldFilters: …`);
  - статус из правила переноса входит в указанный набор и в статусы этой же колонки.

Удаление:

- **Статус** нельзя удалить, если он используется в задачах, наборах статусов или колонках досок (в списке статусов или в правилах переноса).
- **Набор статусов** — если его используют типы задач или доски.
- **Тип задачи** — если у него есть задачи.
- **Поле** — если его используют типы, задачи или колонки досок (условия по полю); с условием колонки нельзя и сменить тип, перечисление и множественность поля (переименование можно).
- **Значение перечисления** — если оно выбрано у задач или входит в условие колонки: нужен явный выбор «убрать» или «переназначить» (см. [«Поля задач»](Поля-задач)).
- **Задачи и доски** удаляются без проверок: на них ничего не ссылается.
- **Проект** удаляется вместе со всем содержимым; в режиме `Files` — вся его папка.

Ответы:

- неверные данные — `400 {"error": "..."}`;
- конфликт с текущими данными — `409 {"error": "...", "code": "..."}`:
  - `in_use` — сущность используется, в `error` перечислены все места;
  - `modified` — сущность уже изменил кто-то другой (см. [«Одновременная правка»](Хранилище-и-формат-файлов#одновременная-правка));
- несуществующий проект или сущность — `404`.

### Описание статусов и типов задач

У статуса и у типа задачи есть необязательное текстовое описание `description`: что значит статус («В работе — задачу взял исполнитель, код пишется») и когда использовать тип («Баг — дефект в уже выпущенном поведении»). Агент, прочитавший `list_statuses` и `list_task_types`, получает правила проекта без README. Описание только у этих двух сущностей; у наборов статусов, досок, колонок, серий, полей, перечислений, типов связей и проектов его нет.

- **Значение.** Свободный текст Unicode с переводами строк, по умолчанию пустая строка (в API поле всегда есть, пустое — «нет описания»). Длина не ограничена — как у описания задачи; пустая строка и строка из одних пробелов равны «нет описания». При правке `null`/не указано — не менять, пустая строка — очистить. Правило одно, `Validate.Description` в ядре (его же использует описание задачи); новая сущность с описанием получает его вызовом при создании и правке.
- **REST.** `description` необязательно в `POST` и `PATCH` `/statuses` и `/task-types` (старые клиенты без него работают) и всегда есть в ответах. В списках работает `?descriptionLength=` как у задач: не задан или `-1` — полный текст (по умолчанию), `0` — без описания, `N` — первые N символов, меньше `-1` — `400`; запись списка тогда имеет `descriptionTruncated` и `descriptionLength` (полная длина). Одна сущность (`GET /statuses/{id}`) всегда с полным описанием.
- **MCP.** `create_status`, `update_status`, `create_task_type`, `update_task_type` принимают `description`; `list_statuses` и `list_task_types` отдают его с параметром `descriptionLength` (по умолчанию 200, как у списков задач; `-1` — полный текст). Усечение общее с задачами: `DescriptionPreview.Cut`, записи списка — `StatusListItem` и `TaskTypeListItem` (`StatusService.List`, `TaskTypeService.List`).
- **Консоль.** `status create/update -d`, `task-type create/update -d` (`-d ""` очищает); `status get` и `task-type get` показывают описание абзацем после полей, в текстовых списках его нет; в `--json` списков оно полное, `--description-length N` усекает, как у задач.
- **Интерфейс.** Поле «Описание» в формах статуса и типа задачи (`settings/statuses`, `settings/task-types`); под названием в списке — первые строки описания, полный текст и на цветной метке статуса — в подсказке при наведении.
- **Хранение.** Файлы: ключ `description` в `statuses/<…>.yaml` и `task-types/<…>.yaml`, только когда описание не пусто; формат файлов 8 (шаг 7 → 8 только меняет версию: старые файлы читаются без описания, данные переносить не нужно). БД: столбец `Description` в `Statuses` и `TaskTypes`, NULL — описания нет; **миграций БД нет: существующую БД нужно пересоздать** (`EnsureCreated` новых столбцов не добавляет).

### Одновременная правка

Используется оптимистическая блокировка. У каждой сущности есть поле `version`, оно меняется при каждой записи.

- `PATCH` передаёт в теле версию, которую видел клиент (`"version": "..."`), `DELETE` — в `?version=...`. Перенос задачи в колонку передаёт версию задачи.
- Если с тех пор запись изменил кто-то другой, операция отклоняется с `409 code: modified`. Клиент перечитывает сущность и повторяет изменение уже поверх новой версии.
- Без версии `PATCH` и `DELETE` отклоняются с `400`.
- Проверка и запись атомарны. В БД версия — счётчик, запись идёт через `UPDATE … WHERE Version = @expected`. В файлах версия — хэш содержимого, проверка и запись идут под блокировкой файла. Из нескольких одновременных изменений одной версии проходит ровно одно.
- В файлах версия не хранится отдельным полем, поэтому git-слияния не конфликтуют из-за неё. Правка файла руками или через git тоже меняет версию.
- Формат версии у хранилищ разный: клиент не разбирает её, а только передаёт обратно.

#### Блокировка на время правки

Версия сообщает о конфликте при сохранении. Чтобы узнать заранее, что запись правит другой («редактирует Иван»), редактор берёт блокировку: пока её держит другой, изменить и удалить запись нельзя ни через интерфейс, ни через MCP, ни через консоль.

- Блокировка есть у проектов, задач, типов задач, статусов, наборов статусов, досок и серий. Она действует **2 минуты**: редактор повторяет взятие, пока открыта форма («пульс»), а забытая блокировка истекает сама.
- **Массовые правки задач** — каскады (убрать серию, `tasker cleanup`, убрать поле из типа с выбором «убрать значения», убрать или переназначить значение перечисления) — подчиняются одному правилу (`TaskRewrites.ModifyAll`): задача, которую правка **действительно меняет** и которую держит другой, ждёт. Сначала ждут блокировки **всех** затрагиваемых задач, и только потом пишут; не снялись за `EditLockService.CascadeWait` (**30 секунд**, опрос каждые 200 мс; в тестах задаётся `EditLockService.CascadeTimeout`) — обычная ошибка `locked` («Task 'A', Task 'B' is being edited by Иван»), ничего не записано. Ждут снаружи атомарной секции записи (в БД это транзакция, а в ней держатель не смог бы снять блокировку); внутри секции перед каждой задачей блокировка проверяется ещё раз без ожидания, и новая чужая блокировка даёт тот же отказ. Заблокированная, но не затрагиваемая задача не мешает; версия задачи остаётся последней защитой. Не охвачено: чистка связей при удалении задачи (`RemoveInbound`) и симметричная связь — они правят задачи-источники мимо этого правила.
- Свободную запись можно изменить и без блокировки — одиночным вызовам (агент, команда) она не нужна. Блокировка для серии связанных правок, которые никто не должен перебить.
- REST, внутри проекта: `POST …/lock` — взять или продлить (`200` с `{entity, id, holder, mine, acquiredAt, expiresAt}`), `GET …/lock` — показать (`404`, если не заблокировано), `DELETE …/lock` — снять свою (`204`, даже если снимать нечего). Пути: `/projects/{id}/lock`, `/tasks/{id}/lock`, `/task-types/…`, `/link-types/…`, `/fields/…`, `/enums/…`, `/statuses/…`, `/status-sets/…`, `/boards/…`, `/series/…`.
- `GET /projects/{id}/locks` — все действующие блокировки проекта (страница `{totalCount, offset, limit, data}`, старые первыми; у каждой `entity`, `id`, `holder`, `mine`, `acquiredAt`, `expiresAt`). Блокировка запоминает проект сущности, поэтому чужие проекты в список не попадают.
- Интерфейс: при открытии формы правки (переименование статуса, правка набора статусов и типа задач, название проекта) берётся блокировка, пока форма открыта — продлевается каждые 40 секунд, при закрытии формы и уходе с экрана снимается. У записей, которые правит другой, в списках плашка «Правит Иван», а изменение и удаление недоступны. Десктоп обновляет плашки по событию `lock`, сервер — опросом раз в 15 секунд.
- Занято другим — `409 code: locked` с `heldBy: {name, expiresAt}`; так отвечают и `POST …/lock`, и `PATCH` и `DELETE` самой записи.
- Держатель: пользователь (на сервере — по JWT), агент (MCP) или «локальный человек». Интерфейс десктопа и консоль — разные держатели: блокировка интерфейса останавливает команды `tasker`, и наоборот. Имя «локального человека» — `tasker whoami [имя]` (по умолчанию — имя пользователя ОС); в блокировках консоли оно с припиской `(console)`.
- MCP: `lock_entity`, `unlock_entity`, `get_lock` (`entity` — `project`, `task`, `taskType`, `status`, `statusSet`, `board`, `series`); ошибка — `[locked]`. CLI: `tasker lock acquire|release|show <сущность> <id или имя>`; ошибка — `Locked: …`.
- Вкладки получают событие SSE `{"entity": "lock", "id": …}`, когда блокировку взяли или сняли (продление события не даёт).
- Хранение: в файлах — `.tasker/.cache/edit-locks` (в git не попадает, между машинами не передаётся — там остаётся проверка версии), в БД — таблица `edit_locks` (существующую БД придётся пересоздать, пока нет миграций).

### Версия формата файлов

Каждый файл сущности в `.tasker` (проект, пользователь, статус, набор, тип задачи, доска, серия, задача, тип связи, поле, перечисление) начинается со строки `formatVersion: 9` — версии **формата файла**. Это не версия программы и не версия сущности (`version`, хэш файла): число растёт, только когда меняется формат файлов, поэтому по нему видно, как файл читать, и старые файлы можно перенести на новый формат.

- **Версии.** `0` — файл без поля (записан до введения версии). `1` — то же, плюс `formatVersion: 1`. `2` — файлы задач называются по заголовку (см. «Имя файла задачи»); содержимое файлов то же. Старый Tasker (до версии 2) имён по заголовку не узнаёт, поэтому версия поднята: он увидит такие проекты как файлы «более нового формата» и попросит обновиться, а не потеряет задачи молча. `3` — появились папки `fields/` и `enums/` (см. [«Поля задач»](Поля-задач)); содержимое прежних файлов то же (шаг 2 → 3 только меняет версию). Старый Tasker этих папок не знает и молча их проигнорировал бы, поэтому версия поднята. `4` — у типа задачи список полей (`fields` в `task-types/`), у задачи — значения полей и собственные поля (`fields` в `tasks/`); прежние файлы остаются как есть (полей у них нет, шаг 3 → 4 только меняет версию). Старый Tasker не знает этих списков и стёр бы их при первой же записи, поэтому версия поднята: файлы, которые записал новый Tasker, старый покажет как «более нового формата» и попросит обновиться. `5` — файлы остальных сущностей проекта (серии, типы задач, статусы, наборы статусов, доски, типы связей, поля, перечисления) называются, как и задачи, по названию и короткому id (см. [«Имя файла сущности»](Хранилище-и-формат-файлов#имя-файла-сущности)); содержимое файлов то же (шаг 4 → 5 только меняет версию). Старый Tasker имён по названию в этих папках не узнаёт и молча проигнорировал бы эти сущности (статусы, типы и серии пропали бы из списков), поэтому версия поднята: `tasker migrate` записывает её и в `project.yaml`, который старый Tasker читает всегда, — он покажет проект как «более нового формата» и попросит обновиться. Поэтому после обновления Tasker в репозитории с проектом выполните `tasker migrate` один раз и закоммитьте результат: пока он не выполнен, `project.yaml` остаётся прежней версии, и старый Tasker, оставшийся у кого-то в команде, файлов с новыми именами не заметит. `6` — у колонок досок появились условия по полям каталога (`fieldFilters` в `boards/`, см. «Поля задач → Колонки доски»); у прежних колонок их нет, файлы остаются как есть (шаг 5 → 6 только меняет версию). Старый Tasker пропустил бы этот список как неизвестный и стёр бы его при первой же правке доски — колонка стала бы показывать лишние задачи, поэтому версия поднята: такие файлы он покажет как «более нового формата» и попросит обновиться. `7` — у типов связей появился признак `allowCycles` (допускает ли тип циклы, см. «Связи между задачами → Циклы»; `link-types/`); в прежних файлах его нет и при чтении он выводится по умолчанию («Blocks» циклы запрещает, остальные допускают), шаг 6 → 7 только меняет версию. Старый Tasker не знает признака и стёр бы его при первой же правке типа (цикл блокировок снова стал бы возможен), поэтому версия поднята: такие файлы он покажет как «более нового формата» и попросит обновиться. `8` — у статусов и типов задач появилось необязательное описание (`description` в `statuses/` и `task-types/`, см. [«Описание статусов и типов задач»](Хранилище-и-формат-файлов#описание-статусов-и-типов-задач)); в прежних файлах его нет и описание пустое, шаг 7 → 8 только меняет версию. Старый Tasker не знает ключа и стёр бы его при первой же правке статуса или типа, поэтому версия поднята: такие файлы он покажет как «более нового формата» и попросит обновиться. `9` — текущая: у типов связей появился признак `hierarchical` (иерархический тип «Parent/Child», см. [«Связи между задачами»](Связи-и-иерархия)); в прежних файлах его нет и тип обычный, шаг 8 → 9 только меняет версию. Старый Tasker не знает ключа и стёр бы его при первой же правке типа (иерархия пропала бы из `task list`), поэтому версия поднята: такие файлы он покажет как «более нового формата» и попросит обновиться.
- **Запись.** Tasker всегда пишет текущую версию первой строкой. Файл, который он не менял, остаётся как был — поэтому в репозитории могут лежать файлы разных версий, пока их не перенесёт `tasker migrate`.
- **Чтение.** Старые версии читаются всегда: текст приводится к текущему формату в памяти (шаги в `FormatVersions.Steps`), файл на диске чтение не меняет. Версия сущности — хэш настоящих байтов файла.
- **Более новый формат.** Файл с версией выше поддерживаемой не читается и не перезаписывается — его нельзя испортить старой программой. В списках его нет, в списке проблем рабочей области (`/api/workspace/problems`, `tasker sync`) — «format version N is newer than this Tasker supports: update Tasker», прямое чтение и запись — `409 unsupported_format` (в консоли — `Unsupported format: …`).
- **`tasker migrate`** переписывает на диске файлы старых версий в текущую: меняется только версия (и то, что меняет шаг миграции), остальной текст файла — байт в байт. Заодно переименовывает файлы сущностей проекта по названию (у задач — по заголовку, см. [«Имя файла сущности»](Хранилище-и-формат-файлов#имя-файла-сущности)): старые, названные Guid, и те, чьё имя «ушло» от названия после правки мимо Tasker. Файл в папке сущностей, у которого id внутри не согласуется с именем (или который не читается), не трогается совсем (в отчёте — как нечитаемый): это проверяется для каждого файла до любых его изменений; не затирается и существующий файл с нужным именем. `project.yaml` и пользователи не переименовываются, но версию формата получают. Каждый файл — под блокировкой записи, индекс обновляется сразу. `--dry-run` показывает, какие файлы были бы переписаны и переименованы (первые десять), `--check` ничего не пишет и завершается кодом 2, если есть файлы не текущей версии, с неверным именем, более новые или нечитаемые (для скриптов и CI), `--json` — отчёт (`scanned`, `upToDate`, `migrated`, `renamed`, `newer`, `unreadable`). Файлы более нового формата и файлы с конфликтом слияния не трогаются, а попадают в отчёт; тогда код выхода 1. У базы данных файлов нет: команда сообщает, что мигрировать нечего.
- **Как менять формат.** Поднять `FormatVersions.Current`, добавить шаг в `FormatVersions.Steps` (старый текст → новый, с выставленной версией) и тест на него: чтение и `tasker migrate` подхватят его сами.

### Имя файла сущности

Файл любой сущности проекта — задачи, серии, типа задачи, статуса, набора статусов, доски, типа связи, поля, перечисления — называется по её названию (у задачи — заголовку): `исправить-вход-3f2a9c1e.yaml`, `в-работе-19d3f76d.yaml` — название (буквы и цифры любого алфавита в нижнем регистре, остальное — один дефис, не длиннее 60 знаков; нет букв и цифр — запасное слово вида сущности: `task`, `type`, `status`, `set`, `board`, `series`, `link`, `field`, `enum`) и **первые 8 знаков id**. Название делает файл узнаваемым в папке и в диффах, суффикс из id — уникальным: две ветки, где создали сущности с одинаковым названием, получают разные файлы и сливаются без конфликта «оба добавили один файл», а одинаковые названия в одной папке — обычное дело (файлы различаются суффиксом). Настоящий id — поле `id` внутри файла; имя лишь подсказывает, где искать, и проверяется при чтении (не совпал суффикс — файл попадает в список проблем). Правила имени и список папок — в одном месте: `EntityFileNames` и `EntityFolders`; все хранилища пишут и ищут файлы одним кодом (`EntityFiles`).

- **Смена названия** переименовывает файл (в репозитории это переименование: файл похож на прежний). Переименование и запись — один шаг под блокировкой записи; под новым именем уже лежит чужой файл — запись отклоняется, файл не затирается.
- **Старые имена** (`<guid>.yaml`; у задач — формат до версии 2, у остальных сущностей — до версии 5) читаются наравне с новыми; файл получает новое имя при первой записи, остальные переименует `tasker migrate`.
- **Поиск по id.** Сначала индекс (быстро: в нём id из содержимого файла, а не из имени), затем поиск по имени — старому и новому, — поэтому файл, принесённый `git pull` или другим процессом и ещё неизвестный индексу, тоже находится. Для людей и скриптов — `ProjectDirectory.FindTaskFile(id)`. События для вкладок (`/api/events`) тоже несут id из содержимого, а не из имени файла.
- **Не переименовываются** `users/<id>.yaml` (пользователь — общий для проектов, имя меняется редко и уникально) и `projects/<projectId>/project.yaml` (папка проекта называется по Guid, сам файл — всегда одинаково).
- **После `git pull`, `merge` и `rebase`** переименование приходит как удаление одного файла и появление другого: `tasker sync` (в том числе из git-хуков) перечитывает оба и находит сущность по id внутри, так что ссылки (по id) переименование переживают. `tasker cleanup` с именами файлов не работает вовсе.

### Индекс файлового режима

Файлы — источник правды, а для списков есть локальный индекс, как `Library` в Unity: `.tasker/.cache/index.db` (SQLite).

- **В git не попадает.** При открытии папки в `.tasker/.gitignore` дописывается правило `/.cache/`, если его ещё нет. Индекс можно удалить в любой момент — он пересоберётся из файлов. Повреждённый индекс или индекс старой схемы пересобирается сам.
- **Что идёт через индекс:** все списки, страницы, фильтры и подсчёты, в том числе проверки «статус используется задачами». Одна сущность по id и все записи идут напрямую в файлы, а версия при записи сверяется с файлом, поэтому отстающий индекс не может привести к потере данных.
- **Когда обновляется:**
  - при запуске — сверка со всеми файлами; перечитываются только новые и изменённые (по размеру и времени изменения), записи об удалённых удаляются. Так видны изменения, сделанные при закрытом приложении: `git pull`, `checkout`, правки руками;
  - во время работы — `FileSystemWatcher`. События копятся и разбираются пачкой, когда папка затихнет на 300 мс (но не реже раза в 2 с): `checkout` на сотни файлов — одна транзакция. Если события потерялись или путей слишком много — полная сверка;
  - после своей записи — сразу, поэтому свой список видит изменение без задержки;
  - на десктопе — при активации окна: страховка на случай пропущенных событий.
- **Какие файлы учитываются:** только файлы раскладки (`users/<id>.yaml`, `projects/<id>/project.yaml`, `projects/<id>/<папка>/<название>-<id8>.yaml` и, в старом формате, `<id>.yaml`). Остальное в `.tasker` пропускается, `.gitignore` не разбирается.
- **Файлы, которые не удалось прочитать** — маркеры конфликта слияния git (`<<<<<<<`, `=======`, `>>>>>>>`), ошибка YAML, пустой файл, id внутри не совпадает с именем файла — исключаются из списков и попадают в список проблем: `GET /api/workspace/problems`, в MCP — `list_workspace_problems`. После исправления файла сущность возвращается в списки сама.
- **Несколько процессов на папку.** С одной папкой одновременно работают десктоп, демон MCP и команды `tasker`: у них общий индекс и файлы. Блокировки короткие — на время самой операции, а не пока папка открыта (`FileLock`: файл, открытый эксклюзивно, на Unix — `flock`): обращение к индексу (чтение, запись, сверка) идёт под `.cache/index.lock`, а «сравнить версию и записать файл» — под `.cache/write.lock`. Занято — ждём освобождения (до 30 с). Пока никто не работает, папка ничем не занята; упавший процесс блокировку не оставляет. Соединения индекса не держатся в пуле, поэтому, если индекс пересоздают, другие процессы этого не замечают. Изменение файла другим процессом вкладки получают по событиям файловой системы (индекс уже мог быть обновлён, но событие всё равно уходит). Все вкладки и окна одного процесса с папкой работают через один индекс и один синхронизатор.

В БД:

- **Удаление проекта** каскадом удаляет всё, что в нём.
- **Ссылки между сущностями** — внешние ключи: статус, набор или тип, на который что-то ссылается, удалить нельзя.
- **Части одной сущности** (колонки доски, статусы набора) удаляются вместе с ней.

### Windows: имена, длинные пути, переводы строк (TSK-116)

Файлы `.tasker` одинаковы на macOS, Linux и Windows; всё, что зависит от системы, собрано в `Tasker.Core/IO` (`WindowsNames`, `PathRules`, `LineEndings`, `AtomicFile`, `FileLock`) и в `CanonicalPath`. Правила Windows — чистые функции, их тесты идут на всех системах; тесты, которым нужна настоящая Windows, помечены `[PlatformFact(TestPlatform.Windows)]` и на других системах явно пропускаются (`skipped`).

- **Имена файлов.** Название в имени файла состоит только из букв, цифр и дефисов (см. [«Имя файла сущности»](Хранилище-и-формат-файлов#имя-файла-сущности)), поэтому запрещённые в Windows знаки (`< > : " / \ | ? *`, управляющие), завершающие точка и пробел в имя не попадают. Зарезервированные имена (`CON`, `PRN`, `AUX`, `NUL`, `COM1`–`COM9`, `LPT1`–`LPT9`, в том числе с расширением: `con.yaml`) тоже не получаются: после названия всегда идёт `-<id8>`, и имя `con-3f2a9c1e.yaml` устройством не является. Регистр не важен: «Баг» и «баг» дают одно название, а файлы различает суффикс id. Название приводится к форме Unicode NFC (файловая система может хранить NFD — такое имя читается как текущее). Длина названия — до 60 знаков, одинаково на всех системах (она не зависит от места папки: иначе один файл назывался бы по-разному на разных машинах).
- **Длинные пути.** Самый длинный файл — `.tasker\projects\<guid>\status-sets\<название 60>-<id8>.yaml` (с временным `.tmp`) — это 144 знака внутри рабочей папки. Сам Tasker (.NET) открывает и пути длиннее 260 знаков, но `git` без `core.longpaths`, проводник и часть программ — нет. Поэтому, если путь рабочей папки длиннее 114 знаков (`PathBudget`), при открытии на Windows в журнал пишется предупреждение. Совет: держать папку ближе к корню диска и включить `git config --global core.longpaths true` (и, при желании, длинные пути Win32: `LongPathsEnabled=1` в реестре или групповая политика).
- **Переводы строк.** Tasker всегда пишет файлы с LF и без BOM (`WithNewLine("\n")`), а читает и с CRLF, и с BOM. Версия сущности — хэш файла, посчитанный по тексту с LF и без BOM: после `checkout` на Windows с `core.autocrlf=true` (файлы приходят с CRLF) версии те же, что на Linux и macOS, и «чужая правка» не мерещится. Строка `formatVersion` при миграции заменяется с сохранением окончания строки. Чтобы git вообще не подменял окончания, в репозитории с `.tasker` добавьте в `.gitattributes` (в этом репозитории он уже есть):

  ```
  /.tasker/** text eol=lf
  ```

  Для уже существующего репозитория это безопасно, если файлы в индексе git с LF (`git ls-files --eol .tasker` показывает `i/lf`). Хуки `tasker hooks install` пишет с LF.
- **Блокировки и атомарная запись.** `FileLock` — файл, открытый с `FileShare.None`: на Windows блокировка обязательная, на Unix — `flock`; процесс упал — система снимает её сама (в файл блокировки ничего не пишут). Запись — во временный `<файл>.tmp` и переименование поверх; на Windows файл, открытый чужим процессом без `FileShare.Delete`, нельзя заменить или удалить, поэтому Tasker читает с `FileShare.ReadWrite | FileShare.Delete`, а замену, переименование и удаление при кратковременном отказе (антивирус, индексатор поиска) повторяет до ~1,5 с (`AtomicFile`). Ключи блокировок на Windows сравниваются без учёта регистра. Соединения SQLite-индекса не держатся в пуле, поэтому `.cache` (индекс и его `-wal`/`-shm`) можно удалить, когда ни один процесс не работает. Остаток `.yaml.tmp` после обрыва безвреден: он в `.gitignore`, индекс его не учитывает, следующая запись его перезапишет.
- **Наблюдатель файлов.** `FileSystemWatcher` на Windows работает с буфером 64 КБ (по умолчанию 8 КБ — его переполняет `checkout` на сотни файлов); потеря событий — полная сверка. Путь события сравнивается с `.cache` без учёта регистра.
- **Канонический путь области** (`mcp workspace add`, вкладки): буква диска всегда заглавная (`c:\work` и `C:\work` — одна область), префикс `\\?\` снимается, регистр имён берётся с диска, короткие имена 8.3 (`RUNNER~1`) раскрываются, junction и символические ссылки раскрываются. UNC-путь (`\\server\share\папка`) остаётся UNC. Пробелы и кириллица в имени папки допустимы; в адресе `workspace` берётся имя папки (знаки, кроме букв, цифр, `-`, `_`, `.`, заменяются дефисом).
- **Каталоги по умолчанию.** Данные Tasker (`settings.json`, журналы, `mcp\daemon.lock`) — `%LOCALAPPDATA%\Tasker`: это данные конкретной машины (блокировки, порты, журналы), поэтому не `%APPDATA%` (он копируется между машинами при перемещаемом профиле). Переопределяется `TASKER_HOME`.
- **Хуки git.** Хук — скрипт `sh`, его запускает Git for Windows; пути в нём записываются с `/` (`C:/Users/me/.local/bin/tasker.exe`), права `chmod` ставятся только на Unix.
