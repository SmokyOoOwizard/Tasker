# Конфигурация

Настройки — классы-наследники `AConfigs` в папке `<Проект>/Configs/Tasker/`. Значения берутся:

1. **из переменных окружения** — полный ключ: `TASKER_DB_CONFIGS_SQLITE_FILE=tasker.db`;
2. **из аргументов командной строки** — алиас `--sqlite=tasker.db` (или `--sqlite tasker.db`) либо полный ключ `--TASKER_DB_CONFIGS_SQLITE_FILE=tasker.db`, без учёта регистра.

Аргументы важнее переменных окружения. Не задано нигде — берётся значение по умолчанию из класса. Файлы (`appsettings.json`) для настроек Tasker не используются.

**Опечатки не проходят молча.** Что парсер не узнал, он пропускает, поэтому `--sqllite=tasker.db` раньше просто не действовало (и сервер тихо работал на SQLite в памяти). Теперь при старте хост (сервер, десктоп, демон MCP) пишет предупреждение в журнал, а консольная утилита — в stderr (stdout, в том числе `--json`, остаётся чистым), и подсказывает похожее имя:

- `Unknown argument --sqllite is ignored. Did you mean --sqlite?` — аргумент, похожий на известный алиас или ключ (расстояние Дамерау — Левенштейна не больше трети длины, до трёх правок; без учёта регистра), а также любой несуществующий `--TASKER_…`. Остальные незнакомые аргументы не трогаем: их ждёт ASP.NET Core (`--urls`, `--environment`, `--Logging:LogLevel:Default=…`) или другая часть хоста.
- `Environment variable TASKER_DB_CONFIGS_SQLITE_FIL is not a Tasker setting and is ignored. Did you mean …?` — любая переменная `TASKER_*`, которой нет среди настроек и известных переменных (`TASKER_HOME`, `TASKER_PROJECT`, `TASKER_LANG`, `TASKER_SERVICE_DIR`, `TASKER_SERVICE_LABEL`, `TASKER_FRONTEND_DEV_URL`; список — `ConfigDiagnostics.OtherVariables`). Новая переменная `TASKER_…` в коде должна попасть в этот список: тест сверяет исходники и падает на незарегистрированной.

Второй запуск десктопа (он передаёт аргументы первому и завершается) тоже пишет предупреждения в консоль. Консольная утилита сама ругается на незнакомые ключи (System.CommandLine), поэтому она проверяет только переменные окружения.

Ключ строится из имени класса и свойства: `Tasker.Storage.Db.Configs.Tasker.DbConfigs.SqliteFile` → `TASKER_DB_CONFIGS_SQLITE_FILE`.

| Переменная окружения | Аргумент | По умолчанию |
|---|---|---|
| `TASKER_DB_CONFIGS_POSTGRES_CONNECTION_STRING` | `--postgres`, `--db` | — |
| `TASKER_DB_CONFIGS_SQLITE_FILE` | `--sqlite` | — |
| `TASKER_FILES_CONFIGS_PATH` | `--files` | — (только десктоп) |
| `TASKER_AUTH_CONFIGS_SIGNING_KEY` | `--jwtkey` | временный ключ (см. ниже) |
| `TASKER_AUTH_CONFIGS_ACCESS_TOKEN_LIFETIME` | — | `00:15:00` |
| `TASKER_AUTH_CONFIGS_REFRESH_TOKEN_LIFETIME` | — | `30.00:00:00` |
| `TASKER_MCP_CONFIGS_PORT` | `--mcpport` | порт из глобальных настроек (`5719`); только десктоп |
| `TASKER_HOME` | — | каталог данных Tasker: `~/Library/Application Support/Tasker`, `%LOCALAPPDATA%\Tasker` |

Выбор хранилища на сервере:

- **задан Postgres** → Postgres;
- **задан файл SQLite** → SQLite в этом файле;
- **не задано ничего** → SQLite в памяти, данные пропадают при перезапуске (удобно для разработки);
- **задана папка** (`--files`) → ошибка при старте: файлы — только на десктопе.

Несовместимые настройки (папка и БД, Postgres и SQLite одновременно) — ошибка при старте, а не молчаливый выбор одного из вариантов. Выбранное хранилище пишется в лог при запуске.

На десктопе хранилище своё у каждой вкладки (см. [«Десктоп: вкладки и рабочие области»](MCP-и-агенты#десктоп-вкладки-и-рабочие-области)): `--files=<папка>` и `--sqlite=<файл>` открывают вкладки при запуске (можно оба сразу), Postgres — ошибка при старте.

Фронт обращается к API относительно своей рабочей области (`frontend/src/api.ts`): на сервере — `/api/…`, на десктопе — `/w/{папка}/api/…`.
