# Параллельная работа

С одной рабочей областью и проектом одновременно работают многие клиенты: консоль (каждый вызов — свой процесс), агенты MCP через демон, десктоп (REST). Стенд `tools/Tasker.Stress` (TSK-96) проверяет это на десяти и более клиентах и сверяет инварианты.

### Что гарантируется

- **Номера серии** выдаются под блокировкой записи: десять клиентов × любое число задач в одну серию дают уникальные номера без пропусков.
- **Нет потерянных обновлений.** Запись с версией проходит ровно у одного из одновременных клиентов, остальные получают `modified` и повторяют. Правка без версии (консоль) не откатывает чужие поля: заголовок и описание, изменённые разными клиентами, не затирают друг друга. Версия файла = хэш его содержимого.
- **Правки разных задач не мешают друг другу:** конфликтов и блокировок без нужды нет (запись коротко сериализуется общей `write.lock`, но это миллисекунды).
- **Блокировка на время правки** между разными держателями (агент A, агент B, консоль): чужие правка, удаление и связь отклоняются `Locked`, владелец правит и продлевает, снятие мгновенно открывает запись, из гонки за блокировку выходит ровно один победитель, забытая блокировка истекает через 2 минуты.
- **Массовые правки** (удаление серии, `cleanup`, каскады полей и значений перечисления) ждут снятия блокировки затрагиваемой задачи (до 30 с, потом `Locked` и ничего не изменено), не блокируют друг друга взаимно и не теряют параллельные правки тех же задач.
- **Связи.** Связь хранится в задаче-источнике; десять клиентов, вешающих связи на одну задачу без версии, не теряют ни одной (в процессе — очередь по задаче, между процессами — повтор с паузой); одна и та же связь с двух сторон («A blocks B» и «B is blocked by A») существует один раз; обратная сторона всегда согласована.
- **Удаление** задачи или проекта во время правки не воскрешает их: поздняя запись получает отказ, папка удалённого проекта не создаётся заново (локальная метка в `.cache/deleted-projects`; проект, вернувшийся из истории, метку перекрывает).
- **kill -9** (консоль и демон посреди потока записей): файлы пишутся через временный `*.yaml.tmp` и переименование, половинчатых файлов нет; недописанный `.tmp` остаётся рядом (в git не попадает, индекс его не видит, следующая запись перезаписывает); индекс и блокировки восстанавливаются сами (блокировки файловые, `flock` снимает ОС; блокировки правки истекают).
- **Индекс** (в том числе живой индекс демона) после затишья равен файлам; `tasker sync` и `cleanup --check` чистые.
- **События SSE:** о каждой созданной задаче вкладка узнаёт событием с её id или общим событием папки/`unknown` (перечитать); поток не обрывается.

### Чего нет

- **Циклы связей** (TSK-97) запрещены у типов с `allowCycles: false` (по умолчанию «Blocks»): сценарий `links` запускает «A blocks B» и «B blocks A» (и треугольник из трёх связей) одновременно из разных клиентов и проверяет, что проходит ровно одна из встречных (у треугольника — две), а вторая получает `Cycle: …`; ни одна пара не оказывается циклом.
- Правка в консоли без `--expected-version` берёт текущую версию в момент вызова: «побеждает последний», защита от потерянного обновления — только у клиента, который передаёт версию (MCP требует её всегда).
- Конфликты версий при правке одной задачи многими клиентами штатны и частые (20 агентов на одну задачу: десятки повторов на успех) — клиент обязан перечитывать и повторять.
- Во время удаления проекта соседние запросы могут получить `[invalid] TypeId: not found…` или необработанное исключение (TSK-99); сразу после перезапуска демона область открывается в фоне — вызов ждёт открытия до 5 с, потом `[unavailable]` (повторить; TSK-100, исправлено).
- Ограничения прогона: Postgres не проверялся (его нет на машине разработки); перенос по доске (`move_task`) есть только в MCP/REST и в стенде заменён сменой статуса; десктоп (REST) и события SSE проверяют тесты `ParallelWorkTests`, а не консольный стенд.

### Как запускать стенд

```bash
dotnet run --project tools/Tasker.Stress -- --clients 10 --ops 5 --client mix --storage files
dotnet run --project tools/Tasker.Stress -- --help
```

Параметры: `--clients` (число агентов), `--ops` (операций на клиента), `--client cli|mcp|mix`, `--storage files|sqlite`, `--scenarios` (`create, edit-same, edit-fields, edit-different, locks, cascade-wait, mass, fields, links, delete-while-edit, delete-project, kill, multiws, scale`), `--scale 1,2,5,10`, `--long` (настоящее истечение блокировки 2 мин и отказ каскада через 30 с), `--keep`/`--dir`, `--json <файл>`. Всё происходит во временной папке: свой `TASKER_HOME`, своя область (папка или файл SQLite), свои агенты и свой демон на свободном порту — настоящий демон (5719) и данные репозитория не затрагиваются. Отчёт: по каждому сценарию «ожидание → факт», таблицы latency (p50/p95/p99, ops/с) по сценариям и вызовам, число успехов, ожидаемых конфликтов (`modified`, `Locked`, не найдено) и неожиданных ошибок; код выхода 1, если нарушен инвариант. В конце каждого сценария проверяются: число задач, уникальность (и сплошность) номеров серии, YAML каждого файла (разбор, `formatVersion`, имя = id), индекс = файлам (в том числе в свежей копии без `.cache` и в живом индексе демона), `sync` и `cleanup --check`, новая запись проходит быстро (нет залипших блокировок), нет действующих блокировок правки, `PRAGMA integrity_check` для SQLite.

Нагрузка: пустой вызов `tasker` стоит ~0,15 с (запуск процесса), десять параллельных консольных клиентов дают p50 около 1 с на запись при загруженной машине (упирается в процессор, а не в блокировки); тот же поток через MCP — единицы и десятки миллисекунд. В обычном наборе тестов идут малые прогоны (`ParallelWorkTests`: 3–4 клиента); большой прогон тестом — `TASKER_STRESS=1 dotnet test --filter ParallelWorkTests`.
