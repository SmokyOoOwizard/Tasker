# Демон MCP

**Демон MCP** — фоновый процесс (отдельная программа `tasker-mcpd`, её запускает `tasker`), который держит MCP-сервер сразу для нескольких рабочих областей: адрес один, как у десктопа, — `http://127.0.0.1:<порт>/mcp` (без токена, только с этой машины, агент — локальный или из `X-Tasker-Agent`; порт — `5719`), а область — аргумент `workspace` вызова (см. «Общий MCP»). Разрешены только области из настроек (`tasker mcp workspace add`); других папок агент открыть не может. Он не зависит от десктопа: его запускают командой, он переживает закрытие терминала и (по желанию) стартует при входе в систему.

```bash
tasker mcp workspace add ~/work/project-a     # разрешить рабочую область (папку или файл SQLite)
tasker mcp workspace add ~/work/project-b
tasker mcp start                              # запустить в фоне; показывает адрес и области
tasker mcp status                             # работает ли, порт, области, автозапуск (код 3, если не работает)
tasker mcp stop                               # остановить
tasker mcp restart                            # перезапустить (например, после смены порта); вызовы в работе обрываются
tasker mcp upgrade                            # перейти на установленную сборку без простоя (см. «MCP-демон: обновление без простоя»)
tasker mcp autostart enable                   # запускать при входе в систему и поднимать при падении
tasker mcp autostart disable                  # выключить; работающий демон продолжает работать
tasker mcp run                                # в этом терминале, до Ctrl+C (запускает tasker-mcpd и ждёт его)
```

- **Автозапуск.** macOS — агент launchd `~/Library/LaunchAgents/com.tasker.mcp.plist` (`RunAtLoad`, `KeepAlive`: launchd перезапускает демон, если он упал). Linux — пользовательская служба systemd `~/.config/systemd/user/tasker-mcp.service` (`Restart=always`; чтобы служба стартовала без входа в систему, нужен `loginctl enable-linger`). Пока автозапуск включён, демоном владеет служба: `start` и `stop` идут через неё (иначе система тут же подняла бы остановленный демон), а `stop` действует до следующего входа в систему. Включение автозапуска забирает у службы демон, запущенный вручную; выключение работающий демон не останавливает. Windows — задача Планировщика заданий «Tasker MCP» для текущего пользователя (не служба Windows, права администратора не нужны; `WindowsTaskService`, управление через `schtasks.exe` с XML-определением): триггер — вход пользователя, перезапуск при падении (раз в минуту, до 999 раз), одна копия (`IgnoreNew`), работает от батареи, не останавливается при простое, без ограничения по времени. Запуск без окна консоли: `conhost.exe --headless tasker-mcpd.exe --detached` (Windows 10 1809 и новее; не wscript/VBS и не PowerShell `-WindowStyle Hidden`: первый отключаем, второй мигает окном), поэтому Планировщик видит процесс демона целиком: `schtasks /end` останавливает его, остановка по запросу не считается падением и демон не поднимается снова. `start`/`stop` идут через `schtasks /run` и `/end`. Определение задачи — UTF-16 XML в `%LOCALAPPDATA%\Tasker\service\Tasker MCP.xml` (оно же признак «автозапуск включён»); пробелы и кириллица в путях квотируются по правилам Windows. Если каталог данных переопределён (`TASKER_HOME`), задача запускает демон через `cmd /c set …` (значение без `%` и `"`). Состояние (`Running`) читается через PowerShell `Get-ScheduledTask`, потому что вывод schtasks переводится на язык системы. Имя задачи и каталог определения подменяются `TASKER_SERVICE_LABEL` и `TASKER_SERVICE_DIR` (тесты). XML, командная строка и разбор состояния — чистые функции со снимками в `WindowsTaskServiceTests`; проверка на настоящей Windows — по чек-листу в задаче TSK-118. Фоновый запуск (`tasker mcp start`, без окна) и остановка (`tasker mcp stop`) на Windows работают и без автозапуска; общий сокет, остановка и режим супервизора — в разделе [«MCP-демон на Windows»](Windows) ниже. Служба запускает `tasker-mcpd --detached` напрямую (описание старого вида — `tasker mcp run --detached` — продолжает работать).
- **Демон — отдельная программа.** Консольной утилите `tasker` веб-слой не нужен, поэтому ASP.NET Core и MCP живут в `tasker-mcpd` (проект `Tasker.Daemon.Host`), а `tasker` (проект `Tasker.Daemon` — клиентская часть без веб-слоя) запускает её из своего каталога: `mcp start` — в фоне, `mcp run` — в терминале (код выхода и остановка Ctrl+C или SIGTERM передаются). Программа ищется рядом с `tasker` (ссылка `~/.local/bin/tasker` раскрывается до настоящего пути; под `dotnet tasker.dll` — `tasker-mcpd.dll` рядом с dll). Нет её (установка с `--no-daemon`) — `mcp start` и `mcp run` объясняют, что делать. При разработке (`dotnet build`, `dotnet run`) демон собирается и кладётся рядом с `tasker.dll` сам. Сам `tasker-mcpd` можно запустить и руками (`tasker-mcpd --help`).
- **Один демон на пользователя.** `mcp/daemon.lock` в каталоге данных держится, пока процесс жив, — второй `run` отказывается. Упавший демон блокировку не оставляет.
- **Области открываются и закрываются на лету.** Демон следит за файлом настроек: `mcp workspace add/remove` (из консоли или десктопа) действует сразу, без перезапуска. Область, которую не удалось открыть (папку удалили, диск не подключён), не мешает остальным, показывается в `status` как `failed` и пробуется снова при следующем изменении настроек и раз в 30 секунд; пустых `.tasker` в отсутствующих папках он не создаёт. Порт из настроек применяется после `restart`; `status` напоминает об этом.
- **Управление.** `tasker` говорит с демоном по `/daemon/status`, `/daemon/stop` и `/daemon/sync` на его порту. Нужен секрет из `mcp/daemon.json` (читает только владелец), и запросы проверяются на локальность (`Host`/`Origin`), как у десктопа. Журнал — `logs/mcp-<дата>.log` (7 дней); если демон не поднялся, `start` показывает причину из журнала (например, что порт занят).
- **Десктоп уступает демону.** При запуске десктоп спрашивает у демона: работает — свой MCP не поднимает (порт не занимает), а адрес области берёт у демона; не работает — поднимает свой на порту из `--mcpport` или из настроек. **Если демон стартует позже и десктоп уже держит порт, десктоп отпускает порт на лету.** Механизм минимальный и без нового протокола: десктоп раз в полсекунды смотрит на `mcp/daemon.lock` (демон берёт его первым делом, ещё до проверки порта); увидев блокировку, перестаёт слушать порт MCP, не останавливая интерфейс (адреса хоста заданы настройкой Kestrel из памяти, которую он перечитывает на лету), и адрес области дальше отдаёт демон. Демон, найдя порт занятым, ждёт до 5 с (проверка каждые 0,2 с), пока его отпустят, и только потом отказывается (`Port … is busy`: смените порт `tasker mcp port <номер>` или закройте то, что его держит). Выбор: не сигнал демона десктопу (нужен адрес и секрет десктопа, обратный канал) и не принудительное закрытие порта; наблюдение за блокировкой работает и при ручном `tasker-mcpd`, и при launchd/systemd. Обратно порт десктоп не забирает: если демон остановился, MCP десктопа вернётся после его перезапуска.
- **Область в демоне и в десктопе одновременно.** С одной папкой параллельно работают демон, десктоп и команды `tasker` (см. «Несколько процессов на папку»): правки агента через MCP видны в десктопе, правки в десктопе — агенту.

**Глобальные настройки** — файл `settings.json` в каталоге данных Tasker (`~/Library/Application Support/Tasker`, `%LOCALAPPDATA%\Tasker`; `TASKER_HOME` меняет каталог). Он общий у консоли, демона и десктопа: что изменено в одном месте, видят остальные (демон следит за файлом; десктоп читает его при запуске и спрашивает демона при каждом обращении). Изменение — под короткой блокировкой `settings.lock` и атомарной записью, поэтому одновременные правки из нескольких процессов не теряются; сломанный файл не перезаписывается, а команды сообщают об ошибке.

```json
{
  "mcp": {
    "port": 5719,
    "workspaces": [
      { "kind": "files", "path": "/Users/me/work/project-a" },
      { "kind": "sqlite", "path": "/Users/me/data/tasker.db" }
    ]
  }
}
```

`tasker mcp config` показывает файл и значения, `tasker mcp port [<номер>]` — порт, `tasker mcp workspace list|add|remove` — области (путь канонический: та же папка по символической ссылке или через `.tasker` — одна запись).

## MCP-демон: обновление без простоя

`tasker mcp restart` закрывает порт на несколько секунд, обрывает вызовы в работе и заново открывает области (в это время вызовы получают `[unavailable]`, TSK-100). Если с демоном постоянно кто-то работает — агенты, скрипты, десктоп, — это ломает чужую работу. `tasker mcp upgrade` заменяет сервер на новую сборку на лету: порт не закрывается, вызовы не отклоняются и не обрываются.

```bash
tasker mcp upgrade                  # заменить на лету (установщик делает это сам после копирования новой сборки)
tasker mcp upgrade --timeout 120    # сколько ждать, пока новый процесс откроет области (по умолчанию 60 с)
tasker mcp upgrade --restart        # жёсткий путь: остановить и запустить (то же, что restart)
tasker mcp status                   # на время замены показывает оба рабочих процесса
```

**Как это устроено (выбранный дизайн).** `tasker-mcpd` теперь — маленький *супервизор*; сервер MCP работает в *рабочем процессе* (`tasker-mcpd --worker`), который супервизор запускает.
- Супервизор — тот процесс, которым владеют launchd (`KeepAlive`), systemd и `tasker mcp start`; он держит `mcp/daemon.lock` (поэтому TSK-51 не меняется: у блокировки один неизменный владелец) и **слушающий сокет на порту** — открывает его один раз и не закрывает, пока жив демон. Описание службы (plist, unit) не изменилось, launchd ничего не знает о рабочих процессах.
- Рабочие процессы наследуют сокет (дескриптор без close-on-exec, Kestrel `ListenHandle`) и принимают из него соединения через *затвор* (`AcceptGate`). Замена: рядом со старым запускается новый (затвор закрыт — соединения принимает старый), открывает все области, сообщает `ready`; супервизор открывает затвор новому, закрывает старому (`drain`). Соединение, которое никто пока не принял, ждёт в очереди ядра: окна, когда порт не принимает, нет — отказов нет.
- Старый процесс: перестаёт принимать, отвечает на уже принятые вызовы (с `Connection: close`, чтобы клиент переподключился к новому), ждёт, пока вызовов в работе не станет ноль на 2 с подряд, но не дольше 60 с (больше `CascadeWait` = 30 с, поэтому массовая правка, ждущая блокировок, успевает закончиться); потом оставшиеся получают `503` с `Retry-After: 1` и процесс выходит. Старый и новый одновременно работают с одной папкой — это штатно (межпроцессные блокировки записи, индекс, версии). Пороги меняют `TASKER_MCP_DRAIN_QUIET_MS` и `TASKER_MCP_DRAIN_TIMEOUT_MS` (для тестов).
- Откат: новый процесс не поднялся, вышел, не открыл область, которая у старого открыта (например, формат файлов новее), или не успел за `--timeout` — его снимают, старый продолжает работать, `tasker mcp upgrade` объясняет причину (код выхода не 0). Затвор новому открывают раньше, чем закрывают старому, поэтому и в момент переключения есть кому принять соединение.
- Рабочий процесс упал — супервизор запускает его снова (с паузами; после пяти падений за минуту сдаётся и выходит — дальше служба). Супервизор погиб — рабочие процессы видят конец канала и выходят, порт освобождается. Обмен супервизор↔рабочий процесс — строки JSON в stdin/stdout, неизвестные поля игнорируются: сборки супервизора и рабочего процесса могут различаться (супервизор не обновляется на лету — только перезапуском демона; он намеренно мал).
- Готовность: `GET /ready` (200, когда все области открыты или не открылись и процесс не закрывается; иначе 503) и `GET /health` (процесс жив). `tasker mcp status` показывает рабочие процессы: сборку, версию, возраст и роль (`accepting calls`, `starting`, `finishing its calls and leaving`).
- Клиенты: `tasker` повторяет запрос управления (`/daemon/status`, `/daemon/sync`) один раз через 0,3 с, если соединение оборвалось. MCP-клиент в штатной замене ошибок не видит; единственный повторяемый исход — вызов, оборванный по истечении 60 с (503 + `Retry-After`, или обрыв соединения).
- SSE: у демона нет долгоживущих потоков — MCP работает без состояния, ответ вызова завершается вместе с вызовом (потоки `/events` есть только у десктопа и демоном не обслуживаются), поэтому переподключать нечего.

**Совместимость.** Демон, запущенный по-старому (одним процессом: до этой версии или `tasker-mcpd --single`), продолжает работать; первый `tasker mcp upgrade` его перезапускает (`restart`) и говорит об этом, дальше замены бесшовные. Порядок обновления — «сначала демон, потом клиенты»: новый демон может уметь больше инструментов; старый демон встречает файлы более нового формата как «более новый формат» и не пишет в них, поэтому область, которую новая сборка не открывает, а старая открывает, останавливает замену. Формат файлов командой `upgrade` не меняется (`tasker migrate` — отдельно). Windows: по умолчанию `tasker-mcpd` работает одним процессом (`--single`), `tasker mcp upgrade` там перезапускает демон; бесшовный режим включается `TASKER_MCP_SUPERVISOR=1` (см. [«MCP-демон на Windows»](Windows)). Установщик при неудачной замене демон НЕ перезапускает (новая сборка могла не подняться, а перезапуск остановил бы и рабочий сервер): печатает причину и подсказку `tasker mcp upgrade --restart`.

**Выбор и альтернативы.** *SO_REUSEPORT* (оба процесса слушают порт): на Linux соединения в очереди закрывающегося слушателя сбрасываются, на macOS распределение между слушателями иное, чем на Linux, — поведение зависит от системы, а процесс под KeepAlive всё равно один. *launchd/systemd socket activation*: сокетом владеет система, но у launchd задача — один процесс (два одновременно не запустить), у systemd — только Linux. *Два порта и прокси*: лишний переход на каждый вызов, а ошибка прокси — простой для всех. *Передача сокета из процесса в процесс (SCM_RIGHTS)*: тот же эффект, что наследование, но сложнее, и новый процесс оказывался бы вне управления службы. Выбранный вариант проверен на macOS (arm64) и на Linux (arm64, TSK-111): интеграционные тесты `DaemonUpgradeTests`, сценарий `upgrade` стенда `tools/Tasker.Stress`; на Linux код тот же (POSIX `fcntl`, наследование дескрипторов), а под настоящим `systemd --user` замена на лету, перезапуск и остановка проверены скриптом — см. [«MCP-демон на Linux»](Linux#mcp-демон-на-linux).
