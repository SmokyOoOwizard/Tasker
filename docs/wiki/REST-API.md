# REST API

`GET/POST /api/projects`, `GET/PATCH/DELETE /api/projects/{projectId}`, `GET /api/projects/{projectId}/stats` — сколько чего в проекте: `{tasks, boards, statuses, statusSets, taskTypes, series, linkTypes}` (404 для несуществующего или недоступного проекта; консоль показывает это перед удалением проекта, а интерфейс — в блоке удаления, где по-прежнему нужно ввести название проекта). Всё остальное — внутри проекта, `/api/projects/{projectId}/…`:

| Путь | Методы |
|---|---|
| `/statuses`, `/status-sets`, `/task-types`, `/link-types`, `/boards`, `/series`, `/fields`, `/enums` | `GET` (список), `POST` (создать) |
| `/statuses/{id}`, `/status-sets/{id}`, `/task-types/{id}`, `/link-types/{id}`, `/boards/{id}`, `/series/{id}`, `/fields/{id}`, `/enums/{id}`, `/tasks/{id}` | `GET`, `PATCH` (изменить), `DELETE` |
| `/tasks/{id}/links` | `GET` (все связи задачи), `POST {"typeId", "targetId", "version"?}` (добавить), `DELETE ?typeId=&targetId=&version=` (убрать) — см. [«Связи между задачами»](Связи-и-иерархия) |
| `/tasks` | `GET` (список; `?statusId=`, `?typeId=`, `?seriesId=` — каждый можно повторять: значения одного параметра ИЛИ, разные И; `?field=Имя%3Dзначение` — повтор, И), `POST` |
| `/boards/{id}/columns/{columnId}/tasks` | `GET` — задачи колонки (статус из списка колонки **и** её условия по полям); `?field=Имя%3Dзначение` (повтор — И) — дополнительное условие просмотра, колонка его не хранит |
| `/boards/{id}/columns/{columnId}/move` | `POST {"taskId": …, "version": …}` — перенести задачу в колонку; статус берётся из правила переноса; задача, не подходящая под условия колонки по полям, не переносится (`400`) |

**Все списки постраничные**: проекты, пользователи, агенты и их токены, участники проекта, статусы, наборы, типы, доски, задачи, поля, перечисления. Это касается и REST, и инструментов MCP `list_*`. Параметры: `?offset=0&limit=50`. `limit` — от 1 до 200, по умолчанию 50, большее значение урезается до 200. Ответ — `{"totalCount": …, "offset": …, "limit": …, "data": [...]}`.

**JSON без `\uXXXX`.** Настройки JSON одни на всё приложение — `Tasker.Core/TaskerJson` (camelCase, enum строками, нестрогое экранирование): REST, SSE, инструменты MCP, `--json` консоли, обмен CLI с демоном, `settings.json`. Кириллица, обратные кавычки, «ёлочки», эмодзи и `<`, `>`, `&` идут как есть (JSON здесь — данные, не HTML), экранируются только `"`, `\`, управляющие символы и U+2028/2029. Новые места сериализации берут `TaskerJson.Options` (или `TaskerJson.Configure` для чужих опций), своих опций не заводят. **На проводе MCP** конверт JSON-RPC кодирует сам SDK (ModelContextProtocol 2.2.0, последняя версия; опции `McpJsonUtilities.DefaultOptions` ни через `ServerOptions`, ни через параметры транспорта не настроить) и пишет всё не-ASCII как `\uXXXX` (кириллица — 6 байт вместо 2, эмодзи — 12 вместо 4, даже кавычка — `"`). Поэтому `Tasker.Mcp/WireJson` перекодирует тело ответа эндпоинта `/mcp` (`application/json` и SSE `text/event-stream`): подмена возможности тела ответа (`IHttpResponseBodyFeature`) на уровне эндпоинта и один лексический проход по байтам, без разбора JSON. Незавершённый escape на границе записей переносится в следующую, так что потоковые ответы и SSE корректны; `Content-Length` снимается (длина меняется); сжатые ответы и прочие типы содержимого не трогаются. Заменяется всё, что не нужно экранировать по правилам выше (`\uXXXX` → символ, пара суррогатов → один символ вне BMP, `"` → `\"`, `\` → `\\`, `\u000A` → `\n`); управляющие символы, U+007F–U+009F, U+2028/2029 и одиночные суррогаты остаются экранированными, `\\u0041` (косая и текст «u0041») не трогается. Замер на демоне: `list_tasks` на 3 кириллические задачи с описанием в 200 символов — 6105 байт на проводе до, 3013 после (−51%); на коротких заголовках без описаний 2954 → 1903 (−36%). Лишняя работа — один проход по байтам ответа (микросекунды на ответ в десятки КБ). Для агента токены не меняются (считаются по разобранному тексту), выигрыш — в весе трафика и читаемости сырого обмена и логов. Тесты: `WireJsonTests` (перекодирование, границы записей, JSON/SSE/прочие типы) и `JsonEscapingTests` (сырой ответ демона).

**Краткий режим списков задач.** Описание может быть длинным (тысячи символов), и страница в 50 задач с полными описаниями слишком велика для агента. Поэтому у списков задач есть один параметр `descriptionLength`: `0` — без описания, `N` — первые N символов, `-1` — полный текст. Он есть у MCP `list_tasks`, `find_tasks_by_reference` и `get_board`, у REST `GET /tasks` и `GET /boards/{id}/columns/{columnId}/tasks` (`?descriptionLength=`) и у консоли — `--description-length` в `task list`, `board tasks`, `board show` (действует на `--json`: в тексте описаний нет). Значение по умолчанию: **200** в MCP, **полный текст** в REST и консоли (интерфейс и скрипты не ломаются). Меньше `-1` — ошибка `[invalid]` / `400`. В записи списка описание усечено, плюс `descriptionTruncated` (true — текст обрезан), `descriptionLength` (полная длина описания в символах) и `linksCount` (число связей: исходящих и входящих). Режет по символам Unicode, не разрывая суррогатные пары (эмодзи) и сочетания с комбинируемыми знаками или ZWJ, «…» в текст не добавляется, поэтому результат не длиннее N символов и может быть короче. `totalCount` и страницы не меняются. Одна задача — `get_task`, `GET /tasks/{id}`, `task get`, а также `GET /tasks/resolve`, `create_task`, `update_task` — всегда с полным описанием; полный текст из списка MCP — `get_task` или тот же вызов с `descriptionLength` `-1`. Усечение одно, в ядре: `TaskService.Preview` строит `TaskListItem` (`TaskItem` + `descriptionTruncated`/`descriptionLength`/`linksCount`; `DescriptionPreview.Cut` режет текст), `TaskService.List` и `BoardService.GetColumnTasks` возвращают `ListDto<TaskListItem>`. Входящие связи считаются одним запросом на страницу — `ITaskStorage.CountLinkedTo` (в файловой реализации по таблице `task_links` индекса, в БД — `GROUP BY`).

**Фильтры списков задач (TSK-105).** Ядро давно принимает массивы (`TaskFilter.TypeIds/StatusIds/SeriesIds`, внутри массива — ИЛИ), интерфейсы собирают их из нескольких значений. Консоль: `--status`, `--type`, `--series` — `Kit.Many` (повтор параметра и несколько значений после одного, как у `--field`); значения разбираются через `Refs.FindDistinct` (имя, id, короткий id; повторы убираются, неизвестное — ошибка с перечнем допустимых по алфавиту; у серий — `SeriesCommands.FindDistinct`). REST: `GET /tasks?statusId=A&statusId=B` (также `typeId`, `seriesId`; одно значение — как раньше). MCP: `statusIds`, `typeIds`, `seriesIds` у `list_tasks`, одиночные `statusId`/`typeId`/`seriesId` объединяются с массивами (`TaskTools.Merge`). Фильтр собирает `TaskFilter.Of`: пустой или не заданный параметр не ограничивает (пустой массив в самом фильтре — «ничего не подходит», поэтому в интерфейсах он не передаётся). Внутри параметра ИЛИ, между параметрами (статус, тип, серия, `field`) И; статус не из набора типа просто ничего не находит. Доска (колонка = статусы, TSK-85) своего фильтра по статусу не имеет, `board tasks`/`board show`/`get_board` не меняются. Автодополнение: `--status` после `--type A --type B` (или `--type A B`) подсказывает статусы наборов всех названных типов, значения подсказываются и после повтора параметра.

**Обрезка строк по ширине окна.** Текстовые списки консоли (`task list`, `task links`, `board tasks`, `board show`, блок `links:` у `task get`, все `… list`) строятся одним форматировщиком `Tasker.Cli/Table` (колонки выровнены по знакам экрана, ширина — не длина UTF-16: кириллица 1, эмодзи и CJK 2, комбинируемые знаки 0). Когда задан предел ширины (`Context.MaxWidth`), строка, которая в него не помещается, обрезается справа с одним `…` (`Table.Truncate`, по графемам: суррогатные пары, флаги, ZWJ-эмодзи и буквы с комбинируемыми знаками не разрываются). Заголовок идёт последней колонкой, поэтому укорачивается именно он, а ссылка, статус и тип остаются целыми и выровненными; если не помещается даже начало без заголовка — режется вся строка. Предел считает `Terminal.Limit` при каждом вызове: `--no-truncate` — не обрезать; `--width N` (число — ширина, `0`/`auto` — по терминалу) и переменная `TASKER_WIDTH` (`--width` сильнее) или `--truncate` (`--no-wrap`) — обрезать, в том числе при перенаправлении; `--width off` и `TASKER_WIDTH=off`/`0` — не обрезать; без них — когда вывод идёт в терминал и ширина известна (`Console.WindowWidth`, иначе `COLUMNS`) либо «под watch» (`Terminal.IsScreen`: stdout не терминал, но экспортированы обе `COLUMNS` и `LINES` с положительными значениями, как делает procps `watch`; ширина — `COLUMNS`; одна переменная, ноль или мусор — не обрезаем; проверки родительского процесса нет); ниже 20 знаков не сжимаем. Не затрагиваются `--json`, текст `task get` (описание), ошибки и подсказка пагинации. Тесты: `TruncateTests`.

**Порядок списков задач (`--sort`, TSK-98).** По умолчанию списки идут в порядке создания (`CreatedAt`, затем id). Параметр `sort` меняет его: консоль — `--sort status,-updated,Estimate` у `task list`, `board tasks`, `board show` (внутри колонок); REST — `?sort=` у `GET /tasks` и `GET /boards/{id}/columns/{columnId}/tasks`; MCP — `sort` у `list_tasks` и `get_board`. Ключи через запятую, `-` перед ключом — по убыванию; ключ — `status`, `type`, `title`, `created`, `updated`, `series` или имя поля (каталога или собственное поле задач; встроенное слово главнее поля с тем же именем). Правила, принятые при разработке:
- **Статус** — по месту в наборе статусов типа задачи (не по алфавиту). У задач с разными наборами: место, затем название набора и название статуса (без учёта регистра); типы на одном наборе делят места. **Тип** — по названию, **заголовок** — без учёта регистра по Unicode (нижний регистр, порядок ординальный, одинаковый во всех хранилищах), **серия** — серия с меньшим префиксом (двоично, как в индексе), внутри неё номер по числу (`TSK-9` раньше `TSK-12`); задача в нескольких сериях берётся по первой.
- **Поле** — по типу: int и float — по числовому столбцу, date — по тексту `yyyy-MM-dd`, bool — `false` раньше `true`, string — без учёта регистра, enum — по порядку значений в перечислении. У поля с несколькими значениями — первое значение (в порядке записи: `rowid` значения в индексе, `Position` в БД), и при убывании тоже первое. Имена полей ищутся как у фильтра (правила `TaskService.ParseFieldFilters`): поле каталога подхватывает и собственные поля с тем же именем и типом; без поля в каталоге — собственные поля, при нескольких типах ошибка со списком типов.
- **Нет значения** — в конце всегда, и при возрастании, и при убывании (первым в `ORDER BY` стоит признак «значения нет»). **Равные ключи** — в порядке по умолчанию (создание, затем id), поэтому страницы не пересекаются и не теряют задачи; `totalCount`, `descriptionLength` и сочетание с фильтрами и `--field` не меняются.
- **Ошибки.** Неизвестный ключ — `400` / `[invalid]` / код 1 со списком допустимых ключей и полей каталога; пустой ключ (`a,,b`), повтор ключа, собственные поля нескольких типов — тоже.
- **Устройство.** Из текста ключи строит `TaskService.ParseSort` → `TaskFilter.Sort` (`TaskSortKey`: что сортировать, направление; для статуса, типа и серии ядро заранее раскладывает таблицы мест — `StatusRank`, `IdRank`, для enum — порядок значений; хранилище только сравнивает по ним). Запрос один, задачи в память целиком не грузятся. Файлы: `WorkspaceIndex.OrderBy` собирает `ORDER BY` по `files` (`sort_text` — заголовок в нижнем регистре, `sort_num` — создание, `sort_updated` — правка; индексы `ix_files_by_name`, `ix_files_by_updated`), `task_series` и `task_field_values` (подзапрос «первое значение», число — столбец `number`), места — `CASE`; `lower()` в соединении индекса подменена на Unicode (`SchemaVersion` 9). БД: `TaskSorting` строит выражения EF (подзапросы по `TaskFieldValues` и номерам серий, `CASE` по таблице мест; `lower()` в SQLite подменяется перехватчиком соединения `SqliteUnicodeLower`, в Postgres она Unicode и так), без изменения схемы. Автодополнение `--sort`: `Sources.SortKeys` — ключи и имена полей, после запятой следующий ключ, записи с `-` — когда набран `-`.

`PATCH` меняет только переданные поля. Списки заменяются целиком: `statusIds` у набора, `statusSetIds` и `columns` у доски. В `columns` колонка с `id` сохраняет его, без `id` создаётся новая, а колонки, которых нет в списке, удаляются. Условия колонки по полям — `fieldFilters` у колонки в `POST /boards` и `PATCH /boards/{id}`: строки, как `field` у `GET /tasks` (`["Component=API", "Estimate>=3", "Owner:set"]`); не передан — у существующей колонки (с `id`) условия остаются, у новой их нет; `[]` — убрать условия; список заменяет условия целиком. В ответе и в `GET /boards` колонка хранит их как `fieldConditions: [{fieldId, operator, value}]` (поле и значение enum — по id, оператор словом: `equal`, `notEqual`, `greater`, `greaterOrEqual`, `less`, `lessOrEqual`, `set`, `unset`, `attached`, `detached`). У задачи `description: ""` очищает описание.

Миграций БД пока нет. Схему при старте создаёт `EnsureCreated`, но изменения уже созданной схемы он не применяет: после изменения моделей старую БД нужно удалить.
