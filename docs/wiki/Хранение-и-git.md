# Хранение и git

Данные лежат либо в папке `.tasker` рядом с кодом (обычные текстовые файлы, которые удобно вести в git), либо в базе данных (SQLite или Postgres). Тип хранилища выбирают при запуске ([Настройка и сервер](Настройка-и-сервер)).

## Папка `.tasker`

```
.tasker/
  users/<id>.yaml
  projects/<id проекта>/
    project.yaml
    tasks/  statuses/  status-sets/  task-types/  boards/
    series/  link-types/  fields/  enums/        — по файлу на сущность
  .cache/                                         — локальный кэш, в git не попадает
```

Файл сущности называется `<название>-<первые 8 знаков id>.yaml`, у задачи название берётся из заголовка: `fix-login-11ab5ea4.yaml`. Переименование сущности переименовывает файл; ссылки идут по id, поэтому не ломаются. Пользователи и `project.yaml` по названию не переименовываются.

```yaml
formatVersion: 9
id: 11ab5ea4-1ad5-4d50-a57b-a749cf965bef
title: Fix login
description: Login fails
typeId: ebb9f429-93b8-4f37-bf78-f5628f9a6379
statusId: 2a7c1942-b5d4-4eb0-ab24-4e67d3b4e57a
series:
- seriesId: 245050ef-c1e4-49b7-acd3-a29ff1daa3d9
  number: 1
```

Нечитаемые (маркеры конфликта, битый YAML) выпадают из списков и показываются как проблемы в `tasker sync`.

## Версия формата

Первая строка каждого файла — `formatVersion` (сейчас `9`). Это версия формата, а не программы.

| Ситуация | Поведение |
|---|---|
| Файл старого формата | читается всегда; на диске меняется только при записи этой сущности |
| Файл новее, чем знает программа | не читается и не перезаписывается; нужно обновить Tasker |
| `tasker migrate` | переписывает все файлы в текущую версию и приводит имена к схеме выше; `--dry-run` показывает план, `--check` ничего не пишет и возвращает код 2, если есть что менять |

## Кэш, `tasker sync` и хуки

Для быстрых списков и поиска Tasker держит индекс `.tasker/.cache/index.db`; он пересобирается из файлов и может быть удалён в любой момент. Десктоп и демон MCP следят за папкой сами (около 0,3–2 с), `tasker` сверяет индекс при запуске.

| Команда | Что делает |
|---|---|
| `tasker sync` | сверяет кэш с файлами сразу и показывает нечитаемые файлы и проблемы серий; `--quiet` молчит, если всё в порядке |
| `tasker hooks install` | git-хуки `post-merge`, `post-checkout`, `post-rewrite` запускают `sync` после pull, checkout, merge, rebase; ещё `hooks status`, `hooks uninstall` |

Хуки локальные: ставьте их в каждом клоне. После `git reset --hard` и `git stash pop` хуков нет, кэш догонит слежение или следующий `tasker`; после слияния с конфликтом запустите `tasker sync` вручную.

## Работа с git

- Коммитьте `.tasker` целиком; `.cache` исключён автоматически.
- Один файл на сущность: правки разных задач сливаются без конфликтов, а конфликт в одной задаче решается как обычный конфликт текста.
- Версия сущности — хэш содержимого файла, отдельного поля нет, поэтому из-за неё конфликтов не бывает.
- Переименование сущности после слияния выглядит как удаление и создание файла; `sync` находит сущность по id внутри файла.
- Если две ветки создали задачи с одним номером серии (оба `TSK-5`), конфликта git нет, но номер дублируется: обе задачи видны с пометкой, `sync` сообщает о них. Исправление: `tasker cleanup --resolve-conflicts` (самая ранняя задача сохраняет номер, остальным выдаются следующие).
- `tasker cleanup` убирает ссылки на удалённые серии, задачи и типы связей; `--dry-run` и `--check` ничего не пишут. Циклы связей только сообщаются.

## Режим БД

В SQLite или Postgres те же сущности лежат в таблицах; версия — счётчик, ссылки между сущностями — внешние ключи. Схема создаётся при первом запуске и не мигрирует: при смене модели старую базу нужно пересоздать.

## Версии и блокировки

| Механизм | Как работает |
|---|---|
| Проверка версии | `PATCH` и `DELETE` несут версию, которую видел клиент; если запись успели изменить, ответ `409 modified`, клиент перечитывает и повторяет. Из нескольких одновременных правок одной версии проходит ровно одна |
| Блокировка на время правки | редактор берёт блокировку записи (`tasker lock acquire\|show\|release <сущность> <id>`; в MCP `lock_entity`, `unlock_entity`, `get_lock`); пока её держит другой, изменить и удалить запись нельзя, ответ `409 locked` с именем держателя |
| Срок | 2 минуты; редактор продлевает её, пока открыта форма, забытая истекает сама |
| Кто держит | пользователь, агент или «локальный человек» (имя — `tasker whoami [имя]`); интерфейс и консоль считаются разными держателями |
| Где хранится | в файловом режиме — `.tasker/.cache/edit-locks`, между машинами не передаётся (там остаётся проверка версии); в БД — таблица |

Блокировка есть у проектов, задач, типов задач, статусов, наборов статусов, досок и серий; одиночным правкам она не нужна.

## Параллельная работа

Десктоп, демон MCP и команды `tasker` могут работать с одной папкой одновременно.

| Гарантируется | Не гарантируется |
|---|---|
| номера серии уникальны и без пропусков | правка в консоли без `--expected-version` берёт версию на момент вызова: побеждает последняя (MCP требует версию всегда) |
| запись с версией проходит только у одного клиента, потерянных обновлений нет | правки одной задачи многими клиентами дают частые `modified`; клиент обязан повторять |
| правки разных задач не мешают друг другу | |
| связи не теряются при одновременном добавлении; встречные связи не образуют цикл | во время удаления проекта соседние запросы могут получить ошибку «не найдено» |
| файлы пишутся через временный файл и переименование; после аварийного завершения повреждённых файлов нет, индекс и блокировки восстанавливаются сами | |
| массовые правки (удаление серии, `cleanup`) ждут снятия блокировки затронутых задач до 30 с, затем `locked` и ничего не меняют | |

Ограничения: Postgres не проверялся.
