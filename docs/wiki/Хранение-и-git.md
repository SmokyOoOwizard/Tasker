# Хранение и git

Данные лежат либо в папке `.tasker` рядом с кодом (обычные текстовые файлы, которые удобно вести в git), либо в базе данных (SQLite или Postgres). Тип хранилища выбирают при запуске ([Настройка и сервер](Настройка-и-сервер)).

## Папка `.tasker`

```
.tasker/
  users/<id>.yaml
  projects/<название проекта>-<первые 8 знаков id>/
    project.yaml
    tasks/  statuses/  status-sets/  task-types/  boards/
    series/  link-types/  fields/  enums/        — по файлу на сущность
  .cache/                                         — локальный кэш, в git не попадает
```

Файл сущности называется `<название>-<первые 8 знаков id>.yaml`, у задачи название берётся из заголовка: `fix-login-11ab5ea4.yaml`. Папка проекта называется так же — по названию проекта: `projects/tasker-6cb8f29b/`; настоящий id проекта — в `project.yaml`. Переименование сущности переименовывает файл, переименование проекта — папку (одной операцией: другие процессы видят старую или новую папку целиком); ссылки идут по id, поэтому не ломаются. Пользователи называются по id и не переименовываются. Папки и файлы с прежними именами по полному id (`projects/<id>/`, `<id>.yaml`) читаются наравне с новыми.

```yaml
formatVersion: 10
id: 11ab5ea4-1ad5-4d50-a57b-a749cf965bef
title: Fix login
description: Login fails
typeId: ebb9f429-93b8-4f37-bf78-f5628f9a6379
statusId: 2a7c1942-b5d4-4eb0-ab24-4e67d3b4e57a
series:
- seriesId: 245050ef-c1e4-49b7-acd3-a29ff1daa3d9
  number: 1
```

Нечитаемые (маркеры конфликта, битый YAML) выпадают из списков и показываются как проблемы в `tasker sync`.

## Версия формата

Первая строка каждого файла — `formatVersion` (сейчас `10`). Это версия формата, а не программы.

| Ситуация | Поведение |
|---|---|
| Файл старого формата | читается всегда; на диске меняется только при записи этой сущности |
| Файл новее, чем знает программа | не читается и не перезаписывается; нужно обновить Tasker |
| `tasker migrate` | переписывает все файлы в текущую версию и приводит имена файлов и папок проектов к схеме выше (папка с прежним именем по id тоже считается требующей миграции); `--dry-run` показывает план, `--check` ничего не пишет и возвращает код 2, если есть что менять |

## Кэш, `tasker sync` и хуки

Для быстрых списков и поиска Tasker держит индекс `.tasker/.cache/index.db`; он пересобирается из файлов и может быть удалён в любой момент. Десктоп и демон MCP следят за папкой сами (около 0,3–2 с), `tasker` сверяет индекс при запуске.

| Команда | Что делает |
|---|---|
| `tasker sync` | сверяет кэш с файлами сразу и показывает нечитаемые файлы и проблемы серий; `--quiet` молчит, если всё в порядке |
| `tasker hooks install` | git-хуки `post-merge`, `post-checkout`, `post-rewrite` запускают `sync` после pull, checkout, merge, rebase; ещё `hooks status`, `hooks uninstall` |

Хуки локальные: ставьте их в каждом клоне. После `git reset --hard` и `git stash pop` хуков нет, кэш догонит слежение или следующий `tasker`; после слияния с конфликтом запустите `tasker sync` вручную.

## Работа с git

- Коммитьте `.tasker` целиком; `.cache` исключён автоматически.
- Один файл на сущность: правки разных задач сливаются без конфликтов, а конфликт в одной задаче решается как обычный конфликт текста.
- Переименование сущности после слияния выглядит как удаление и создание файла; `sync` находит сущность по id внутри файла.
- Если одна ветка переименовала проект, а другая добавила задачу в его прежнюю папку, после слияния у проекта две папки. Tasker читает их вместе (задачи обеих видны в проекте), а `sync` и `list_workspace_problems` сообщают о второй папке. `tasker cleanup` (и `tasker migrate`) переносит её файлы в папку с текущим именем; файл, который там уже есть с другим содержимым, остаётся на месте и попадает в отчёт — его нужно слить вручную.
- Если две ветки создали задачи с одним номером серии (оба `TSK-5`), конфликта git нет, но номер дублируется: обе задачи видны с пометкой, `sync` сообщает о них. Исправление: `tasker cleanup --resolve-conflicts` (самая ранняя задача сохраняет номер, остальным выдаются следующие).
- `tasker cleanup` убирает ссылки на удалённые серии, задачи и типы связей; `--dry-run` и `--check` ничего не пишут. Циклы связей только сообщаются.

## Режим БД

В SQLite или Postgres те же сущности лежат в таблицах. Схема создаётся при первом запуске и не мигрирует: при смене модели старую базу нужно пересоздать.

## Версии и блокировки

- **Версия.** Правка и удаление несут версию, которую видел клиент; если запись успели изменить, ответ `409 modified` — перечитайте и повторите. Из нескольких одновременных правок проходит одна.
- **Блокировка на время правки.** `tasker lock acquire|show|release <сущность> <id>` (в MCP `lock_entity`, `unlock_entity`, `get_lock`). Пока её держит другой, запись не изменить (`409 locked` с именем держателя). Срок 2 минуты, редактор продлевает её сам. Одиночным правкам она не нужна.
- **Параллельная работа.** Десктоп, демон MCP и консоль могут работать с одной папкой одновременно: номера серий уникальны, потерянных обновлений нет, файлы пишутся атомарно. Правка в консоли без `--expected-version` берёт версию на момент вызова (побеждает последняя); MCP версию требует всегда.

Ограничения: Postgres не проверялся.
