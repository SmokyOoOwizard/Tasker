# Поля задач

Кастомные поля задач (фича из нескольких частей). Реализованы **каталог** полей и перечислений проекта, **поля у типов задач** и **значения у задач** — в ядре и обоих хранилищах (`Tasker.Core.Fields`, `Tasker.Core.Tasks`: `FieldService`, `FieldEnumService`, `TaskTypeService`, `TaskService`). Доступны в **REST и MCP** (см. [«REST и MCP»](Поля-задач#rest-и-mcp) ниже) и блокировке правки (`…/fields/{id}/lock`, `…/enums/{id}/lock`, `tasker lock … field|enum`, `lock_entity`). Есть **консоль** (см. «Консоль» ниже). Есть и **фильтр по значениям полей** (см. [«Фильтр по значениям полей»](Поля-задач#фильтр-по-значениям-полей) ниже). Все выборы ядра (что делать со значениями при удалении поля из типа и значения из перечисления) передаются параметрами REST и MCP.

### Каталог

- **Поле.** `name`, `type` (`string`, `int`, `float`, `bool`, `date`, `enum`), `multiple` (несколько значений; по умолчанию одно) и, для типа `enum`, `enumId` — перечисление проекта. Имя уникально в проекте без учёта регистра и состоит **только из букв и цифр** (любого алфавита, кириллица допустима; без пробелов, `_`, `-` и знаков `= ! < > :`): имя стоит в условии фильтра (`Estimate>=3`, `Estimate:set`) и в записи значения (`Estimate=3`), и по нему условие читается однозначно. Правило действует при создании и переименовании во всех клиентах (ошибка `Field name must consist of letters and digits only …`, `400`); поле, созданное раньше правила (например, `Story points`), остаётся как есть: читается, правится без смены имени и находится фильтром по имени (если в нём нет знаков `= ! < > :`), а новое имя при переименовании проверяется. Тип enum обязан ссылаться на существующее перечисление **того же проекта**, остальные типы перечисления иметь не могут. Имя, тип, множественность и перечисление можно менять и после создания (см. [«Правка определения поля»](Поля-задач#правка-определения-поля)); обязательность и значение по умолчанию этой правкой не меняются.
- **Перечисление.** `name` и список значений в порядке отображения; у каждого значения свой `id` и `name`. Имя перечисления уникально в проекте без учёта регистра, названия значений — в перечислении (тоже без учёта регистра); хотя бы одно значение. Одно перечисление могут использовать несколько полей. Правка заменяет список значений целиком: значение с `id` остаётся тем же значением (так его переименовывают и переставляют), без `id` — новое, пропавшее — удаляется. У задач значения хранятся по `id`, поэтому переименование ничего не ломает.
- **Удаление.** Поле, которое подключено к типу или записано у задачи (значения или добавленное), удалить нельзя (`409 in_use`: «used by task type 'X'; 3 task(s)»). Перечисление, на которое ссылаются поля каталога или собственные поля задач, — тоже. Проверка и удаление идут под `IWriteScope`. Удаление проекта удаляет всё.
- **Одновременная правка.** Как у остальных сущностей: у каждой есть `version`, изменение и удаление принимают версию, которую видел клиент (`409 modified`), и учитывают блокировку на время правки (`409 locked`). Проверки уникальности имён и существования перечисления идут под `IWriteScope`, поэтому два одновременных запроса не создадут одноимённые поля.

### Правка определения поля

`FieldService.Update` меняет `name`, `type`, `multiple` и `enumId` (поля `null` не меняются; `enumId` — перечисление, на которое переходит поле: при смене типа на `enum` обязателен, поле, переставшее быть enum, его не указывает). Значения, уже выбранные у задач, преобразуются в той же операции (`FieldConversion`). Собственные поля задач (определение хранится в задаче) не затрагиваются.

- **Допустимые смены типа:** любой → `string` (значение становится текстом; у enum — названием значения); `int` → `float` (без потерь); `string` → `int`/`float`/`bool`/`date` (значение должно разбираться по правилам этого типа, `007` → `7`) и → `enum` (по названию значения без учёта регистра или явному соответствию); `enum` → другое перечисление (по названию или соответствию). Прочие смены (например `float` → `int`, `bool` → `date`) отвергаются `400`: они теряли бы значения, их делают через `string` в два шага. Значения, ставшие одинаковыми после преобразования (`07` и `7`), сливаются в одно.
- **Множественность.** Один → несколько ничего не меняет в задачах (значение — список из одного). Несколько → один: у задач с несколькими значениями нужен выбор — оставить первое или очистить.
- **Явный выбор** (`UpdateField.Choice`), нужен только если без него значения не сохранить: `ClearUnconvertible` — убрать значения, которые не разобрались в новом типе или не нашли пары в новом перечислении (остальные значения преобразуются); `Mapping` — `[{from, to}]`: явное соответствие значения старого поля (у enum — его id или название, у остальных — текст) значению нового перечисления (id или название), остальные сопоставляются по названию; `Several` — `KeepFirst` или `Clear` для «несколько → один». Без нужного выбора и при наличии затронутых задач — `409 in_use`: число задач и до пяти примеров проблемных значений; затронутых задач нет — выбор не нужен и игнорируется. Обязательное поле, оставшееся без значения после очистки, у задачи остаётся пустым (как при удалении значения перечисления); у задачи типа пустое поле просто не записывается, дополнительное — остаётся пустым.
- **Атомарность и блокировки.** Определение и значения задач меняются одной секцией записи (в БД — одна транзакция; в файлах — под общей блокировкой записи: сначала задачи, каждая по версии и с повтором, потом поле; если что-то не вышло, ту же операцию можно повторить). Версия поля (`409 modified`) проверяется до записи и ещё раз под блокировкой записи; блокировка правки поля — как всегда. Затрагиваемые задачи подчиняются общему правилу блокировок массовых правок (`TaskRewrites.ModifyAll`): сначала ждут снятия чужих блокировок, потом пишут.

### Поля у типа задачи

Тип задачи (`TaskType.Fields`) — список `{fieldId, required}` в порядке отображения: поля каталога проекта, без повторов. Такие поля **всегда есть у каждой задачи типа и у задачи не удаляются**. Список задаётся при создании типа и заменяется целиком при правке (`UpdateTaskType.Fields`; не передан — не меняется).

- **Добавили поле (в том числе обязательное) или сделали его обязательным — существующие задачи остаются как есть.** Обязательность проверяется при создании задачи и при её правке (см. ниже).
- **Убрали поле из типа** — если у задач типа есть значения этого поля, нужно явно выбрать (`UpdateTaskType.RemovedFields`, один выбор на все убираемые поля): `Clear` — убрать значения у всех задач типа; `Keep` — оставить: поле становится **дополнительным** полем каждой задачи со значением (необязательным; его можно убрать у задачи вручную). Без выбора — `409 in_use` с числом затронутых задач и названиями полей. Если значений нет ни у одной задачи, выбор не нужен. Тип и задачи при `Clear` меняются одной атомарной секцией записи (в БД — одна транзакция; в файлах — под общей блокировкой записи: сначала задачи, каждая по версии и с повтором, потом тип; если что-то не вышло, ту же операцию можно повторить). `Keep` ничего не пишет в задачи: значения уже в них. **Итог:** `TaskTypeService.Update` возвращает `CascadeResult<TaskType>` — тип и `AffectedTasks`: сколько задач затронул выбор (при `Clear` — переписано, при `Keep` — задач, у которых поле стало дополнительным; 0 — убранных полей нет или значений ни у одной задачи не было). То же число отдают REST, MCP и консоль (ниже); счётчик — это число реально переписанных задач (`TaskRewrites.ModifyAll` возвращает его).

### Значения у задачи

Задача (`TaskItem.Fields`) хранит только значения и дополнительные поля — `{fieldId, values[], own?}`; поле типа без значения в задаче не записано. Полный вид поля (с определением, источником и названиями значений enum) даёт `TaskService.GetFields` — `TaskFieldView`: `Type` (поле типа), `Extra` (дополнительное из каталога), `Own` (собственное).

- **Значения** — текст, который ядро проверяет по типу поля и приводит к каноническому виду (в нём и хранится): `int` — целое (`007` → `7`), `float` — число с точкой (`2.50` → `2.5`; `NaN` и бесконечность нельзя), `bool` — `true`/`false` в любом регистре, `date` — `yyyy-MM-dd`, `enum` — id значения перечисления или его название (хранится id), `string` — текст без пробелов по краям, не пустой и до 2000 знаков. Несколько значений — только у множественных полей; повторов нет; порядок сохраняется. Пустой список — «значения нет».
- **Дополнительные и собственные поля.** Поля типа убрать у задачи нельзя, но задаче можно добавить свои (`TaskFieldChanges` в `CreateTask`/`UpdateTask`): `AddFields` — поля каталога без значений; `Values` — значения (поле каталога, которого у задачи нет, значением добавляется как дополнительное); `NewOwnFields` — **собственные поля**, полностью определённые в самой задаче (имя, тип, обязательность, множественность, перечисление — хранятся в задаче и нигде больше; у них свой id внутри задачи); `RemoveFields` — убрать дополнительные и собственные поля. Имя собственного поля не повторяет имя другого поля задачи (без учёта регистра). Определение собственного поля не меняется: нужно другое — убрать и добавить новое.
- **Обязательность.** Обязательные поля (типа и собственные) проверяются при **создании** задачи и при **правке, которая меняет содержимое** (заголовок, описание, тип, поля): правка обязана в той же операции заполнить все пропущенные — иначе `400` со списком полей. **Перенос по доске и смена статуса** (`move_task`, `board`-перенос, правка одного только статуса) обязательность не проверяют: пропущенное поле не мешает переносу.
- **Смена типа задачи.** Поля прежнего типа, у которых есть значения, остаются дополнительными полями задачи; значение поля, общего у двух типов, сохраняется; обязательные поля нового типа без значения — ошибка со списком, значения передаются в той же правке.
- **Значение перечисления, которое убирают, а оно выбрано у задач** (`UpdateFieldEnum.Removed`): явный выбор — `Clear` (убрать значение у всех задач, которые его используют) или `ReassignTo` (id другого значения этого же перечисления, которое остаётся; у множественного поля — без дублей). Выбор один на все убираемые значения. Без выбора, если значение где-то выбрано, — `409 in_use` с числом задач. Если значение нигде не используется, выбор не нужен. Обязательное поле, оставшееся без значения после `Clear`, у задачи остаётся пустым: это не правка пользователем, обязательность не блокирует (проверит следующая правка содержимого). Атомарность — как у убранного поля типа. **Итог:** `FieldEnumService.Update` возвращает `CascadeResult<FieldEnum>` — перечисление и `AffectedTasks` (сколько задач переписано; 0 — убранных значений нет или они нигде не выбраны).
- **Одновременная правка.** Задача правится по `version` (`409 modified`) и блокировке на время правки (`409 locked`); правка полей идёт под `IWriteScope`, поэтому перечисление собственного поля и поле каталога нельзя удалить между проверкой и записью. Массовые правки задач (убрать значения у задач типа, переназначить или убрать значение перечисления) следуют общему правилу блокировок массовых правок (см. «Блокировка на время правки»): ждут снятия чужих блокировок затрагиваемых задач, потом переписывают каждую по её версии с повтором.
- **Что осталось «висеть».** Запись о поле, которого нет в каталоге (удалили в другой ветке git), `GetFields` пропускает; значения в файле не теряются.

### REST и MCP

REST — внутри проекта (`/api/projects/{projectId}/…`), права и изоляция как у остальных сущностей: недоступный или несуществующий проект — `404` на всех маршрутах, а поле, перечисление и значения чужого проекта подключить нельзя (`400`). MCP — те же операции инструментами; `projectId` и `workspace` необязательны по общим правилам (проект по умолчанию, область-аргумент), сервер с токенами агентов работает так же. Ошибки — как везде: REST `400 {error}` / `404` / `409 {error, code}` (`in_use`, `modified`, `locked`), MCP `[invalid]`, `[not_found]`, `[in_use]`, `[modified]`, `[locked]`, `[forbidden]` в начале текста. Все списки постраничные (`offset`, `limit`).

- **Каталог.** REST: `GET/POST /fields`, `GET/PATCH/DELETE /fields/{id}`, `GET/POST /enums`, `GET/PATCH/DELETE /enums/{id}`; тела — `{name, type, multiple?, enumId?}` для поля и `{name, values: [названия]}` для перечисления; `PATCH` поля — `{version, name?, type?, multiple?, enumId?, choice?: {clearUnconvertible?, several?: "keepFirst"|"clear", mapping?: [{from, to}]}}` (см. [«Правка определения поля»](Поля-задач#правка-определения-поля); без нужного выбора при затронутых задачах — `409 in_use` с числом задач; MCP `update_field` — те же параметры: `type`, `multiple`, `enumId`, `clearUnconvertible`, `several`, `mapping`); `DELETE` — `?version=`. MCP: `list_fields`, `get_field` (по id или имени), `create_field`, `update_field`, `delete_field`, `list_enums`, `get_enum` (по id или имени), `create_enum`, `update_enum`, `delete_enum`.
- **Перечисление: правка значений.** `PATCH /enums/{id}` с `values: [{id?, name}]` (значение с `id` остаётся тем же, без `id` — новое, пропавшее — удаляется). Если убираемое значение выбрано у задач, нужен выбор: в REST — `removed: {"clear": true}` (убрать у задач) или `removed: {"reassignTo": "<id оставшегося значения>"}` (переназначить); в MCP — `removedValues: "clear"` или `removedValues: "reassign"` вместе с `reassignTo`. Без выбора — `409 in_use` / `[in_use]` с числом задач; неполный или противоречивый (`reassign` без `reassignTo`, `clear` вместе с `reassignTo`) — `400` / `[invalid]`. Успешный ответ — то же перечисление (`id`, `name`, `values`, `version`…) и ещё `affectedTasks` — число задач, переписанных выбором (0, если значения нигде не были выбраны; старые клиенты лишнего поля не замечают) и, если значение входило в условия колонок досок, `affectedColumns` (выбор «убрать» снимает условие с колонки, «переназначить» подставляет другое значение; без выбора — `in_use` и с колонками). В MCP `update_enum` возвращает то же.
- **Поля типа задачи.** В `POST/PATCH /task-types` (MCP: `create_task_type`/`update_task_type`) — `fields: [{fieldId, required}]`; при правке список заменяет прежний целиком. Убрали поле, у задач которого есть значения, — нужен выбор: REST `removedFields: "clear" | "keep"`, MCP — параметр `removedFields` с теми же значениями; без выбора — `409 in_use` / `[in_use]` с числом задач и названиями полей. Тип в ответе содержит `fields` и `affectedTasks` — число затронутых задач (при `clear` — у скольких убраны значения, при `keep` — у скольких поле стало дополнительным; 0 — убранных полей нет или значений не было). То же в результате MCP `update_task_type`.
- **Значения и собственные поля в задаче.** В `POST/PATCH /tasks` (MCP: `create_task`/`update_task`) — `fields: {values?, addFields?, newOwnFields?, removeFields?}`: `values` — `[{fieldId, values: ["текст"]}]` (пустой список убирает значения; enum — id значения или название), `addFields` — `[fieldId]`, `newOwnFields` — `[{name, type, values?, required?, multiple?, enumId?}]`, `removeFields` — `[fieldId]` (только дополнительные и собственные). Обязательные поля проверяются при создании и правке содержимого (заголовок, описание, тип, поля), но не при смене статуса и переносе по доске.
- **Вид полей задачи.** `GET /tasks/{id}`, `POST`/`PATCH /tasks` и `get_task`/`create_task`/`update_task` отвечают задачей с дополнительным `fieldViews` (вычисляет `TaskService.GetFields`): `[{fieldId, name, type, multiple, enumId, required, source: "type"|"extra"|"own", values, texts}]` — `values` у enum это id значений, `texts` — их названия. `fields` в ответе — только записанные значения (как они хранятся). В списках задач `fieldViews` нет (для каждой задачи это чтение каталога): нужен вид — читайте задачу.

### Консоль

Работает напрямую через ядро (см. [«Консоль (Tasker.Cli)»](Консоль)), `--json` — те же сущности, что в API ядра.

- **Каталог.** `tasker field create <имя> --type string|int|float|bool|date|enum [--multiple] [--enum <перечисление>]`, `field list | get | delete`; `tasker enum create <имя> --value A B C`, `enum list | get | delete`.
- **Правка поля.** `field update <поле> [--name …] [--type …] [--multiple | --single] [--enum <перечисление>]` — значения у задач преобразуются (см. [«Правка определения поля»](Поля-задач#правка-определения-поля)). Выбор при затронутых задачах: `--clear-unconvertible` (убрать значения, которые не подошли), `--map Старое=Новое`… (соответствие значений для нового перечисления, остальные — по названию), `--several keep-first|clear` (при `--single`, у задач несколько значений); без нужного выбора — `In use: …` с числом задач, примерами и подсказкой.
- **Значения перечисления.** `enum update <имя> [--name …] [--add-value X]… [--remove-value X]… [--rename-value Старое=Новое]…` или `--values A B C` (список и порядок целиком; значение с тем же названием остаётся тем же значением). Убираемое значение, выбранное у задач, — только с выбором: `--drop` (убрать у задач) или `--replace-with <значение>` (переназначить на значение, которое остаётся; id или название); без выбора — `In use: …` с числом задач и подсказкой. После выбора вторая строка называет итог: `Removed 'P1' from 12 tasks` / `Reassigned 'P1' → 'P2' in 12 tasks` (`0 tasks`, если значение нигде не выбрано); в `--json` — перечисление и `affectedTasks`.
- **Поля типа.** `task-type create <имя> --status-set … --field Имя[:required]…`; `task-type update <тип> --field Имя[:required]…` (список целиком), либо `--add-field Имя[:required]` (добавить или сменить обязательность) и `--remove-field Имя`. Убираемое поле со значениями у задач — только с `--drop-values` (убрать значения) или `--keep-values` (оставить: поле становится дополнительным у задач); без выбора — `In use: …` с числом задач. После выбора вторая строка называет итог: `Removed 'Note' from 12 tasks` / `Kept 'Note' as an extra field in 7 tasks`; в `--json` — тип и `affectedTasks`. `task-type get` показывает поля.
- **Значения у задачи.** `task create | update … --field Имя=значение` (поле типа, дополнительное или собственное поле задачи, либо поле каталога — оно добавляется задаче как дополнительное); для поля с несколькими значениями параметр повторяют (`--field Labels=ui --field Labels=crash`), новые значения заменяют прежние, `--field Имя=` убирает их. `int`, `float` (с точкой), `bool` (`true`/`false`), `date` (`yyyy-MM-dd`), `enum` — название или id значения. `--add-field Имя` добавляет задаче поле каталога без значения, `--remove-field Имя` (только `update`) убирает дополнительное или собственное поле; поля типа убрать нельзя. Обязательные поля проверяются при создании и правке содержимого (заголовок, описание, поля, тип), но не при смене статуса; ошибка называет поле и подсказывает `--field`.
- **Собственные поля задачи.** `--custom-field Имя:тип[:required][:multiple][:enum=Перечисление][=значение]`: `Estimate:int=5`, `Tags:string:multiple=a`, `Risk:enum:required:enum=Priority=High`. Значение — всё после первого `=` вне `enum=…` (в нём можно `:` и `=`); имя и перечисление без `:` и `=`. Повтор того же определения собирает значения нескольких (`--custom-field Tags:string:multiple=a --custom-field Tags:string:multiple=b`); то же имя с другим определением — ошибка.
- **Вывод.** `task get` показывает блок `fields:` рядом со связями, по строке на поле: `Priority (enum, required): High`; в скобках тип (`[]` — несколько значений), `required`, и `extra` (дополнительное из каталога) или `own` (собственное); нет значения — `-`. В `--json` к задаче добавляется `fieldViews` (определение, источник, значения и `texts` — названия значений enum).
- Блокировки: `tasker lock acquire|release|show field|enum <имя>`.

### Фильтр по значениям полей

- **Синтаксис.** Условие — строка `Имя<оператор>значение` или `Имя:слово`; имя — поле каталога или собственное поле задач (без учёта регистра), оно стоит до первого из знаков `= ! < > :` (в именах их нет). Операторы: `=`, `!=`, `>`, `>=`, `<`, `<=`; значение разбирается после знака целиком (`Note=x:y` — значение `x:y`, `Note=a=b` — `a=b`) и приводится к каноническому виду, как при записи: `Estimate=003` найдёт `3`, `Level=high` — значение enum `High` (id тоже годится), `Ratio=0.50` — `0.5`. Повтор условий — **И**; диапазона `3..8` нет — это два условия: `Estimate>=3` и `Estimate<=8`. Неверное имя, неподходящий оператор, значение не того типа, неизвестное значение enum, пустое значение, условие без знака — `400` (`Field filter …`).
- **Типы.** `=` и `!=` — для всех типов. `>`, `>=`, `<`, `<=` — только для **int, float и date** (`Estimate>=3`, `Ratio<0.5`, `Due<2026-12-01`); у string, enum и bool — ошибка `'>' does not apply to field 'Level' of type enum (only int, float and date can be compared; use = or !=)`. Числа сравниваются как числа (10 больше 3), даты — по каноническому тексту `yyyy-MM-dd` (он сортируется как текст). Значение сравнения — того же типа, что поле (для int — целое: `Estimate>2.5` — ошибка).
- **Семантика.** У поля с несколькими значениями `=`, `>`, `>=`, `<`, `<=` — «**хотя бы одно** значение подходит» (`Tags=ui Tags=api` — есть оба; `Scores<2 Scores>15` могут выполнить разные значения). **`!=` — «ни одно значение не равно X»**: подходят и задачи без значения поля (в том числе когда поле к ней не подключено); `=` и `!=` — дополнения, вместе дают все задачи. Строки сравниваются точно (с регистром). Для `=`, `>`… задача без значения не подходит.
- **Наличие и подключение.** Слово после `:` (регистр не важен; двоеточия в именах нет, поэтому запись однозначна, кавычки не нужны): `Имя:set` — у поля есть хотя бы одно значение; `Имя:unset` — значения нет (в том числе поле задаче не подключено); `Имя:attached` — поле **подключено** к задаче: входит в её тип или добавлено ей как дополнительное, даже без значения; `Имя:detached` — не подключено. «Подключено, но не заполнено» — два условия: `Имя:attached` и `Имя:unset`. Поле типа без значения в задаче не хранится, поэтому «подключено» вычисляется: `TaskService.ParseFieldFilters` находит типы проекта, в которых есть поле (`FieldCondition.TypeIds`), а хранилище добавляет к ним задачи с записью о поле (`task_fields`). Типы разбираются при каждом запросе, поэтому смена типа задачи, добавление поля типу и его удаление из типа (со значениями или без) учитываются сразу, без перестройки данных.
- **Область: каталог и собственные поля.** Один синтаксис ищет и по **полям каталога** (полям типа и дополнительным), и по **собственным полям задач** (определение хранится в самой задаче, id у каждой задачи свой, имена одноимённых полей разных задач — разные сущности, типы могут различаться). Имя собственного поля — тоже только из букв и цифр. Как читается имя (`TaskService.ParseFieldFilters`): если поле с таким именем есть в **каталоге** — значение разбирается по его типу, и условию подходят также собственные поля с этим именем и **тем же типом**; собственные поля с тем же именем, но другим типом пропускаются (`Estimate=3` с полем каталога int не найдёт собственное string `Estimate`=`3`). Если в каталоге поля нет, а у задач проекта есть собственные поля с таким именем — при **одном типе** значение разбирается по нему; при **нескольких** (например, int и string) — ошибка `Field filter …: tasks have own fields 'Code' of several types (int, string) and the catalog has no such field …` (указать тип в условии пока нельзя); у enum «тип» — перечисление (`enum 'Levels'`). Нет ни там, ни там — `no field 'X' in the project's catalog and no task has an own field with this name`. Операторы и предикаты те же; `Имя:attached` для собственного поля — «у задачи есть собственное поле с этим именем (и типом)», то есть вместе с `:unset` находит собственные поля без значения. Собственные поля со старыми именами (до правила «буквы и цифры»), не годящимися для условия, фильтром не находятся.
- **Где.** Консоль: `task list --field Имя=значение` (повтор или несколько значений после одного `--field`); условия с `<` и `>` в оболочке пишут в кавычках: `--field "Estimate>=3"` (`!=` лучше в одинарных, иначе оболочка может раскрыть `!`: `--field 'Level!=Low'`); в PowerShell — везде одинарные: `--field 'Estimate>=3'` (без кавычек `>` — перенаправление в файл `=3`), в cmd.exe — только двойные (подробнее — [«Windows: консоль»](Консоль#windows-консоль-tsk-119)); `Имя:set` кавычек не требует. REST: `GET /tasks?field=Estimate%3E%3D3` (параметр можно повторять; знаки кодируются как обычно, кавычек нет). MCP: `list_tasks` с `field: ["Estimate>=3", "Level!=Low", "Due:set"]`. Всё это страницы с `totalCount` (`TaskService.List` → `ITaskStorage.GetRange(filter, page)`; из текста условия строит `TaskFilter.FieldValues` — список `FieldCondition` (имя и тип поля, `FieldOperator`, значение, число, id поля каталога — если оно есть, типы задач) — `TaskService.ParseFieldFilters`).
- **Хранилища.** Значения лежат текстом (и поля каталога, и собственные поля — в одних таблицах значений, строки собственных полей записываются вместе с задачей в той же транзакции); для сравнений int и float у каждого значения есть **числовой столбец** `number` (`double`, `FieldNumbers.Parse`; `null`, если значение не число), а индекс идёт по `(field_id, number)` (БД: `FieldId, Number`) и по `(field_id, value)`. Собственное поле у каждой задачи с новым id, поэтому у его строк (и у строк `task_fields`) есть колонки **`own_name`** (имя в нижнем регистре, `FieldNames.Key`) и **`own_type`** (тип; БД: `OwnKey`, `OwnType`), а индексы идут ещё по `(own_name, value)` и `(own_name, number)`; строка подходит условию, если это поле каталога (`field_id`) или собственное поле с тем же именем и типом. `ITaskStorage.GetOwnFieldKinds` отдаёт различные пары «тип, перечисление» собственных полей с этим именем — для разбора условия, когда в каталоге поля нет. Схема индекса файлового хранилища — 8. Файловое хранилище ищет по таблице `task_field_values` индекса SQLite (схема индекса 8 — старый индекс пересобирается сам; запрос — подзапросы `path IN (SELECT path …)` и их отрицания для `!=` и `:unset`), БД — подзапросами к `task_field_values` (EF Core; сравнение date — по тексту, в БД это столбец `Value`). Равенство float — по каноническому тексту, как и раньше; сравнения — по `double`: у int больше 2^53 (9 007 199 254 740 992) последние разряды при сравнении `>`/`<` теряются (равенство остаётся точным).
- **Колонки доски.** Колонка = статусы **И** условия по полям (TSK-85): задача попадает в неё сама, когда у неё подходящий статус и выполнены все условия, перенос не нужен — правка поля задачи переносит её в другую колонку. Условия — те же, что у `task list --field` (`=`, `!=`, `>`, `>=`, `<`, `<=`, `:set`, `:unset`, `:attached`, `:detached`; один разбор — `TaskService.ParseFieldFilters`), пишутся по **именам** полей каталога, а хранятся по **id**: поля и значения enum (`ColumnFieldFilter {FieldId, Operator, Value}`, значение — каноническая запись, у enum — id значения), поэтому переименование поля или значения колонку не ломает. То, что считается при разборе (число для сравнений, типы задач для `:attached`/`:detached`), считается заново при каждом чтении колонки. Условие просмотра (`?field=`, `board tasks … --field`, `board show … --field`, `get_board field`) по-прежнему не хранится и **добавляется** к условиям колонки по И: `BoardService.GetColumnTasks` собирает фильтр колонки (типы доски, статусы, условия колонки), а `TaskService.List` дописывает к нему условия просмотра.
  - **Один статус в нескольких колонках.** Раньше статус мог быть только в одной колонке. Теперь — в нескольких, если у каждой пары таких колонок есть пара условий по одному полю, которые вместе не выполняются (`BoardService` → `ColumnFilters.AreExclusive`): `Level=High` и `Level=Low` (поле с одним значением), `Level=High` и `Level!=High`, `:set` и `:unset`, `:attached` и `:detached`, `Estimate>=3` и `Estimate<3` (отрезки значений int, float, date не пересекаются), `Estimate=5` и `Estimate:unset`. У поля с **несколькими** значениями два условия «=» разными значениями могут выполниться вместе, поэтому исключающими считаются только пары, верные при любом наборе значений (`=` и `!=` с одним значением, наличие и отсутствие). Проверка осторожная: пересечение, которое не доказано, считается пересечением и доска не принимается. Правка колонок, сохранённая из любого клиента, проверяется целиком, поэтому доска всегда корректна.
  - **Хранение.** Файл доски: `fieldFilters` у колонки (формат 6) — `[{field: <id>, op: greaterOrEqual, value: "3"}]` (оператор словом; у `set`, `unset`, `attached`, `detached` значения нет), только у колонок с условиями; старый файл (формат ≤ 5) читается без условий и переписывается `tasker migrate`. БД: таблица `board_column_field_filters` (`ColumnId`, `Position`, `FieldId`, `Operator`, `Value`; удаляется вместе с колонкой, внешний ключ на поле без каскада — поле, которое использует колонка, не удалить). В уже созданной БД таблицы нет, поэтому её нужно пересоздать (схему создаёт `EnsureCreated`, как и для остальных новых таблиц).
  - **Ввод.** REST/MCP — `fieldFilters` строками у колонки, консоль — `--column-filter "Колонка:условие"` (название колонки до первого `:`, которым оно заканчивается в списке `--column` — в названии колонки двоеточие допустимо; повтор — И; `"Колонка:"` — убрать условия). Выбор синтаксиса: условия остаются теми же строками, что и `--field`, поэтому им не нужно учиться заново, а привязка к колонке — по названию, как в `--column`. Не переданные условия существующей колонки (с `id` в REST/MCP, с тем же названием в консоли) сохраняются: правка статусов не стирает условия.
  - **Каскады.** Поле, на которое есть условие колонки, не удаляется (`409 in_use`: `board 'Main' (column 'Critical')`) и не меняет тип, перечисление и множественность; переименование можно. Значение enum, которое входит в условие колонки, — как у задач (TSK-73) только с выбором: `removed: {clear: true}` / `--drop` — условие на это значение **убирается из колонки** (остальные условия остаются), `removed: {reassignTo}` / `--replace-with` — условие получает другое значение; без выбора — `409 in_use` с колонками. Если правка сделала бы так, что колонки с общим статусом пересекаются (убрали условие у обеих половин пары «Level=High»/«Level!=High»), — `409` без записи, условия нужно поправить на доске. Ответ перечисления получает `affectedColumns` (только если не 0), консоль — «… and N board column condition(s)». Доска, которую сейчас правит другой (блокировка), ждёт освобождения, как и затрагиваемые задачи (`Locked`, если не дождались).
  - **Перенос задачи** (`move_task`, `POST …/move`). Статус задаётся правилом переноса, а поля перенос не меняет, поэтому задача, не подходящая под условия колонки по полям, **не переносится**: `400` «Task … does not match the field conditions of column … (Поле=значение, …): change the task's fields first». Предупреждение вместо отказа оставило бы задачу, которая после переноса исчезает с доски, — отказ честнее. Подходящая задача получает статус из правила и сразу видна в колонке.
  - **Вывод.** `board get` — условия колонки текстом (`; where Level=High and Estimate>=3`, поля и значения по названиям); `board show` — в заголовке колонки в `[…]` и `fieldFilters` в `--json`; `get_board` — `fieldFilters` у колонки. Интерфейс (доски пока только читаются) знает поле `fieldConditions` и отмечает колонки с условиями.
- **Автодополнение и справочник.** `--column-filter` подсказывает названия колонок (с `:`), затем условие как `--field`; `--column` после `=` и `,` — статусы. `--field` подсказывает имена полей (с `=`), после `=` и `!=` — значения enum и `true`/`false`, после `:` — слова наличия; у сравнений значений нет. `tasker manual fields` описывает операторы и примеры (команды из примеров проверяет тест справочника).

### Хранение

- **Файлы.** `fields/<название>-<id8>.yaml` и `enums/<название>-<id8>.yaml` — как у остальных сущностей. У типа (`task-types/<название>-<id8>.yaml`) — `fields: [{field, required}]` (`required` — только у обязательных). У задачи (`tasks/…`) — `fields: [{id, values, name?, type?, enum?, required?, multiple?}]`: `id` — поле каталога, а при наличии `name` — собственное поле задачи с полным определением (`required` и `multiple` — только если `true`), `id` тогда — его id внутри задачи. Значения — всегда строки в каноническом виде, строки вроде `null`, `true`, `007` пишутся в кавычках. Списки есть, только если не пусты. Формат файлов — версия 5. В индексе папки (`SchemaVersion` 9, пересобирается сам) — таблица `task_fields` (`path`, `project_id`, `field_id`, `enum_id`): по ней находятся задачи, у которых записано поле или есть собственное поле с перечислением (`TaskFilter.FieldIds`/`EnumIds`, `ITaskStorage.GetAll`), и таблица `task_field_values` (`path`, `project_id`, `field_id`, `value`, `number` — значение числом для сравнений int и float; индексы по `field_id, value` и `field_id, number`): по ней работает фильтр по полям (`TaskFilter.FieldValues`). Строки обеих таблиц заменяются вместе с файлом задачи в одной транзакции.
- **БД.** Таблицы `fields`, `field_enums`, `field_enum_values`, `task_type_fields` (поле типа; внешний ключ на поле без каскада — подключённое поле удалить нельзя), `task_fields` (поле задачи: собственное определение в `Own*` столбцах; внешний ключ на перечисление собственного поля без каскада), `task_field_values` (значения по порядку; столбец `Number` — значение числом для сравнений int и float; индексы по `FieldId, Value` и `FieldId, Number` — для фильтра по полям; в уже созданной БД столбца `Number` нет, поэтому её нужно пересоздать). Поля и значения удаляются вместе с типом и задачей. На поле каталога у `task_fields` внешнего ключа нет (столбец общий с собственными полями): «используется ли поле» проверяет сервис под `IWriteScope` (транзакция). **Миграций БД нет: в уже созданной БД новых таблиц нет — её нужно пересоздать.**
