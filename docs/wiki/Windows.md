# Windows

Минимальная версия: Windows 10 версии 1809 (октябрь 2018) и новее, Windows PowerShell 5.1 или PowerShell 7. Права администратора и установленный .NET не нужны.

**Установка.** Скрипт `install.ps1` ставит утилиту `tasker` и демон MCP в `%LOCALAPPDATA%\Programs\Tasker`, добавляет их в PATH пользователя, включает автозапуск демона (задача Планировщика заданий для текущего пользователя) и автодополнение PowerShell. Подробности: [Установка](Установка).

**Что проверено.** Код для Windows написан и собирается (`dotnet build -r win-x64`), чистая логика (имена файлов, XML задачи Планировщика, квотирование, скрипт автодополнения) покрыта тестами на macOS и Linux. Запуск на самой Windows пока не проверялся: для каждой части есть пошаговый чек-лист «ПРОВЕРИТЬ НА WINDOWS» в описании соответствующей задачи (TSK-116, 117, 118, 119, 120 в проекте Tasker). До их прохождения считайте поддержку Windows экспериментальной.

**Главное отличие от macOS и Linux:** бесшовное обновление демона (супервизор с общим слушающим сокетом) на Windows выключено по умолчанию, пока чек-лист не пройден; включается переменной `TASKER_MCP_SUPERVISOR=1`. Без неё `tasker mcp upgrade` на Windows перезапускает демон.

## Демон на Windows: как устроено

Windows поддерживается наравне с macOS и Linux, но **проверить его на этой машине разработки нельзя** (macOS, CI ещё нет, TSK-115): всё, что не вызывает ОС (командная строка, блок окружения, имя события, выбор режима, описание сокета, раскладка структур Win32, весь обмен «сокет в сообщении `hello`»), покрыто тестами на macOS и Linux, а вызовы Windows изолированы и ждут чек-листа ниже. Поэтому **супервизор на Windows по умолчанию выключен**: `tasker-mcpd` работает одним процессом, как раньше, а `tasker mcp upgrade` ведёт себя как перезапуск. Включить бесшовный режим: переменная `TASKER_MCP_SUPERVISOR=1` (в окружении `tasker mcp start`; `1`, `true`, `yes`, `on`) или `tasker-mcpd --supervised`; `--single` сильнее. Когда чек-лист пройден людьми на Windows, умолчание можно поменять в `DaemonPlatform.UseSupervisor`.

- **Слушающий сокет между процессами.** `Process.Start` в .NET не умеет передавать дескриптор, поэтому супервизор *дублирует* сокет в рабочий процесс: запускает его, берёт его номер, вызывает `WSADuplicateSocketW` и отправляет получившееся описание (628 байт, `wsa:<base64>`) в сообщении `hello`; рабочий процесс собирает из него свой дескриптор того же сокета (`WSASocketW`) и отдаёт Kestrel (`ListenHandle`). Очередь соединений у двух дескрипторов общая, поэтому затвор приёма и замена на лету — те же, что на Unix. Исходный сокет супервизор не закрывает (`Socket.DuplicateAndClose` закрыл бы его и оставил следующий рабочий процесс без сокета). Код: `ListenerHandoff`, `WindowsSockets` (единственное место с вызовами WinSock). На Unix тот же путь можно включить `TASKER_MCP_HANDOFF=message` (сообщение `fd:<номер>`): так на macOS и Linux проверяется всё, кроме двух вызовов WinSock. Порт на Windows занимается исключительно (`ExclusiveAddressUse`): `SO_REUSEADDR` там, в отличие от Unix, разрешил бы второй программе занять тот же порт.
- **Остановка без сигналов.** `tasker mcp stop` сначала шлёт запрос `/daemon/stop` (драйн как на Unix), а если демон не принял запрос — взводит именованное событие `Local\tasker-mcp-stop-<хэш каталога данных>`, которое слушает супервизор (или одиночный демон). Супервизор останавливает рабочие процессы сообщением `stop` по каналу и ждёт до 20 с; `Process.Kill` (вместе с деревом процессов) — только когда ничего не помогло, и только процессу, у которого номер **и время старта** совпали с `daemon.json` (номер мог достаться другой программе). `tasker mcp run` по Ctrl+C и Ctrl+Break передаёт остановку тем же событием. Событие живёт в пространстве имён сеанса: из другого сеанса остаётся запрос по HTTP.
- **Фон без окна.** `tasker mcp start` запускает `tasker-mcpd --detached` через `CreateProcessW` с `CREATE_NO_WINDOW | CREATE_NEW_PROCESS_GROUP` (и `CREATE_BREAKAWAY_FROM_JOB`, если задание родителя это разрешает) и без унаследованных дескрипторов: закрытие консоли и Ctrl+C демона не задевают, а канал вывода вызвавшей программы (`$x = tasker mcp start`) не держится открытым. Рабочие процессы супервизора помещаются в объект «задание» с `KILL_ON_JOB_CLOSE`: убит супервизор — они уходят вместе с ним (на Unix их уводит закрытие канала). Обмен супервизора с рабочим процессом — всегда UTF-8 (кодовая страница консоли испортила бы пути с кириллицей).
- **`mcp/daemon.lock`** — файл, открытый с `FileShare.None`, как и на Unix: занят — демон работает, умер процесс — Windows снимает блокировку сама; десктоп уступает порт, видя блокировку (TSK-51).
- **Брандмауэр.** Демон слушает только `127.0.0.1`: запроса Защитника Windows (Windows Defender Firewall) быть не должно; если он появился — это ошибка, сообщите.
- **Повтор управляющих запросов и `/ready`** — общие для всех систем (`DaemonClient.Retrying`: оборванное соединение повторяется один раз через 0,3 с).
- **Альтернативы.** Общий порт через `SO_REUSEADDR` на Windows не годится (захват порта). HTTP-прокси на localhost между клиентами и рабочими процессами — лишний процесс и лишний переход на каждый вызов. Короткое окно переключения с повтором на клиенте — запасной вариант, если дублирование сокета на Windows окажется хрупким (тогда: режим `--single`, как сейчас по умолчанию).

### ПРОВЕРИТЬ НА WINDOWS

Чек-лист в PowerShell (после сборки или установки; свой `TASKER_HOME`, чтобы не трогать настоящие данные):

```powershell
$env:TASKER_HOME = "$env:TEMP\tasker-check"; $env:TASKER_MCP_SUPERVISOR = "1"
mkdir $env:TEMP\ws1; tasker project create Demo -w $env:TEMP\ws1
tasker mcp port 5799; tasker mcp workspace add $env:TEMP\ws1
```

1. `tasker mcp start`: команда возвращается сразу, окно не появилось, запрос брандмауэра не появился; `tasker mcp status` показывает один рабочий процесс (супервизор работает).
2. `Invoke-RestMethod http://127.0.0.1:5799/health` отвечает; `(Invoke-WebRequest http://127.0.0.1:5799/ready).StatusCode` — 200. `netstat -ano | findstr :5799` — LISTENING только на `127.0.0.1`; `Get-Process tasker-mcpd` — два процесса (супервизор и рабочий).
3. `tasker mcp upgrade` дважды подряд: оба раза «replaced without downtime», `tasker mcp status` — другой pid рабочего процесса, pid демона тот же; `netstat` по-прежнему показывает один слушающий сокет.
4. Под нагрузкой: `dotnet run --project tools/Tasker.Stress -- --scenarios upgrade`: все проверки сценария «ok», ни одного отказанного вызова.
5. Запустить `tasker mcp start` из отдельного окна PowerShell и закрыть это окно: демон жив (`tasker mcp status` из другого окна).
6. `$out = tasker mcp start` в PowerShell не зависает (канал вывода не держится).
7. `Stop-Process -Id <pid супервизора из status> -Force`: рабочий процесс тоже исчез за секунду; `tasker mcp start` поднимается снова без ручной чистки.
8. `tasker mcp stop`: возвращается за секунды, `Get-Process tasker-mcpd` пусто, `mcp\daemon.json` удалён; журнал `mcp-*.log` содержит `Stopping the MCP server`, а не `killed`.
9. `tasker mcp run` в окне, Ctrl+C: демон останавливается штатно, `daemon.json` удалён; повторить с Ctrl+Break.
10. Порт занят чужой программой (`$l = [Net.Sockets.TcpListener]::new('127.0.0.1',5799); $l.Start()`): `tasker mcp start` отвечает «Port 5799 is busy» через ~5 с и порт не перехватывает.
11. Без `TASKER_MCP_SUPERVISOR`: `tasker mcp start` работает одним процессом (в `status` нет рабочих процессов), `tasker mcp upgrade` перезапускает демон и говорит об этом.
12. Тесты: `dotnet test tests/Tasker.Tests --filter "FullyQualifiedName~Daemon"` — проходят `DaemonWindowsTests.Windows_*` (на других системах они `Skipped`) и `DaemonUpgradeTests`.
