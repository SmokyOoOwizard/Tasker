# Консоль tasker

Команда `tasker` работает с рабочей областью напрямую, как вкладка десктопа: папкой (`<папка>/.tasker`) или файлом SQLite. Приложение запускать не нужно, а если оно (или демон MCP) работает с той же папкой — не мешает: блокировки короткие (см. «Несколько процессов на папку»). Пользователи, как на десктопе, — только имена, права не проверяются.

```bash
dotnet run --project src/Tasker.Cli -- <команда>
```

Общие параметры (можно ставить где угодно): `-w/--workspace <папка>` (по умолчанию текущая), `--sqlite <файл>` вместо папки, `-p/--project <id или имя>` (или переменная `TASKER_PROJECT`; если в рабочей области ровно один проект, параметр не нужен — команда работает с ним, а при нескольких проектах или без них — ошибка с подсказкой), `--json` — результат JSON, как в API. Сущности в параметрах указываются по id или имени; вместо полного id годится короткий (см. «Короткий id» ниже). Ошибка — сообщение в stderr и код 1.

| `<сущность> delete <id или имя>` | удалить |

**Справочник `tasker manual`.** Короткие рецепты с готовыми командами — `tasker manual` (список тем), `tasker manual <тема>`, `tasker manual <слово>` (поиск по названиям и описаниям, затем по тексту; одна находка — страница, несколько — список). Тексты здесь не дублируются: источник правды — страницы `src/Tasker.Cli/Manual/<язык>/NN-<тема>.md`, они встроены в сборку (EmbeddedResource `manual/<язык>/…`). Страница — заголовок `# …`, короткое описание и разделы; код в блоках ```` ```bash ````, пример вывода — ```` ```text ````. Тест разбирает каждую команду `tasker …` из блоков `bash` деревом команд, так что переименование команды или параметра, не отражённое в справочнике, ломает сборку. Язык — `--lang` или переменная `TASKER_LANG`, по умолчанию `ru`; чтобы добавить язык, достаточно положить страницы в новую папку (языки определяются по найденным ресурсам), темы без перевода показываются по-русски с пометкой. `--json` — список тем или тема (`content` — Markdown). Рабочая область команде не нужна.

Сущности в `get`/`update`/`delete` — те же: `project`, `status`, `status-set`, `task-type`, `link-type`, `field`, `enum`, `board`, `task`, `user`, `agent`. Задача указывается только по id (названия повторяются): найти его можно через `task list` (в строке списка у задач без серии вместо ссылки короткий id; у остальных — ссылка `ПРЕФИКС-номер`; и то и другое принимают `get`/`update`/`delete`). Параметры `update` — те же, что у `create`, но необязательные; `--status`, `--status-set` и `--column` заменяют список целиком (колонка с именем существующей остаётся той же колонкой), `-d ""` очищает описание задачи. `project delete` удаляет проект со всем содержимым, поэтому сначала показывает, что пропадёт, и спрашивает подтверждение:

```
Project 'Demo' will be deleted with everything in it: 42 tasks, 3 boards, 5 statuses, 2 status sets, 3 task types, 1 series, 5 link types. This cannot be undone.
Delete project 'Demo'? [y/N]
```

`y`/`yes` (в любом регистре) удаляет; любой другой ответ, пустой ввод и конец ввода — `Cancelled, nothing was deleted` и код 1, ничего не удаляется. Нулевые количества в сводке пропускаются. `--yes` удаляет без вопроса (скрипты). Если ввод перенаправлен (CI, конвейер) и `--yes` не указан, команда не ждёт ответа, а сразу падает с той же сводкой и подсказкой `Repeat with --yes to confirm`. С `--json` сводка и вопрос идут в stderr, stdout остаётся для JSON-результата. В MCP инструмента удаления проекта нет намеренно: агент не должен удалять проекты. Занятая сущность (статус в наборе или у задач, тип с задачами) не удаляется: `In use: …`.

Версии (защита от одновременной правки) CLI берёт сам — текущую на момент команды. Чтобы изменить или удалить, только если сущность не менялась с момента `get`, передайте её `version` в `--expected-version`: иначе `Modified by someone else: …`.

**Короткий id.** В списках консоли (`task list`, `task links`, `board tasks`, `board show`, блок `links` в `task get`, `project|status|status-set|task-type|series|board|link-type|field|enum|user|agent list`) первая колонка — короткий id: первые 8 символов Guid (`3f9a1c2e`; тот же суффикс в имени файла `<название>-3f9a1c2e.yaml`, так что файл находится по строке списка). Он показывается там, где у сущности нет ссылки серии (у задачи с серией — `TSK-12`), поэтому колонка узкая и не раздувается из-за Guid. Полный id остаётся в `--json` и в поле `id` команды `get`. Правила разбора ссылки на сущность в командах (`Refs`): полный Guid, затем точное имя (без учёта регистра; у задач — ссылка серии), затем префикс Guid из **8 и более** шестнадцатеричных символов без дефисов, регистр не важен. Имя сильнее префикса: сущность, названная 8 hex-символами, находится по имени. Префикс короче 8 символов не принимается, подходящий нескольким сущностям — ошибка `Several …s start with '…', use a longer prefix or the full id: <полные id>`. Поиск по префиксу: у задач — `ITaskStorage.FindByIdPrefix` (файлы — по колонке `id` индекса, `id LIKE 'xxxxxxxx%'`; БД — `LIKE` по тексту Guid), у остальных сущностей — по уже загруженному списку проекта. MCP: инструменты по задачам (`get_task`, `update_task`, `delete_task`, `get_task_links`, `link_tasks`, `unlink_tasks`, `add_task_to_series`, `remove_task_from_series`, `renumber_task`, `move_task`) принимают в `taskId`/`otherTaskId` и короткий id (агент берёт его из вывода консоли), `find_tasks_by_reference` — и префикс id; неоднозначный префикс — `[invalid]` со списком полных id, нет такой задачи — `[not_found]`. REST принимает только полный id. Автодополнение id не подсказывает: ссылки на сущности — по имени, на задачи — `ПРЕФИКС-номер`.

Все `list` постраничные: `--offset` и `--limit`. **Первая строка текстового списка консоли — сколько найдено (TSK-107)**, в stdout, до строк данных: `Found 3` (показано всё), `Found 106, shown 1-2 (use --offset/--limit)` (страница; число — `totalCount` после фильтров), `Found 0` (пусто); у списка деревом (`task list`, TSK-109) число — уникальные задачи, а страница — задачи верхнего уровня: `Found 106, shown top-level 1-20 of 57 (use --offset/--limit)` (см. [«Связи между задачами»](Связи-и-иерархия)). Строку печатает общий форматировщик `Context.Print(ListDto…)` (для списков без страниц — `Context.PrintAll`; строка собирается в `Context.FoundLine`), поэтому одинаково у `task list`, `task links`, `board tasks`, всех `… list` и `mcp workspace list`; в `board show` итога доски нет (счётчики колонок в заголовках), `task get` не затронут. Она не обрезается по ширине (TSK-106) и не входит в таблицу выравнивания (TSK-91). Глобальный `-q`/`--quiet` убирает её (тот же параметр у `sync`: молчать, если нечего сообщить); `--json` не меняется (число в `totalCount`, итоговой строки нет). В конвейерах (`tasker task list | wc -l`, `| head -1`) первая строка — итог: для скриптов `--json` или `-q`. `--all` выводит всё без ограничения по количеству (например, `tasker task list --all`); вместе с `--offset`/`--limit` — ошибка. В `--json` с `--all` ответ — одна страница, в которой `totalCount` и `limit` равны числу элементов.

### Автодополнение по Tab

`tasker pro<Tab>` дописывает `project`, `tasker task cr<Tab>` — `create`, `--st<Tab>` — `--status`; значения тоже подсказываются. Поддержаны **zsh** и **bash** (macOS ставит bash 3.2 — скрипт работает и с ним); fish и PowerShell добавляются новым скриптом без правок остального (см. ниже).

**Что подсказывается.** Команды, вложенные команды, параметры (`-w`, `-p`, `--json` и остальные). Значения — из хранилища текущей рабочей области (`-w`/`--sqlite` или текущая папка; проект — `-p`/`--project`, `TASKER_PROJECT` или единственный):

| Где | Что подсказывается |
|---|---|
| `-p/--project`, `project get\|update\|delete` | проекты |
| `status …`, `status-set …`, `task-type …`, `board …`, `link-type …`, `field …`, `enum …`, `series …` | имена сущностей (у серий — префиксы) |
| `--status`, `--status-set`, `--type`, `--series`, `--enum`, `--field Имя`, `--add-field`, `--remove-field` | статусы (у `task create --type Тип --status` — только набор этого типа), наборы статусов, типы, серии, перечисления, поля |
| `board tasks <доска> <Tab>` | колонки этой доски |
| `board create\|update --column <Tab>` | после `=` и `,` — статусы проекта: `Имя=В\ работе,<Tab>` |
| `board create\|update --column-filter <Tab>` | названия колонок из набранных `--column` (у `update` без них — колонки доски) с `:`; после него — условие по полю, как у `--field` |
| `task get\|update\|delete\|links`, `task link <Tab>`, `series add-task`, `lock … task` | ссылки задач: `TSK-7<Tab>` → `TSK-7`, `TSK-70`, `TSK-71`…; фраза связи в `task link` — типы и названия сторон (`blocks`, `is blocked by`) |
| `--field Имя=<Tab>` (`task`, `board`) | значения поля: перечисления, у логического — `true`/`false`; `--field Имя:<Tab>` у `task-type` — `required` |
| `enum update … --remove-value`, `--replace-with`, `--rename-value` | значения перечисления |
| `lock acquire\|release\|show <вид> <сущность>` | виды сущностей и сущности этого вида |
| `mcp workspace remove <Tab>` | области, разрешённые в MCP (из глобальных настроек) |
| `manual\|howto <Tab>`, `--lang` | темы справочника на языке, уже набранном в строке (`--lang`, иначе `TASKER_LANG`), и языки, найденные в каталоге страниц; область не открывается, и `-w`/`--sqlite`/`-p` у `manual` и `completion` не предлагаются |
| `-w`, `--sqlite`, `mcp workspace add`, всё остальное | нечего подсказать — оболочка предлагает файлы, как обычно |

Дополнение работает на каждое нажатие Tab, поэтому быстрое и тихое: область открывается только если она уже есть (ничего не создаётся: нет `.tasker` или файла SQLite — вариантов нет), демон не запускается, дольше 1,5 с не ждёт, вариантов не больше 50; при любой ошибке (нет области или доступа, формат файлов новее, проект не выбран) ответ пустой и в stderr ничего нет. Кириллица и пробелы в названиях работают: оболочка экранирует их сама (`Основная\ доска`, `"Основная доска"`, `'Основная доска'` понимаются одинаково).

**Подключение.** `scripts/install.sh` (macOS и Linux) кладёт скрипты в `<prefix>/share/tasker/completions/` (`_tasker` для zsh, `tasker.bash` для bash) и сам подключает их к вашей оболочке — по `$SHELL`: в `~/.zshrc` (zsh) или в файл bash: на Linux `~/.bashrc`, на macOS — тот, который читает login-оболочка (первый существующий из `~/.bash_profile`, `~/.bash_login`, `~/.profile`, иначе создаётся `~/.bash_profile`), дописывается один помеченный блок `# >>> tasker completion >>>` … `# <<< tasker completion <<<`. Правка безопасная: повторная установка заменяет блок, а не дублирует (актуальный блок — файл не трогается), перед первой правкой делается копия `<файл>.tasker-backup`, остальное содержимое файла не меняется, в конце установщик пишет, что изменено и как отменить. `--no-completion` файлы оболочки не трогает (скрипты всё равно кладутся), `--uninstall` убирает блок (только свой: по пути установки) и скрипты. Новое окно терминала (или `source ~/.zshrc`) — и Tab работает. Отменить вручную — удалить блок из файла.

Без установщика: `eval "$(tasker completion bash)"` или `source <(tasker completion zsh)` (в zsh после `compinit`) в файле настроек. Скрипт печатает `tasker completion zsh|bash|pwsh`. **PowerShell (Windows, macOS, Linux)**: `tasker completion pwsh --install` — см. [«Windows: консоль»](Консоль#windows-консоль-tsk-119) ниже. cmd.exe автодополнение не поддерживает.

**Устройство.** Скрипты оболочек знаний о командах не содержат: они вызывают директиву `tasker "[suggest:позиция]" "строка без имени программы"` (строка — как набрана, до курсора) и отдают ответ (по варианту в строке) оболочке: zsh через `compadd`, bash через `COMPREPLY` с экранированием и учётом кавычек и разделителей слов readline (`=`, `:`). Нет вариантов — файловое дополнение оболочки. Директива (`Completion/CompleteDirective.cs`) разбирает строку по правилам оболочки (`Completion/ShellWords.cs`), берёт команды и параметры из дерева System.CommandLine, значения — из источников (`Completion/Sources.cs`): источник цепляется к аргументу или параметру одной строкой `.Suggests(g, Sources.Statuses)`. Параметры не предлагаются, пока слово не началось с «-» (или предлагать больше нечего). Аргумент команды без источника не проходит тест: либо `.Suggests(g, …)`, либо явная пометка `.NoSuggestions()` (имя новой сущности, число, путь). Для PowerShell директива вызывается как `[suggest:позиция:pwsh]`: строку тогда разбирают по правилам PowerShell (`'…'` и `''`, обратный апостроф, `\` — обычный знак; `ShellDialect` в `ShellWords.cs`). Новая оболочка: скрипт в `Completion/Shells/`, строка в `Completion/Shells.cs` и ветки в `scripts/install.sh` (`completion_file`, `completion_rc`, `completion_block`).

### Windows: консоль (TSK-119)

Консоль работает в Windows Terminal, PowerShell 7, Windows PowerShell 5.1 и cmd.exe. Подробности для пользователя — `tasker manual windows`. Здесь — устройство.

- **Кодировка (`ConsoleSetup.cs`).** Только на Windows. В окне консоли кодовая страница вывода и ввода переключается на UTF-8 при запуске и возвращается при выходе. Перенаправленный stdout, stderr и stdin обходят `Console` и работают напрямую с потоками: UTF-8 без BOM (ввод — с распознаванием BOM). Нет консоли (процесс без окна) — это не ошибка. Расшифровка вывода — дело оболочки: PowerShell читает программы в `[Console]::OutputEncoding` (по умолчанию кодовая страница окна), см. мануал. Аргументы и переменные окружения приходят в Юникоде.
- **Пути (`UserPath`).** `~`, `~/…` и `~\…` раскрывает сам `tasker` (cmd.exe и PowerShell не раскрывают `~` в аргументах программ): `-w`, `--sqlite`, `mcp workspace add|remove`, `TASKER_HOME`, подсказки пути при дополнении.
- **Имя пользователя (`OsUser`).** Для блокировок и `whoami` без `whoami <имя>` — имя ОС без домена: `DOMAIN\user` и `user@domain` дают `user`.
- **Ширина (`Terminal.UsableColumns`).** На Windows из `Console.WindowWidth` вычитается один столбец: в conhost строка на всю ширину переносится сама, и перевод строки после неё давал бы пустую строку. `COLUMNS`/`TASKER_WIDTH` берутся как заданы.
- **Автодополнение PowerShell (`Completion/Shells/tasker.ps1`).** `Register-ArgumentCompleter -Native -CommandName tasker, tasker.exe`; работает в PowerShell 7 и 5.1 (файл только ASCII, без синтаксиса новее 5.1). Строку после имени программы до курсора передаёт директиве `[suggest:позиция:pwsh]`, запуская `tasker` как процесс с аргументами по правилам Windows (5.1 сам не экранирует кавычки) и с выводом в UTF-8, в текущей папке PowerShell (а не процесса); ответ кладёт в `CompletionResult`: слова с пробелами и знаками PowerShell — в одинарных кавычках (`'` удваивается), у `Имя=`, `TSK-` кавычка остаётся открытой. Ошибки молчат, нет ответа — PowerShell предлагает файлы. `tasker completion pwsh --install` (`Completion/PowerShellProfile.cs`, `PowerShellProfileFiles.cs`): скрипт — `<данные Tasker>/completions/tasker.ps1`, в профили (Windows: `Документы\PowerShell\…` и `Документы\WindowsPowerShell\…`; иначе `~/.config/powershell/…`) — помеченный блок, подключающий файл, если он есть. Повторная установка заменяет блок; копия `.tasker-backup` один раз; кодировка профиля сохраняется (BOM; BOM добавляется, если появился не-ASCII текст); профиль не в UTF-8 не трогается. Установщик Windows (`scripts/install.ps1`) вызывает эту команду; `--no-completion` у него — не вызывать.
- **Тесты (`WindowsConsoleTests`).** Чистые функции и golden-проверки скрипта идут везде. Настоящий PowerShell: тест запускает `pwsh` из PATH или, если его нет, контейнер Docker из переменной `PWSH_DOCKER_IMAGE` (образ с `pwsh`; на Apple Silicon подойдёт `FROM mcr.microsoft.com/dotnet/sdk:10.0` + `RUN dotnet tool install --global PowerShell`) и подменяет `tasker` sh-скриптом; без них — пропуск. На Windows эти проверки не идут (подставной `tasker` — sh-скрипт). Проверенное только на Windows перечислено в задаче TSK-119, раздел [«ПРОВЕРИТЬ НА WINDOWS»](Windows#проверить-на-windows).

## Производительность консоли

Обычная команда `tasker` — отдельный процесс: он сам открывает область (демон для этого не нужен; к демону обращается только `sync`), сверяет индекс с файлами и выполняет операцию. Время вызова складывается из старта рантайма (~35 мс — пол .NET), построения дерева команд и контейнера, открытия индекса и самой операции; около 80 мс уходит на JIT (≈1000 методов: дженерики и `async` над типами приложения, Autofac, System.Text.Json).

**Как измерять** (ничего не трогает в настоящей установке: временные `TASKER_HOME`, область и свой демон на свободном порту):

```
scripts/perf/publish.sh /tmp/tasker-bin                       # tasker и tasker-mcpd так же, как у релиза (R2R, self-contained)
scripts/perf/bench.py calls   --bin /tmp/tasker-bin --phases  # медианы version / status list / task list / task get / task create + фазы
scripts/perf/bench.py degrade --bin /tmp/tasker-bin --steps 100 500 1000 2000 --soak 200            # от числа задач и числа вызовов
scripts/perf/bench.py degrade --bin /tmp/tasker-bin --clients 8 --steps 100 500 1000 --soak 200      # то же, 8 параллельных клиентов
        --mode nodaemon   # без демона (по умолчанию daemon: демон запущен и следит за областью)
```

`TASKER_PROFILE=1 tasker …` печатает в stderr фазы вызова (`[profile] имя мс_от_старта_процесса число_JIT-методов`) и счётчики (`[count]`: обращения к индексу, время JIT). Какие методы компилируются JIT: `DOTNET_JitStdOutFile=f DOTNET_JitDisasmSummary=1`. Замеры на общей машине шумят: стенд печатает load average и загрузку CPU в начале и конце, берёт медиану и p90; ключевые измерения повторяйте.

**Что нашли.**

- Последовательно и на тихой машине время вызова **не** растёт ни с числом выполненных вызовов (200 подряд: отношение 0,98), ни заметно с числом задач (100 → 2000 задач: +5–10 %, обход файлов — десятки микросекунд на файл). Деградация до 1,5–2,7 с — это параллельность и нагрузка: каждый вызов — ~0,2 с CPU (в основном JIT), а вызовы делят очередь на `.cache/index.lock` (у одного вызова ~9 обращений к индексу), поэтому 8 одновременных клиентов ждут друг друга, а на загруженной машине (load 10–15) время вызова вырастало втрое.
- Лишнее в каждом вызове: `FileSystemWatcher` на `.tasker` (77 мс на запуск и остановку на macOS; консоли слежение не нужно), проверка опечаток в `TASKER_*` рефлексией по всем настройкам (25 мс), Autofac строил фабрики (дерево выражений + JIT) для всех ~40 регистраций, дерево всех команд, JSON сущностей индекса через отражение, `task get` строил JSON и в текстовом режиме, лишнее соединение SQLite ради строки журнала, опрос занятой блокировки с паузой до 50 мс.

**Что сделано.** Слежение в консоли выключено (`Session.Open(watch: …)`, `FileStorageModule(watchFiles: …)`); проверка окружения — только при чужой переменной `TASKER_*`; JSON индекса — source-generator (`IndexJson.cs`); для одной команды строится только её ветка дерева (справка, автодополнение и опечатка в имени — полное дерево); сервисы регистрируются «по требованию» (`LazyRegistration`); потолок опроса `FileLock` 50 → 5 мс; SQLite прогревается до `index.lock`; `TieredPGO` и фоновый GC выключены. Тесты: `PerformanceGuardTests` — отношения времени 200-го вызова к первому и 500 задач к 50 (с запасом ×3–4, чтобы не флакать), ветка дерева равна части полного.

**Цифры** (мс, медиана; 100 задач, демон запущен; до — сборка на коммите перед TSK-92, после — эта; машина load ≈ 5–7, 25 вызовов):

| команда | до | после |
|---|---|---|
| `--version` | 73–101 | 59 |
| `status list` | 251–272 | 145 |
| `task list --limit 1` | 272–299 | 165 |
| `task get TSK-1` | 318–340 | 194 |
| `task create` | 341–354 | 232 |

Параллельно, 8 клиентов, load 10–15 (шум!): `task get` 1050–1190 → 650–880 мс, p90 1,6–1,8 с → 0,75–0,97 с; 8 клиентов с демоном: p90 1,3 → 0,6 с. Время от числа вызовов в обоих вариантах плоское.

**Чего ещё нет.** Пол — процесс .NET с JIT (~150 мс на `get`; цели 0,15 с достигает только `status list`/`list`). Дальше — тонкий клиент, исполняющий команду в прогретом демоне (TSK-99), и чтение индекса без `index.lock` (TSK-100, граница с TSK-96).

## Обновление кэша после git (`tasker sync` и хуки)

Файлы `.tasker` — источник правды, а кэш (индекс) пересобираемый. Его обновляют разные части: процесс, который что-то записал, обновляет свой путь сразу; процессы, которые держат папку открытой (десктоп, демон MCP), следят за файлами и подхватывают `git pull`, `checkout` и слияния (с задержкой около 0,3–2 с); любой запущенный `tasker` при старте сверяет кэш с диском (перечитываются только изменившиеся файлы: на 10 000 задач это около 0,1 с). Чтобы кэш обновился **сразу** после команды git, есть два инструмента:

- **`tasker sync`** — сверить кэш папки с файлами сейчас и вернуться, когда он актуален. Если демон MCP обслуживает эту папку, команда просит его (`POST /daemon/sync`: он уже держит индекс), иначе сверяет сама (`via daemon` или `via direct` в выводе). Файлы, которые не удалось прочитать (конфликт слияния git, битый YAML), показывает сразу: `N file(s) cannot be read …`. `--quiet` — молчать, если всё в порядке (для хуков); в папке без `.tasker` команда ничего не создаёт: ошибка, а с `--quiet` — тишина. У SQLite кэша нет — сверять нечего.
- **`tasker hooks install`** — ставит git-хуки `post-merge` (pull, merge), `post-checkout` (checkout, switch, новое рабочее дерево) и `post-rewrite` (rebase, amend), которые запускают `tasker sync --quiet` для этой папки. Кэш обновляется в момент команды git — без задержки слежения и даже когда ни демон, ни десктоп не запущены. `tasker hooks status` показывает состояние, `tasker hooks uninstall` убирает хуки.

Как устроены хуки:

- **Чужие хуки не ломаются.** Блок Tasker помечен маркерами и вставляется сразу после строки `#!` (чтобы `exit` в чужом скрипте его не отменял); остальное остаётся как есть. Установка идемпотентна, удаление убирает только блок (хук, в котором больше ничего нет, удаляется).
- **Хук не мешает git.** Ошибка `tasker sync` не прерывает команду git (`|| true`); нет `tasker` по записанному пути — хук молчит.
- **Путь и рабочие деревья.** В хуке записан путь к запущенному `tasker`; рабочая папка вычисляется при запуске от корня репозитория (`git rev-parse --show-toplevel` + путь папки в репозитории), поэтому хук работает и в других рабочих деревьях (`git worktree`), и когда рабочая папка — подпапка репозитория. `core.hooksPath` учитывается.
- **Ограничения git.** Хуки локальные — ставить надо в каждом клоне. Команды git, после которых хуков нет (`git reset --hard`, `git stash pop`, `restore`), кэш не обновят: его догонит слежение демона или десктопа либо следующий `tasker`. Слияние с конфликтом `post-merge` не вызывает; после правки конфликта вызывайте `tasker sync` (он покажет, какие файлы ещё нечитаемы).
