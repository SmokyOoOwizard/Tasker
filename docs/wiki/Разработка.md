# Разработка

Всё написано на .NET (`dotnet/`): консоль `tasker`, демон `tasker-mcpd`, сервер и тесты. Нужны .NET SDK 10 и Node.js с npm (фронтенд); для сборки консоли NativeAOT — ещё C-компилятор платформы (Xcode Command Line Tools на macOS, `clang`, `zlib1g-dev` и `libsqlite3-dev` на Linux, Visual Studio с C++ на Windows). Остальное тянется через NuGet и npm.

## Структура

`dotnet/` — решение .NET, `tests/golden` — корпус эталонов поведения консоли и демона. В корне — `frontend/`, `scripts/`, `docs/wiki/`, `.tasker` (задачи самого проекта), `VERSION`, `README.md`.

| Папка | Что там |
|---|---|
| `dotnet/` | `Tasker.slnx`, `Directory.Build.props` и всё, что собирает `dotnet build` |
| `dotnet/src/Tasker.Cli` | консоль `tasker`: команды (`Commands/`), автодополнение, справочник `manual`, интерактивный режим `-i` (`Interactive/`) |
| `dotnet/src/Tasker.Daemon.Host` | демон MCP `tasker-mcpd`: супервизор, рабочий процесс, замена на лету |
| `dotnet/src/Tasker.Core` | домен и сервисы |
| `dotnet/src/Tasker.Configs` | настройки из переменных окружения и аргументов |
| `dotnet/src/Tasker.Storage.Files`, `dotnet/src/Tasker.Storage.Db` | хранение файлами (`.tasker`) и в БД (EF Core: SQLite, Postgres) |
| `dotnet/src/Tasker.Mcp` | инструменты MCP поверх сервисов Core (у сервера — по токену агента, у демона — область аргументом `workspace`) |
| `dotnet/src/Tasker.Web` | API и встроенный фронтенд (`frontend/dist` как ресурс) |
| `dotnet/src/Tasker.Server` | хост сервера (ASP.NET Core) |
| `dotnet/src/Tasker.Global`, `dotnet/src/Tasker.Daemon` | глобальные настройки; клиент демона: `daemon.json`, `/daemon/status`, запуск `tasker-mcpd`, службы автозапуска, области в `settings.json` |
| `dotnet/tests/Tasker.Tests` | тесты xUnit |
| `dotnet/tools/Tasker.Stress` | стенд параллельной работы (гоняет процессы `tasker` и `tasker-mcpd`) |
| `tests/golden/` | эталоны поведения консоли и демона (см. ниже) |
| `frontend/` | React + TypeScript (Vite), единственный фронтенд |
| `scripts/` | установка, релиз, тесты в Docker, стенд замеров |

## Сборка и запуск

Консоль и демон:

```bash
dotnet build dotnet/src/Tasker.Cli    # консоль; сборка кладёт рядом и демон tasker-mcpd (bin/Debug/net10.0/)
scripts/install.sh --from-source      # собрать (NativeAOT, как релиз) и установить в ~/.local
```

Сервер: фронтенд встраивается при сборке .NET, поэтому сначала он:

```bash
cd frontend && npm install && npm run build
dotnet build dotnet/Tasker.slnx            # или dotnet build из папки dotnet/
```

| Что | Команда |
|---|---|
| Сервер (:5156, SQLite в памяти) | `dotnet run --project dotnet/src/Tasker.Server` |
| Сервер с файлом SQLite | `dotnet run --project dotnet/src/Tasker.Server -- --sqlite=tasker.db` |
| Фронтенд с hot reload | сервер, затем `cd frontend && npm run dev` (Vite на :5173, `/api` идёт на :5156) |

Боевые настройки сервера (Postgres, ключ подписи): [Настройка и сервер](Настройка-и-сервер). Линтер фронтенда: `npm run lint`. Сборка без встраивания фронтенда (тесты): `-p:EmbedFrontend=false`.

## Тесты

.NET (консоль, демон, сервер, домен и сквозные сценарии):

```bash
dotnet test dotnet/Tasker.slnx                                                 # все
dotnet test dotnet/tests/Tasker.Tests --filter "FullyQualifiedName~CliTests"   # по фильтру
scripts/test-linux.sh [--filter "..."]    # на Linux в Docker (нужен docker)
scripts/test-linux.sh --stress "upgrade"  # стенд вместо тестов
```

- В CI (`.github/workflows/dotnet-tests.yml`) сборка решения и `dotnet test` идут на Linux, macOS и Windows; результаты (trx) — артефактом прогона.
- Тесты сквозные: настоящее хранилище (файлы; SQLite — у сервера и демона), процессы `tasker`, демон на свободном порту с отдельным `TASKER_HOME`.
- Идут параллельно: окружение переопределяется через `AppEnvironment.Override`; менять переменные окружения и текущую папку всего процесса в тестах нельзя.
- Тест под конкретную ОС помечается `[PlatformFact(TestPlatform.Windows)]`: на других системах он считается пропущенным.

### Консоль и демон в тестах

Сквозные тесты запускают настоящие процессы `tasker` и `tasker-mcpd` (`TaskerProcess`, `TestWorkspace`, `DaemonFixture`). Сборка тестов
(и стенда) кладёт их рядом с собой: проект тестов ссылается на `Tasker.Cli` и `Tasker.Daemon.Host`. Переменная `TASKER_BIN` подменяет
консоль на другой исполняемый файл (`tasker-mcpd` консоль ищет рядом с собой), `TASKER_MCPD_BIN` — программу демона для тестов,
которые запускают его сами (`TaskerProcess.DaemonCommand`); переменные читаются один раз при загрузке сборки тестов и дочерним
процессам не передаются (`TestRun`).

- Интерактивный ввод (подтверждение `project delete`) — псевдотерминал на стандартном вводе (`TestWorkspace.RunWithInput(…, interactive: true)`, python3 `pty`, macOS и Linux).
- Автозапуск — поддельные `launchctl` и `systemctl` первыми в PATH (`AutostartTests`): настоящие launchd и systemd не трогаются.
- Рабочая область, открытая общим .NET-кодом хранилищ (`Session` в тестах), работает одновременно с процессами `tasker`.

Стенд параллельной работы (временная папка, свой демон; данные и демон на 5719 не трогает; код возврата 1 при нарушении инвариантов):

```bash
dotnet run -c Release --project dotnet/tools/Tasker.Stress -- --clients 10 --client mix --scenarios create,locks
```

## Golden-корпус

`tests/golden/` — эталоны поведения консоли и демона: каноническая область `.tasker` со всеми сущностями и «опасными» строками,
версии файлов, стиль YAML, вывод команд консоли, результат `migrate`, снапшоты MCP, разделы SQLite и кэша индекса (подробности —
`tests/golden/README.md`). С ним сверяют сборку .NET-тесты `Golden*Tests`.

```bash
dotnet test dotnet/tests/Tasker.Tests --filter "FullyQualifiedName~Golden"                          # сверить сборку с корпусом
TASKER_GOLDEN_UPDATE=1 dotnet test dotnet/tests/Tasker.Tests --filter "FullyQualifiedName~Golden"   # переснять эталоны этой сборкой
git diff --stat tests/golden                                                                          # что изменилось в поведении
```

Расхождение с корпусом — ошибка. Намеренное изменение вывода консоли, схемы инструментов MCP или формата файлов меняет и корпус в том же
изменении: эталоны переснимаются режимом `TASKER_GOLDEN_UPDATE=1`, дифф `tests/golden` и есть список изменений поведения, его надо
просмотреть целиком. Снапшоты с путями переснимаются на macOS или Linux.

## Устройство

- DI: у сервера и демона — Autofac. `TaskerWebApp.CreateBuilder<THostModule>()` подключает `CoreModule` и `WebModule`, хост добавляет `ServerModule` или `DaemonModule`. Консоль собирает сервисы без контейнера (`CoreServices`, `FileWorkspaceStorage`): так она быстрее запускается и собирается NativeAOT.
- Логи: Serilog, настраивается в `Program` хоста. Сервер пишет в консоль.

| Добавить | Шаги |
|---|---|
| Команду консоли | класс в `dotnet/src/Tasker.Cli/Commands/` и строка в `CliApp.BuildRoot`; вывод `--json` — через `Context.Print`, новые типы DTO — в `CliJsonContext` |
| Инструмент MCP | метод с `[McpServerTool]` в `dotnet/src/Tasker.Mcp/Tools`; `tools/list` сверяется с `tests/golden/expected/mcp/tools-list.json` (`McpInputSchemaTests`) |
| Страницу интерфейса | компонент в `frontend/src/pages`, маршрут в `frontend/src/App.tsx` |

## Сборка релиза

```bash
scripts/release.sh                                   # все платформы, которые собираются на этой машине -> artifacts/release/<версия>/
scripts/release.sh --rid osx-arm64,osx-x64           # выбранные; --rid all — все восемь или ошибка до сборки
scripts/release.sh --rid linux-musl-x64 --builder docker  # Linux musl в контейнере Alpine
```

Скрипт собирает консоль `tasker` (`dotnet publish -p:PublishAot=true`) и демон `tasker-mcpd` (один файл с рантаймом: `PublishSingleFile`)
для восьми RID — `osx-arm64`, `osx-x64`, `linux-x64`, `linux-arm64`, `linux-musl-x64`, `linux-musl-arm64`, `win-x64`, `win-arm64`.
NativeAOT собирает только свою ОС: macOS и Windows — обе архитектуры на своей ОС, Linux — архитектуру машины (musl — в Docker или на
musl-машине). Консоль на macOS и Linux использует системную SQLite (`-lsqlite3`), на Windows рядом лежит `e_sqlite3.dll`. Архив
`tasker-<версия>-<rid>.tar.gz` (Windows — `.zip`): `app/` с программами, установщик и `release.txt`; рядом `.sha256` и общий
`SHA256SUMS` (`shasum -a 256 -c SHA256SUMS`). Все платформы сразу — workflow `.github/workflows/release-build.yml` (каждая на машине своей
ОС и архитектуры, архивы — артефакты прогона; релизов и тегов он не создаёт).

Версия одна на все программы — файл `VERSION` в корне (`dotnet/Directory.Build.props`); `tasker --version` печатает её, у сборки из
исходников — с коммитом (`0.1.0+f2a114d`). Выпуск: правка `VERSION`, коммит, тег `v<версия>`, `scripts/release.sh` (тег должен
совпадать с файлом).

Автозапуск под настоящим systemd --user (Linux в Docker), в том числе для релизного архива:

```bash
scripts/test-linux-systemd.sh [--bin <каталог> | --archive <tasker-…-linux-arm64.tar.gz>]
```
