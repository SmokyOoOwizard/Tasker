# .NET NativeAOT против Rust: размер и скорость (TSK-177)

Вопрос задачи: можно ли оставить единственное ядро на C#, если собрать консоль и демон через .NET NativeAOT.
Критерии: каждый исполняемый файл — до 10 МБ; вызовы консоли медленнее Rust не больше чем на 10–20 %.

**Итог: NativeAOT критериям не соответствует.** Даже облегчённый вариант (без EF Core, с InvariantGlobalization) даёт 18 МБ у консоли
и 35 МБ у демона, а вызовы консоли на 50–150 % медленнее Rust. Больше половины разрыва на маленькой области — фиксированная цена
запуска процесса .NET (рантайм и большой бинарник). Правками кода её не убрать. По сравнению с текущей JIT+R2R-сборкой AOT при этом
быстрее в 4–7 раз.

## Как мерили

- Машина: Apple M5, macOS 27.2, osx-arm64. Базовая линия TSK-126 снималась на M2 Max, поэтому .NET JIT+R2R переснята здесь же.
- .NET-консоль (`src/Tasker.Cli`) и хост демона (`src/Tasker.Daemon.Host`) восстановлены из `d9042d3^` и собраны на текущих
  Tasker.Core / Storage.Files / Web / Mcp (ветка `task/tsk-177`). Все три .NET-варианта собраны из одного исходника.
- Rust: `scripts/perf/publish.sh`, профиль release, тот же коммит.
- Стенд: `scripts/perf/bench.py calls`, n = 25 вызовов на команду, области на 50, 100 и 2000 задач, режимы с демоном и без.
  Варианты прогонялись по очереди в каждом сочетании; для 50 и 100 задач — два круга, в таблицах медиана двух медиан.
  Загрузка машины во время прогонов: load1 ≈ 3–4 на 10 ядрах. Сырые замеры — `docs/perf-aot/*.json`.
- Сборка .NET: `scripts/perf/publish-dotnet.sh <каталог> r2r|aot [ключи msbuild]`.

Варианты:

| Вариант | Что это |
|---|---|
| .NET JIT+R2R | как старый релиз: self-contained, ReadyToRun |
| .NET AOT | NativeAOT с минимальными правками: рефлексия оставлена, EF Core на месте, ICU |
| .NET AOT-lite | то же + `InvariantGlobalization`, без EF Core и Npgsql (`-p:NoDb=true`: нет областей-файлов SQLite) |
| Rust | `tasker`, `tasker-mcpd` |

## Размер

| Вариант | tasker | tasker-mcpd | Ещё | Всего | Архив .tgz |
|---|---:|---:|---|---:|---:|
| .NET JIT+R2R | — | — | 390 файлов | 156,6 МБ | 59,1 МБ |
| .NET AOT | 39,1 МБ | 56,6 МБ | libe_sqlite3.dylib 1,7 МБ | 97,4 МБ | 39,2 МБ |
| .NET AOT-lite | 18,4 МБ | 35,5 МБ | libe_sqlite3.dylib 1,7 МБ | 55,6 МБ | 22,6 МБ |
| Rust | 5,2 МБ | 5,6 МБ | — | 10,8 МБ | 5,3 МБ |

Из чего состоит AOT-lite (машинный код по map-файлу ILC; метаданные, типы и GC-info добавляют примерно столько же):

- консоль (8,4 МБ кода): CoreLib 2,9 МБ; System.Text.Json на рефлексии и Linq.Expressions 1,2 МБ; HTTP-клиент к демону (Net.Http,
  Security, Sockets, Asn1, Cryptography) 0,8 МБ; Tasker.* 1,2 МБ; Linq и Regex 0,6 МБ; YamlDotNet, Autofac, System.CommandLine 0,4 МБ.
  EF Core и Npgsql давали ещё 20 МБ бинарника (39 → 18 МБ). «Не вырезать Tasker.*» стоит 1,2 МБ;
  `OptimizationPreference=Size`, `StackTraceSupport=false`, `UseSystemResourceKeys` — меньше 10 %.
- демон (16,5 МБ кода): CoreLib 5,0 МБ, System.Text.Json 2,6 МБ, Tasker.* 1,6 МБ, ASP.NET Core 1,3 МБ, MCP SDK 0,7 МБ,
  Microsoft.Extensions 0,7 МБ, криптография 0,5 МБ, Net.Http 0,4 МБ, Serilog 0,2 МБ.

Даже при полном переходе на генераторы и отказе от Autofac консоль, по оценке, останется около 10–14 МБ. Демон на ASP.NET Core и
MCP SDK в 10 МБ не уложится: один только минимальный веб-API на ASP.NET Core в AOT весит около 10 МБ.

## Откуда разрыв с Rust

1. **Запуск процесса.** До первой строки `Main` у AOT-lite проходит ~6 мс (у AOT с EF ~8,7 мс), весь `tasker --version` у Rust — 2,7 мс.
   Пустое AOT-приложение на 1 МБ стартует за 3,6–4,1 мс, то же приложение, раздутое до 29 МБ, — за 5,9 мс (`/bin/echo` — 1,9 мс).
   Значит, ~1,5 мс — инициализация рантайма .NET, остальное растёт с размером бинарника (загрузка и релокации dyld).
   Это 4–5 мс на каждый вызов, и правками кода их почти не убрать.
2. **Глобализация.** С ICU сравнение строк и инициализация культуры добавляли ~8 мс на вызов (task get 36 → 28 мс). Лечится
   `InvariantGlobalization`, но тогда сравнение без учёта регистра только ординальное — для кириллических slug-имён этого хватает.
3. **Сверка индекса с папкой на больших областях.** На 2000 задачах у .NET sync-indexed + sync-scan ≈ 12,7 мс, у Rust index-sync 6,6 мс.
   Это обход каталога и `FileInfo`; в C# можно ускорить.
4. Остальное (Autofac, YamlDotNet и JSON на рефлексии) на маленькой области — 1–2 мс.

Даже если убрать пункты 3 и 4 полностью, task get останется около 13–14 мс против 9,7 у Rust (+35–45 %).

## Что понадобилось, чтобы AOT вообще заработал (сделано в ветке)

- `strip` из Homebrew binutils перекрывал Apple-овский: публикация падала на шаге strip. Нужно `/usr/bin` первым в PATH.
- Autofac не находил конструкторы после тримминга → сборки Tasker.* целиком помечены `TrimmerRootAssembly` (`src/Aot.props`).
- System.Text.Json на рефлексии включён (`JsonSerializerIsReflectionEnabledByDefault`). Рефлексия не работает для записей с
  параметрами-значимыми типами (Guid, enum) — нужны генераторы: `DaemonJsonContext` (настройки, daemon.json, обмен с демоном),
  `HostJsonContext` (протокол супервизор↔воркер), `McpJsonContext` (51 тип аргументов и результатов инструментов MCP,
  список собран рефлексией по `[McpServerTool]`). Контексты ставятся первыми в цепочку резолверов `TaskerJson.Options`.
- `ConfigsParser` обходил ссылки сборок (`GetReferencedAssemblies` в AOT не поддерживается) → в AOT берутся уже загруженные сборки;
  классы настроек и инструменты MCP описаны для триммера (`Aot.Roots.xml`).
- Apple ld падал с «too many large addends», когда Tasker.Web и Tasker.Mcp помечались корнями целиком → корни только для нужных типов.
- Быстрый путь `getattrlist` в `CanonicalPath` (как в Rust): перебор системного временного каталога стоил ~9 мс на вызов. Это
  алгоритмическое выравнивание, оно ускорило и R2R; без него сравнение языков было бы нечестным.
- `-p:NoDb=true` вырезает EF Core из консоли и демона (условная компиляция в Session, TaskerWebApp, WorkspaceRegistry, StorageRegistration).

Проверено на AOT-сборке: все сценарии стенда, `mcp start/status/stop` с супервизором, MCP `initialize`, `tools/list`,
`tools/call` на чтение и запись (list_projects, list_statuses, create_status, create_field).

## Что ещё нужно для полноценного AOT (не сделано)

- Убрать Autofac: ручная регистрация или DI на генераторе. Сейчас он работает на рефлексии благодаря корням.
- Генераторы System.Text.Json для всех типов: вывод `--json` консоли (`Context.Print(object)`), REST Tasker.Web, индекс
  (`IndexJson`), блокировки; заменить `CascadeResultConverterFactory` (MakeGenericType) и необобщённый `JsonStringEnumConverter`.
- YamlDotNet — статический контекст (генератор) вместо рефлексии.
- EF Core для областей-файлов SQLite заменить на Microsoft.Data.Sqlite напрямую (как rusqlite в Rust): иначе +20 МБ на каждый бинарник.
- ASP.NET Core: 3 предупреждения RDG012, minimal API на генераторе; Serilog, MCP SDK (`AIFunctionFactory` на рефлексии).
- SQLite: нативная библиотека лежит отдельным `libe_sqlite3.dylib`, нужна статическая сборка.
- Предупреждения AOT/тримминга по проектам: Storage.Db 46, Web 33, Daemon 17, Daemon.Host 10, Core 9, Mcp 11, Cli 8,
  Storage.Files 7, Configs 4, Global 4; плюс пакеты Autofac, EF Core, Npgsql, YamlDotNet, AspNetCore.Http.Extensions.
- win-x64 не замерен: NativeAOT не собирается кросс-компиляцией с macOS, нужна машина с Windows.

## Вывод

| Критерий | .NET AOT-lite | Rust |
|---|---|---|
| Бинарник ≤ 10 МБ | нет: 18,4 и 35,5 МБ; после полного перевода — ~10–14 и ≥ 20 МБ (оценка) | да: 5,2 и 5,6 МБ |
| Медленнее Rust ≤ 10–20 % | нет: +60…+155 %; после доработок — около +35–45 % (оценка) | — |
| RSS демона | 97–101 МБ | 23–26 МБ |
| Архив релиза | 22,6 МБ | 5,3 МБ |

NativeAOT не укладывается ни в критерий размера, ни в критерий скорости. Перевод на AOT при этом потребует заметной работы по всему
коду: DI, сериализация, YAML, замена EF Core. По результату замеров единственное ядро — на Rust.
