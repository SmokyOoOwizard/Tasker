# План перевода консоли `tasker` и демона `tasker-mcpd` на Rust

Статус: черновик плана, код не тронут. Цель: убрать два недостатка .NET-сборки, которые не лечатся настройками
публикации, — время запуска консольной команды (пол процесса .NET + JIT ≈ 60–230 мс на вызов даже после TSK-92) и размер
релиза (самодостаточная папка `app/` со средой выполнения; trimming и единый файл невозможны: Autofac, EF Core,
System.CommandLine и ASP.NET Core опираются на рефлексию, см. `scripts/release.sh`).

Ориентиры после переноса: `tasker task get` — единицы-десятки миллисекунд (процесс без рантайма, без JIT), два статически
слинкованных бинарника по 3–8 МБ (LTO, `opt-level="z"`/`s`, `strip`, `panic="abort"`), без зависимостей кроме libc.

## 1. Границы

### Что переносим

| Сейчас (C#) | Строк | Куда в Rust |
|---|---|---|
| `Tasker.Cli` | 5 700 | бинарник `tasker` |
| `Tasker.Daemon.Host` | 2 100 | бинарник `tasker-mcpd` |
| `Tasker.Daemon` (клиент демона, автозапуск) | 1 700 | крейт `tasker-daemon` |
| `Tasker.Mcp` (62 инструмента) | 2 000 | крейт `tasker-mcp` |
| `Tasker.Core` (домен, сервисы) | 8 300 | крейт `tasker-core` |
| `Tasker.Storage.Files` (YAML + индекс SQLite) | 4 200 | крейт `tasker-files` |
| `Tasker.Global`, `Tasker.Configs` | 850 | крейт `tasker-core` (модули `settings`, `config`) |
| `Tasker.Web/Workspaces/*` — только часть, нужная демону (реестр областей, маршрутизация `/w/<key>`) | ~600 | крейт `tasker-mcpd` |

Итого порядка 25 тысяч строк C#; домен и хранилище переносятся целиком, потому что демон исполняет инструменты MCP поверх
тех же сервисов, что и консоль. Это не «обёртка над протоколом», а второй полноценный движок.

### Что остаётся на .NET

- `Tasker.Desktop` (Avalonia + WebView) и `Tasker.Server` (ASP.NET, REST, JWT, фронтенд). Они продолжают использовать
  C#-версии `Core`/`Storage.*`/`Web`, поэтому **C#-код домена и хранилища не удаляется**, пока десктоп и сервер не переедут
  (отдельное решение, в этот план не входит).
- Следствие: в переходный период на одной машине одновременно работают два движка над одной папкой `.tasker` — десктоп на
  .NET и консоль/демон на Rust. Это главное ограничение плана: всё, что лежит на диске и в локальных протоколах, должно быть
  совместимо байт в байт (раздел 3).

### Открытые вопросы объёма (решить до начала фазы 1)

1. **Режим `--sqlite` в консоли и в демоне** (хранилище `Tasker.Storage.Db`, EF Core, 3 300 строк). Варианты: (а) перенести
   на `rusqlite` с той же схемой таблиц; (б) не поддерживать в Rust-консоли, оставить только файловые области. Рекомендация:
   (б) в первом релизе Rust-версии с явной ошибкой «используйте .NET-сборку», (а) — отдельной фазой после переключения,
   если режим реально нужен кому-то кроме тестов. Postgres в консоли и демоне не нужен вовсе.
2. **Windows.** Сейчас поддержка экспериментальная и на Windows не проверялась. Предлагаю переносить Windows-ветки
   (отсоединённый процесс, Планировщик заданий, `WSADuplicateSocket`, именованное событие остановки, кодовая страница консоли)
   в той же фазе, что и Unix, но помечать их как непроверенные, как сейчас.

## 2. Архитектура Rust-решения

Cargo workspace `rust/` в корне репозитория (рядом с `src/`, чтобы C# и Rust жили в одном репозитории до переключения):

```
rust/
  Cargo.toml                workspace, общий профиль release
  crates/
    tasker-core/            домен: сущности, сервисы, валидация, версии, ShortId, JSON-конвенции, настройки, конфиг
    tasker-files/           папка .tasker: YAML-файлы, имена, formatVersion, миграции, атомарная запись, flock, индекс SQLite
    tasker-mcp/             62 инструмента MCP, фильтры workspace/projectId, коды ошибок, формат ответов
    tasker-daemon/          клиент демона (daemon.json, /daemon/*), запуск, автозапуск (launchd, systemd, schtasks)
    tasker-cli/             бинарник tasker
    tasker-mcpd/            бинарник tasker-mcpd: HTTP, реестр областей, супервизор, воркер
  tests/                    сквозные тесты: запуск бинарников, golden-корпус файлов
```

Ключевые зависимости и почему именно они:

| Задача | Крейт | Замечание |
|---|---|---|
| разбор командной строки | `clap` (builder API, не derive) | дерево команд строится по одной ветке, как сейчас в `CliApp.BuildRoot`; у `clap` есть свои completion-генераторы, но мы сохраняем **существующие** скрипты `tasker.bash/zsh/ps1` и директиву `[suggest]`, чтобы установленные пользователям скрипты не ломались |
| YAML | чтение: `saphyr` (наследник `yaml-rust`); запись: **свой эмиттер** | схема файлов плоская и маленькая (раздел 3.1); собственный эмиттер даёт байт-в-байт совпадение с YamlDotNet дешевле, чем подгонка чужого. `serde_yaml` не брать: заброшен и его вывод не совпадает |
| JSON | `serde_json` + свой `Formatter` | нужно повторить экранирование `TaskerJson` (сырые не-ASCII, экранируются только `"`, `\`, < 0x20, 0x7F–0x9F, U+2028/2029, одиночные суррогаты) |
| SQLite | `rusqlite` с `bundled` | индекс области, статически в бинарнике |
| HTTP-сервер | `axum` + `hyper` на `tokio` | демон; `tokio::net::TcpListener::from_std` принимает унаследованный дескриптор |
| MCP | `rmcp` (официальный Rust SDK MCP) — транспорт Streamable HTTP, stateless | проверить в фазе 0, что текущая версия даёт stateless-режим и ручное формирование `inputSchema` (нам нужно добавлять `workspace` и убирать `projectId` из `required`); если нет — реализовать JSON-RPC-слой самим, протокол небольшой |
| слежение за файлами | `notify` + собственный сборщик окон (`tasker-files::watch`) | окно 300 мс / потолок 2 с / порог 500 путей как сейчас; `notify-debouncer-full` не подходит: на FSEvents пара `Create` + `Remove` одного файла схлопывается в ничего, и удаление теряется |
| блокировки, setsid, fcntl | `nix`, `rustix` | `flock(LOCK_EX)` — совместимо с тем, как .NET реализует `FileShare.None` на Unix |
| Windows API | `windows-sys` | Job Object, `CreateProcessW`, `WSADuplicateSocketW`, именованное событие |
| хэши, id | `sha2`, `md5`, `uuid` | id типов связей по умолчанию — MD5 + `Uuid::from_bytes_le` (конструктор .NET `Guid(byte[])` little-endian!) |
| Unicode | `unicode-normalization` (NFC), `unicode-segmentation` (графемы для превью описаний) | |
| логи | `tracing` + `tracing-appender` | формат строк как у Serilog (`[ERR]`/`[FTL]`): консоль читает хвост журнала при неудачном старте демона |
| HTTP-клиент в консоли | `ureq` (блокирующий, без tokio) | консоль не должна тащить tokio ради одного запроса к `/daemon/status` |

Консоль — синхронный код без async-рантайма (запуск быстрее, бинарник меньше). Демон — `tokio`. Сервисы в `tasker-core`
пишутся синхронными; демон вызывает их через `spawn_blocking` или отдельный пул. Это сознательный отказ от `async` в
домене: в текущем C# сервисы асинхронны только потому, что так принято в .NET, реальной параллельности внутри одного вызова нет.

Профиль release: `lto = "fat"`, `codegen-units = 1`, `opt-level = "s"` (мерить против `3`: быстрее ли SQLite-запросы),
`panic = "abort"`, `strip = true`. Цели: `x86_64/aarch64-unknown-linux-gnu` (glibc, как сейчас; `musl` — бонус, с ним
уйдёт и требование ICU), `aarch64/x86_64-apple-darwin`, `x86_64/aarch64-pc-windows-msvc`.

## 3. Контракты совместимости (то, что нельзя менять)

Всё перечисленное проверяется автоматически в фазе 1–2 на golden-корпусе, снятом с текущей .NET-сборки.

### 3.1 Файлы `.tasker` (читает и пишет десктоп на .NET)

- Схема каждой сущности, порядок ключей, какие ключи опускаются при null/false/пустом списке — по `Storages/*File.cs`.
- Вывод YamlDotNet 18.1: LF, UTF-8 без BOM, camelCase, последовательности под ключом без отступа (`series:\n- seriesId: …`),
  многострочные строки литеральным блоком `|`/`|-`, кавычки только у строк, которые иначе прочитались бы как число/bool/null
  (`'007'`, `'true'`), `DateTimeOffset` в формате `O` (7 знаков дробной части, `+00:00`), Guid в форме `D`.
  **Перед написанием эмиттера снять эталоны** с реального YamlDotNet: стиль кавычек (`'` или `"`), строки с `#`, `: `,
  ведущими пробелами, пустые строки, `|-` против `|`.
- `formatVersion: 9` первой строкой; файлы новее не читать; старые читать с «апгрейдом в памяти» (только замена номера);
  `tasker migrate` переписывает версию и переименовывает в схему `<slug>-<id8>.yaml`.
- Версия сущности = первые 16 hex SHA-256 от байтов файла с CRLF→LF и без BOM. Она ходит через `--expected-version`, MCP
  и REST, поэтому Rust и .NET обязаны считать её одинаково.
- Slug имени файла: NFC, `Rune.IsLetterOrDigit` (категории L*, Nd), `ToLowerInvariant`, не более 60 UTF-16-единиц.
  В Rust: `char::is_alphabetic() || is_numeric()` даёт другое множество (Nl, No) — брать категории через `unicode-general-category`
  или `icu_properties`, а длину считать в UTF-16-единицах, не в `char`.
- `ToLowerInvariant` против `str::to_lowercase`: различия на спецсимволах (например, `İ`). Там, где результат попадает
  на диск или в индекс, воспроизвести .NET-поведение (простое посимвольное отображение без спец-правил), покрыть тестами.
- Атомарная запись: `<path>.tmp` → `rename`, без fsync, под `.cache/write.lock` (`flock`). Порядок захвата:
  `write.lock` → семафор файла → `index.lock`. Повторы открытия файлов — только на Windows.
- Блокировки правки `.cache/edit-locks/<Entity>-<guid>.json` — JSON в **PascalCase** (System.Text.Json по умолчанию).
- Маркеры `.cache/deleted-projects/<id>`, добавление строк в `.tasker/.gitignore`.

### 3.2 Индекс `.tasker/.cache/index.db`

Индекс — кэш, но функционально обязательный: все списки, поиск, `max(number)` для серий, циклы связей идут SQL-запросами.
Он **разделяется между процессами** через файл. Два пути:

- (А) воспроизвести схему `user_version = 10` точно, включая колонку `data` с JSON в PascalCase и числовыми enum
  (IndexJson, source-gen) — тогда Rust и .NET пишут в один файл. Дорого и хрупко: любое расхождение в `data` ломает чужой
  процесс, причём .NET при чужом `user_version` молча сносит таблицы.
- (Б) **свой файл** `.cache/index-rs.db` со своей схемой (рекомендуется). Общие остаются только блокировки (`write.lock`,
  `index.lock` не нужен — у Rust свой `index-rs.lock`) и источник истины — YAML. Цена: в переходный период два индекса на
  область (несколько МБ), каждый сверяется по `(size, mtime)` своим процессом. Инвариант нумерации серий сохраняется, потому
  что `max(number)` считается после `Refresh(tasks/)` под `write.lock` — его повторяем.

Принято (Б), TSK-131: файл `.cache/index-rs.db`, `PRAGMA user_version = 1`, блокировка `.cache/index-rs.lock`; таблицы `files`,
`task_series`, `task_links`, `task_fields`, `task_field_values` как у .NET, `data` — JSON serde моделей `tasker-core` (camelCase);
модуль `tasker_files::index`.

После того как десктоп/сервер тоже переедут (вне плана), остаётся один индекс.

### 3.3 Локальные протоколы демона (читает десктоп на .NET и .NET-консоль в переходный период)

- `<data>/mcp/daemon.lock` — `flock(LOCK_EX|LOCK_NB)` на весь срок жизни; десктоп опрашивает его каждые 500 мс и по нему
  отпускает порт.
- `<data>/mcp/daemon.json` — `{"pid","port","token","startedAt"}`, запись через `.tmp` + rename, права 0600.
- `GET /daemon/status`, `POST /daemon/sync|stop|upgrade`, `GET /health`, `GET /ready` с заголовком `X-Tasker-Control`;
  формы JSON `DaemonStatus`, `WorkspaceStatus`, `SyncResult`, `UpgradeResult` — camelCase, enum строками.
- `settings.json` (`userName`, `mcp.port`, `mcp.workspaces[{kind,path}]`), `settings.lock`, слежение с debounce 200 мс.
- Каталог данных: `TASKER_HOME` или `~/Library/Application Support/Tasker`, `$XDG_DATA_HOME/Tasker` (`~/.local/share/Tasker`),
  `%LOCALAPPDATA%\Tasker`; журнал `logs/mcp-YYYYMMDD.log` (7 дней).
- Ключ области: slug имени папки, повторы `-2`, `-3`; id области = 12 hex SHA-256 от `"Files:<канонический путь>"`.
- Протокол супервизор↔воркер: NDJSON по stdin/stdout, префикс `@tasker ` у строк воркера, сообщения `hello/ready/activate/
  active/drain/stop/workers/request/reply`, `--worker --listen-fd N` (Unix: дескриптор без `FD_CLOEXEC`),
  `listenSocket: "wsa:<base64>"` на Windows. Это **ключ к бесшовному переходу**: супервизор никогда не обновляется на месте,
  значит `tasker mcp upgrade` на .NET-супервизоре запустит Rust-воркер, и порт не закроется ни на секунду (раздел 5).
- Остановка: SIGTERM/SIGINT; на Windows именованное событие `Local\tasker-mcp-stop-<16 hex SHA-256 пути>`.

### 3.4 MCP

- Streamable HTTP, stateless, `/mcp`, только loopback (`Host`/`Origin`), `X-Tasker-Agent`, аргумент `workspace` во всех
  инструментах кроме `list_workspaces`, `projectId` необязателен при одном проекте, коды `[invalid] [forbidden] [not_found]
  [modified] [locked] [unsupported_format] [in_use] [unavailable] [failed]` в начале текста ошибки, `isError: true`.
- Экранирование JSON на проводе как у `WireJson` (сырой UTF-8 вместо `\uXXXX`).
- Имена, описания и схемы 62 инструментов — снять снапшот `tools/list` с .NET-демона и сравнивать в тесте.

### 3.5 Консоль

- Дерево команд, тексты справки, коды выхода (0, 1, 2 у `migrate --check`, 3 у `mcp status`), формат таблиц и обрезка по
  ширине, `--json` без отступов, строка `Found N, shown a-b`, подсказки по опечаткам в `TASKER_*` (Дамерау–Левенштейн),
  `tasker manual` (встроенные md), `tasker completion <shell>` печатает те же скрипты, директива `[suggest]`,
  `hooks install`, `sync`, `cleanup`, `migrate`, `lock`, `whoami`.
- Снапшоты вывода снять с .NET-версии; совпадение требовать для `--json` строго, для текстового вывода — построчно.

## 4. Фазы

Порядок выбран так, чтобы каждая фаза заканчивалась проверяемым артефактом, а переключение пользователей произошло
один раз и без простоя демона.

### Фаза 0. Зафиксировать поведение и снять эталоны (до кода на Rust)

1. Golden-корпус: скриптом на .NET-сборке создать область со всеми сущностями, всеми типами полей, многострочными и
   «опасными» строками (кавычки, `#`, `: `, кириллица, эмодзи, ведущие нули, `true`), всеми formatVersion 0–9, legacy-именами
   `<guid>.yaml`, файлом с маркером конфликта. Сохранить в `rust/tests/golden/` вместе с ожидаемыми версиями (хэшами),
   именами файлов и выводом ключевых команд (`task list --json`, `task get --json`, `sync`, `cleanup --check`, справка).
2. Снапшоты MCP: `tools/list` и ответы `list_workspaces`, `get_task`, ошибка каждого кода.
3. Сделать существующие сквозные тесты запускаемыми против **любого** бинарника: в `TestWorkspace`/`TaskerProcess`/`DaemonFixture`
   добавить `TASKER_BIN`/`TASKER_MCPD_BIN` (сейчас они запускают `dotnet tasker.dll`). Тесты, идущие через `CliApp.Run`
   в процессе, для Rust не годятся — их список известен (BoardConsoleTests, FieldCliTests, …); перевести самые ценные из них
   на запуск процесса или продублировать в Rust-тестах. Это самая дешёвая форма «проверки паритета»: ~840 тестов уже написаны.
4. Базовая линия скорости: `scripts/perf/bench.py` на текущей сборке (с демоном и без, 100 и 2000 задач) — чтобы было с чем
   сравнивать. Зафиксировать размер `app/` текущего релиза.
5. Решить открытые вопросы раздела 1 (режим `--sqlite`, Windows) и выбор (Б) по индексу.

Результат: папка эталонов, тесты с переключаемым бинарником, числа «до».

### Фаза 1. `tasker-core` + `tasker-files`: файлы байт в байт

1. Модели сущностей, `Validate`, `ShortId`, `TaskReference` (`PREFIX-N`, короткий id), `Versioning`, конвенции JSON
   (`TaskerJson`), канонизация значений полей (`FieldValues`: `007`→`7`, float `R`, даты `yyyy-MM-dd`).
2. Разбор YAML (saphyr) в модели с игнорированием неизвестных ключей; свой эмиттер; `formatVersion` и апгрейд в памяти.
3. Имена файлов (slug, `id8`, legacy), `WindowsNames`, `PathRules`, `CanonicalPath`, `PathBudget` (предупреждение о длине).
4. `AtomicFile`, `FileLock` (flock + повторы 1→5 мс до 30 с, реентерабельность в потоке), `WriteScope`.
5. Настройки (`settings.json`, `settings.lock`), каталог данных, `UserPath` (`~`), разбор `TASKER_*`/аргументов с подсказками.
6. `tasker migrate` целиком (это первая команда, которую можно проверить на реальной области).

Критерий готовности: для каждого файла корпуса `parse → emit` даёт идентичные байты; версии совпадают с эталоном; migrate на
копии корпуса даёт такие же файлы, что .NET.

### Фаза 2. Индекс и сервисы домена

1. Схема `index-rs.db` (свои таблицы; можно упростить `data` до собственного компактного JSON), `Sync` по `(size, mtime)`,
   `Refresh` путей, ошибки чтения в колонке `error`, полный пересбор при повреждении.
2. Сортировки (`WorkspaceIndex.Sort`): бинарная коллация, ранги типов/статусов, числовой порядок серий, `lower()` как
   `ToLowerInvariant`, NULL в конец.
3. Сервисы: Project, Status, StatusSet, TaskType (каскады Clear/Keep), Field/FieldEnum/FieldConversion, Board/ColumnFilters
   (взаимоисключающие условия колонок), Task (Create/Update/Delete, фильтры полей, дерево иерархии до глубины 10 и 5000 строк),
   Series (нумерация под `Exclusive`, Renumber), TaskLink/LinkCycles (BFS и Тарьян, лимит 20 000), LinkType (дефолтные типы с
   детерминированными id), EditLock (2 мин, ожидание 30 с), Cleanup, SeriesHealth/LinkHealth, Usages (единый текст 409).
4. Наблюдатель файлов (`notify`) с теми же окнами и порогом 500 путей — нужен только демону, но живёт здесь.

Критерий: Rust-тесты уровня сервисов повторяют сценарии SeriesCoreTests, TaskFieldsTests, LinkCoreTests, LinkCycleTests,
EditLockTests, FieldCatalogTests (самые большие классы, ~250 тестов); `cleanup --check` и `sync` на корпусе дают тот же отчёт.

### Фаза 3. Консоль `tasker`

1. Каркас: глобальные опции, `Session` (открытие области, проверка папки), `Context` (таблицы, `--json`, `Found …`, коды
   выхода, тексты ошибок `Not found:`/`In use:`/`Locked:`/`Modified by someone else:`), терминал и ширина, UTF-8 на Windows.
2. Команды по одной, в порядке частоты использования: `task`, `project`, `status`, `status-set`, `task-type`, `series`,
   `field`, `enum`, `board`, `link-type`, `lock`, `whoami`, `user`, `agent`, `sync`, `cleanup`, `migrate`, `hooks`, `manual`,
   `completion`, `mcp` (клиентская часть: `DaemonClient` по `daemon.json`, запуск отсоединённого процесса, автозапуск).
3. Автодополнение: директива `[suggest]` и источники (`Sources.cs`: проекты, задачи по префиксу, статусы…), существующие
   скрипты оболочек встраиваются как есть (`include_str!`).
4. `PerfTrace` (`TASKER_PROFILE=1`) — сохранить, чтобы `bench.py` работал без изменений.

Критерий: сквозные тесты фазы 0 проходят с `TASKER_BIN=rust`; `bench.py calls` показывает целевые времена; бинарник
статически слинкован и весит единицы МБ.

Консоль можно отдавать пользователям **раньше демона**: `tasker` на Rust умеет управлять .NET-демоном по тем же
`daemon.json`/`/daemon/*`, а `tasker mcp upgrade` просто продолжит передавать путь к тому `tasker-mcpd`, который лежит рядом.

### Фаза 4. Демон `tasker-mcpd`

1. Одиночный режим: `daemon.lock`, ожидание порта 5 с, Kestrel→axum на `127.0.0.1:<port>`, токен управления, `daemon.json`,
   `/health`, `/ready`, `/daemon/*`, loopback-фильтр, реестр областей (ключи, статусы `opening/open/failed`, повтор через 30 с),
   слежение за `settings.json`, журнал в `logs/`.
2. MCP: 62 инструмента поверх сервисов фазы 2; фильтры `workspace`, `DefaultProject`, `X-Tasker-Agent` и локальный агент;
   текст ошибок; экранирование на проводе. Снапшот `tools/list` совпадает с эталоном.
3. Супервизор и воркер: сокет без `FD_CLOEXEC` и `--listen-fd`, протокол NDJSON, `AcceptGate` (accept только при открытых
   воротах, `Connection: close` при дренаже, 503 + `Retry-After: 1` в фазе закрытия), перезапуск с backoff 0/1/2/5/10 с и
   лимитом 5 падений в минуту, `upgrade` с проверкой `require`, таймауты дренажа (`TASKER_MCP_DRAIN_*`). Windows:
   Job Object, `WSADuplicateSocketW`, именованное событие, `--supervised`/`TASKER_MCP_SUPERVISOR`.
4. Автозапуск: launchd plist, systemd unit (с тем же квотированием), Планировщик заданий (XML UTF-16 LE с BOM, `conhost --headless`).
   Файлы генерировать **дословно** как сейчас: `autostart enable` на уже стоящей службе должен давать байт-идентичный файл.
5. `tasker mcp run` (foreground), `mcp status` с кодом 3.

Критерий: DaemonTests, DaemonUpgradeTests, *McpTests, ParallelWorkTests, `scripts/test-linux-systemd.sh` проходят с
Rust-бинарниками; `tools/Tasker.Stress` (остаётся на .NET как внешний клиент) не находит нарушений инвариантов при смешанных
клиентах: Rust-консоль + Rust-демон + .NET-десктоп (REST) на одной области.

### Фаза 5. Сборка, релиз, переключение

1. `scripts/release.sh`: вместо `dotnet publish` — `cargo build --release --target …`. Кросс-сборка: `cargo-zigbuild` для
   Linux/macOS с одной машины либо матрица GitHub Actions по платформам (для Windows MSVC второе надёжнее). Архив тот же:
   `app/tasker`, `app/tasker-mcpd`, `install.sh`, `release.txt`; `VERSION` читается `build.rs`.
2. `install.sh`/`install.ps1`: убрать `--framework-dependent`, `--from-source` собирает `cargo`; раскладка `<prefix>/share/tasker/app`
   и ссылка `<prefix>/bin/tasker` не меняются, чтобы обновление было обычным `install.sh --from`.
3. Сценарий обновления у пользователя с работающим .NET-демоном под автозапуском:
   `install.sh` кладёт Rust-бинарники → `tasker mcp upgrade` (новая Rust-консоль, старый .NET-супервизор) → супервизор
   запускает `tasker-mcpd --worker --listen-fd N` (Rust), проверяет `ready` и `require`, активирует, дренирует старый воркер.
   Порт не закрывается. Супервизор остаётся .NET-процессом до первого `mcp restart`/перезагрузки — это штатно (он никогда
   не обновляется на месте и сейчас). Проверить этот сценарий тестом в Docker (есть `test-linux-systemd.sh`).
4. Документация: `Разработка.md` (Rust toolchain вместо .NET SDK для консоли и демона), `Установка.md`, `Платформы.md`
   (появится musl/Alpine, уйдёт требование ICU), README (размер и скорость).
5. Один-два релиза «параллельно»: Rust-сборка как основная, .NET-консоль доступна в архиве как `tasker-dotnet` на случай
   регрессий (только если фаза 0 выявит зоны риска, иначе не нужно).

### Фаза 6. Снос C#-кода консоли и демона

Удалить `Tasker.Cli`, `Tasker.Daemon.Host`, из `Tasker.Daemon` — всё, кроме того, что использует десктоп (`DaemonClient`,
`DesktopMcpPlan`, `DaemonFiles`), `Tasker.Mcp` — остаётся для десктопа и сервера. Тесты, завязанные на `CliApp.Run`, либо
переведены в Rust в фазе 2–3, либо удаляются. `tools/Tasker.Stress` остаётся на .NET как независимый клиент.

## 5. Риски и как их снять

| Риск | Чем грозит | Мера |
|---|---|---|
| Расхождение в байтах YAML | ложные `[modified]`, лишние диффы в git, перезапись файлов десктопом и консолью по кругу | golden-корпус и тест `parse→emit` байт в байт (фаза 1), стилевые эталоны YamlDotNet снимаются до написания эмиттера |
| Unicode: `ToLowerInvariant`, NFC, категории символов, длина в UTF-16 | разные имена файлов и ключи индекса у .NET и Rust → «две задачи с одним id», ложные переименования | тест на slug по корпусу строк (кириллица, умляуты, `İ`, эмодзи, комбинируемые знаки); реализация, воспроизводящая .NET, а не «правильная» |
| Общий `index.db` | .NET сносит таблицы при чужом `user_version`, Rust портит `data` для .NET | вариант (Б): свой файл индекса |
| Зрелость `rmcp` | stateless-режим, ручные схемы, SSE-ответы могут не совпасть с SDK .NET | spike в фазе 0: поднять эхо-сервер и прогнать `claude mcp add` + снапшот `tools/list`; запасной план — свой JSON-RPC-слой |
| Супервизор .NET + воркер Rust при `upgrade` | единственный момент, где два языка говорят по протоколу | тест в Docker: .NET-демон под systemd → `upgrade` на Rust; `ready`/`require`/`drain` таймауты как сейчас |
| Два движка на одной области (десктоп .NET) | расхождение правил домена → один клиент принимает, другой отвергает | правила зафиксированы тестами фазы 2; стресс-стенд смешанных клиентов в фазе 4; `formatVersion` не повышать до завершения переноса |
| Windows не проверен и сейчас | Windows-ветки Rust тоже останутся непроверенными | честно оставить статус «экспериментально»; хотя бы собирать `windows-msvc` в CI и гонять unit-тесты имён/путей |
| Объём: ~25 тыс. строк C# | долго, соблазн «упростить по дороге» | фазы с критериями; никаких изменений поведения до фазы 6 — только перенос; идеи улучшений записывать задачами в `.tasker` |
| Производительность индекса в Rust окажется не лучше | цель по времени не достигнута | профилировать `bench.py` после фазы 3; пол процесса в Rust ~1–3 мс, остальное — SQLite и чтение файлов, оно одинаково; ожидаемый выигрыш именно на рантайме/JIT (~60–200 мс) |

## 6. Что сознательно не делаем

- Не чиним и не улучшаем поведение по ходу переноса (кроме явных багов, которые найдут golden-тесты — их заводим задачами).
- Не трогаем формат `.tasker` и `formatVersion`.
- Не переносим десктоп, сервер, REST, JWT, фронтенд, Postgres.
- Не меняем раскладку установки, имена файлов состояния, порты, пути автозапуска, скрипты автодополнения.

## 7. Оценка

Ориентир по трудоёмкости при одном разработчике полной занятости (с учётом того, что поведение уже задокументировано
кодом и тестами, а не выдумывается):

| Фаза | Оценка |
|---|---|
| 0. Эталоны, тесты с переключаемым бинарником | 1–2 недели |
| 1. Core + файлы байт в байт | 2–3 недели |
| 2. Индекс и сервисы | 3–4 недели |
| 3. Консоль | 2–3 недели |
| 4. Демон, MCP, супервизор, автозапуск | 3–4 недели |
| 5. Релиз и переключение | 1 неделя |
| 6. Снос | 2–3 дня |

Итого порядка 3–4 месяцев. Первый полезный артефакт (Rust-консоль, управляющая .NET-демоном) появляется после фазы 3,
примерно на середине пути.
