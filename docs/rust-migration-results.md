# Rust против .NET: размер и скорость после переноса (TSK-136)

Итог фазы 3 плана `docs/rust-migration-plan.md`: консоль `tasker` и демон `tasker-mcpd` на Rust сравниваются с базовой линией
.NET (`docs/rust-migration-baseline.md`, TSK-126) тем же стендом `scripts/perf/bench.py` с теми же параметрами. Сырые замеры —
`docs/perf-baseline/rust-*.json` (Rust) и `docs/perf-baseline/net-*-20261010.json` (повтор .NET в тот же вечер).

**Коротко: цель достигнута.** Типичный вызов консоли — 8–15 мс вместо 140–230 мс у .NET (в 14–18 раз быстрее), на 2000 задачах —
24–39 мс вместо 183–270 мс; `tasker --version` — 4 мс вместо 60. Два бинарника по 4,3 и 5,0 МиБ (вместе 9,3 МиБ, архив 4,6 МБ)
вместо папки на 152 МБ и 377 файлов; консоль зависит только от `libSystem`.

### Где лежит область: системный temp и обычная папка

Стенд по умолчанию создаёт область в системном временном каталоге (`/var/folders/…/T`). К 2026-10-10 в нём ~50 000 записей, и
это заметно на обеих сборках: при открытии области путь приводится к каноническому виду (`CanonicalPath`), а он перечисляет каждый
каталог пути, чтобы узнать регистр имени. В .NET это фаза `container-register`: 10 мс в обычной папке, 22 мс 9 октября (temp
был меньше) и 148 мс сегодня — `status list` .NET в temp стал 286 мс вместо 152. В Rust то же перечисление стоило 43 мс; в этой
задаче оно заменено быстрым путём (`getattrlist` по полному пути на macOS, 0,1 мс), для .NET заведён баг TSK-150.

Поэтому основные таблицы ниже сняты с `--tmp <папка в домашнем каталоге>` (каталоги пути — единицы и сотни записей, как у
настоящей области пользователя): у .NET в таких условиях те же числа, что в базовой линии (на 5–8 % меньше), так что сравнение
честное. Прогоны в системном temp приведены отдельно.

## Размер

| | .NET (базовая линия) | Rust |
|---|---:|---:|
| Консоль `tasker` | apphost 122 КБ + общая папка | **4 554 928 байт (4,3 МиБ)** |
| Демон `tasker-mcpd` | apphost 122 КБ + общая папка | **5 206 816 байт (5,0 МиБ)** |
| Всё вместе | папка `app/` **152 МБ, 377 файлов** | **9,3 МиБ, 2 файла** |
| Архив `tar.gz` | 56 МБ | 4,6 МБ (4 775 773 байт) |
| Зависимости консоли (`otool -L`) | среда .NET (`libcoreclr`, `libclrjit`, 14 `.dylib`) | только `/usr/lib/libSystem.B.dylib` |
| Зависимости демона | то же | `libSystem`, `CoreFoundation`, `CoreServices` (FSEvents у `notify`) |

Оба бинарника в пределах цели плана 3–8 МБ. «Статически слинкованы» в смысле macOS: всё своё (SQLite, YAML, HTTP, MCP) внутри,
из системы — только `libSystem` (на macOS полностью статический бинарник невозможен); консоль не тянет `tokio`/`axum`/`rmcp`
(`cargo tree -p tasker-cli` — их нет: консоль синхронная, async-рантайм только у демона).

Что внутри консоли (`cargo bloat --release --crates`, сборка без `strip`): `.text` 3,2 МиБ — SQLite (C, ~840 КиБ), свой код
(`tasker_cli` 520 КиБ, `tasker_services` 420 КиБ, `tasker_files` 280 КиБ, `tasker_core` 76 КиБ), `std` 354 КиБ, `regex` (+`aho-corasick`,
`regex-syntax`) ~400 КиБ, `clap` 110 КиБ, `ureq` 73 КиБ; остальное — данные (тексты справки, страницы `manual`, таблицы Unicode).
Одного раздувающего крейта нет.

### Что пробовали

| Мера | `tasker` | `tasker-mcpd` | Скорость | Решение |
|---|---:|---:|---|---|
| `opt-level = "s"` (было) | 4,3 МиБ | 5,0 МиБ | — | **оставлено** |
| `opt-level = "z"` | 3,5 МиБ | 4,0 МиБ | на 20–45 % медленнее: `task get` на 2000 задачах 29,5 мс против 24,6, пересбор индекса на 2000 задач 209 мс против 144 | нет: выигрыш 0,8 МиБ при уже выполненной цели не стоит потери скорости |
| `opt-level = 3` | 5,8 МиБ | 6,9 МиБ | на 3–5 % быстрее: `task get` 23,9 мс, `task list --all --json` 68 против 71, пересбор индекса 136 против 144 | нет: +33 % размера за 1 мс; SQLite (C) в `s` почти не теряет |
| `-dead_strip_dylibs` (macOS) | без изменений | без изменений | запуск −1,2 мс (консоль не грузит `CoreFoundation`/`CoreServices`, которые тянет `notify`) | **включено** (`rust/.cargo/config.toml`) |

Сравнение `opt-level` — `optbench.py` из каталога задачи: одна область на 2000 задач, вызовы попеременно тремя сборками,
медианы из 20 (шум: load 7–8, относительные числа устойчивы). Фичи зависимостей уже урезаны (`default-features = false` у `clap`,
`axum`, `ureq`, `rmcp`, `tracing-subscriber`, `chrono`); `notify` в консоли — мёртвый код, его выбрасывает LTO, а библиотеки — `-dead_strip_dylibs`.

## Время вызова консоли (50 задач)

`bench.py calls --n 30 --tmp <папка>`: 30 вызовов каждой команды после прогревочного, время — от запуска процесса до завершения,
мс. Колонка «.NET 10-09» — базовая линия.

| `version` | 59 (57–63) | 4.3 (3.8–4.7) | ×14 | 60 |
| `status list` | 140 (137–143) | 7.8 (7.5–8.2) | ×18 | 152 |

### `--mode nodaemon`

|---|---:|---:|---:|---:|
| `version` | 60 (58–62) | 4.5 (4.2–5.0) | ×14 | 59 |

Режимы снова совпадают: консоль не ходит в демон, работающий демон (Rust или .NET) ей не мешает. Разброс у Rust ±5–10 % медианы
(p10–p90 укладываются в 1–2 мс).

Нижняя граница: запуск процесса из Python (`subprocess.run` `/usr/bin/true`) на этой машине — 2,1 мс, пустой Rust-бинарник — 2,7 мс,
`tasker --version` — 4,3 мс. Оставшиеся ~1,5 мс — загрузка 4,5 МБ бинарника с диска в память (страницы кода и данных) и проверка подписи.

## Зависимость от числа задач

`bench.py degrade --steps 100 500 1000 2000 --n 15 --tmp <папка>`: на каждом шаге область доращивается, затем по 15 вызовов;
медиана, в скобках p90, мс.

| 500 | 197 (202) / 16 (16) | 172 (178) / 14 (15) | 240 (244) / 20 (21) |
| 1000 | 197 (199) / 19 (20) | 172 (175) / 17 (19) | 242 (247) / 26 (29) |
| 2000 | 203 (212) / 25 (26) | 183 (189) / 24 (25) | 270 (275) / 39 (41) |

### `--mode daemon`

| Задач | get .NET / Rust, мс | list --limit 1 .NET / Rust, мс | create .NET / Rust, мс |
|---:|---:|---:|---:|
| 100 | 186 (190) / 13 (14) | 163 (167) / 11 (12) | 227 (232) / 15 (15) |
| 500 | 192 (199) / 16 (17) | 171 (177) / 14 (15) | 238 (241) / 20 (21) |

| 2000 | 195 (200) / 26 (27) | 171 (174) / 24 (26) | 255 (261) / 39 (41) |

RSS демона после 2000 задач и ~2200 изменений файлов: Rust — 7 МБ, .NET — 67 МБ в этом прогоне (36 МБ в базовой линии).

У Rust время растёт сильнее в процентах (100 → 2000 задач: `get` 13 → 25 мс, `create` 15 → 39 мс), но остаётся в десятках
миллисекунд, и в абсолютных числах на 2000 задачах Rust в 7–8 раз быстрее. Рост — это сверка индекса с диском на каждом вызове
(`index-sync`: обход папок и `stat` каждого файла — ~10 мс на 2000 файлов) и у `task create` ещё две сверки папки задач под
блокировкой записи (`exclusive` и обновление индекса после записи). Это поведение (индекс догоняет правки `git pull` и другого
движка без демона), а не лишняя работа; ускорение — задачей TSK-152.

## Разбивка по фазам (`TASKER_PROFILE=1`)

с `#` — счётчики: число вызовов за процесс и суммарное время. Фазы Rust: `main` — от запуска процесса (время старта у ядра,

### Где выигрыш (`task get`, мс)

| Что | .NET (сегодня, обычная папка) | Rust |
|---|---:|---:|
| Запуск процесса и среды выполнения (`main`) | 29 | 3,8 (из них ~2 — сам `fork`/`exec`) |
| Окружение, дерево команд, разбор | 9 | 0,2 |
| DI-контейнер Autofac (`container-register` + `container-build`) | 31 | — |
| Открытие индекса (`index-lock` + `index-schema`) | 20 | 0,7 |
| Сверка индекса с файлами (`sync-*`) | 7 | 1,3 |
| Сама команда (`get.*`) | 68 (из них ~50 — JIT) | 5,7 |
| Завершение и вне меток | ~15 | ~0 |
| **Итого** | **189** | **12,7** |

Ожидания базовой линии сбылись и с запасом: запуск среды (29 мс) → ~2 мс сверх `fork`/`exec`, JIT (50–80 мс) и Autofac (31–43 мс) исчезли
полностью. То, что базовая линия считала неулучшаемым, тоже стало дешевле: открытие SQLite с блокировкой — 18 → 0,7 мс, запись после
создания задачи (`sync-indexed` 88 + `sync-commit` 20 мс у .NET) — 3,5 мс на три сверки у Rust.

## Выводы

- **Цель плана — `tasker task get` за единицы-десятки миллисекунд — достигнута** на всех вызовах и всех размерах области: 4–15 мс на
  50 задачах, 24–39 мс на 2000 (.NET: 59–228 и 183–270 мс). Ускорение типичного вызова — в 14–18 раз, `task create` на 2000 задачах — в 7 раз.
- **Цель по размеру достигнута**: 4,3 + 5,0 МиБ против 152 МБ (в 16 раз меньше; архив — в 12 раз), консоль без внешних зависимостей.
- Режим `daemon`/`nodaemon` на скорость консоли не влияет ни у .NET, ни у Rust.
- Где Rust выигрывает меньше всего: рост со числом задач (сверка индекса — `stat` каждого файла на каждом вызове, ~5 мкс на файл) и
  `task create` (три сверки). На 2000 задачах это 10–25 мс из 25–39 — следующий резерв (TSK-152), если области будут расти до десятков тысяч задач.
- Найдено попутно: перечисление каталогов в `CanonicalPath` стоит .NET 10–150 мс на вызов в зависимости от размера каталогов пути (TSK-150).

## Как повторить

```bash
# сборки
(cd rust && cargo build --release -p tasker-cli -p tasker-mcpd)
mkdir -p /tmp/tasker-rs && cp rust/target/release/{tasker,tasker-mcpd} /tmp/tasker-rs/
scripts/perf/publish.sh /tmp/tasker-net
ls -l /tmp/tasker-rs; otool -L /tmp/tasker-rs/tasker

# папка с малым числом записей на пути (как у настоящей области); без --tmp — системный temp
mkdir -p ~/tasker-bench-tmp
for bin in /tmp/tasker-rs /tmp/tasker-net; do
  for mode in daemon nodaemon; do
    scripts/perf/bench.py calls   --bin $bin --mode $mode --n 30 --tmp ~/tasker-bench-tmp --json calls-$mode.json
    scripts/perf/bench.py calls   --bin $bin --mode $mode --n 30 --phases --tmp ~/tasker-bench-tmp --json calls-$mode-phases.json
    scripts/perf/bench.py degrade --bin $bin --mode $mode --steps 100 500 1000 2000 --n 15 --tmp ~/tasker-bench-tmp --json degrade-$mode.json
  done
done

# автодополнение: сверка с .NET байт в байт (0 расхождений)
scripts/completion-diff.py --net /tmp/tasker-net/tasker --rs /tmp/tasker-rs/tasker --mode seeded
```

Файлы в `docs/perf-baseline/`: `rust-calls-{daemon,nodaemon}.json`, `rust-calls-nodaemon-phases.json`, `rust-degrade-{daemon,nodaemon}.json` —
с `--tmp` (основные таблицы); `rust-*-systemp.json` — в системном temp (там же фазы в режиме `daemon`); `net-*-20261010.json` — повтор .NET
с `--tmp`, `net-*-systemp-20261010.json` — в temp.
